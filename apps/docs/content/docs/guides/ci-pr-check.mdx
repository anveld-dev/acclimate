---
title: Run a pull request check
description: Gate pull requests on your quality policy with the Acclimate GitHub Action or the CI wrapper, then release the evaluated candidate after merge.
---

A PR check evaluates the agent files committed at one Git commit. It compares them with the channel's current release on your saved cases, applies your quality policy and fails the check when the policy fails. The check never releases. A separate job with a separate credential releases after merge.

The check uses the CI starter from your [SDK release](/docs/get-started/install): `ci.sh` (the wrapper), `action.yml` (a GitHub composite action), and `workflows/pr-check.yml` and `workflows/release.yml` to copy. You also need a trusted evaluator installed on the runner, with its private cases and a quality policy.

## Choose a runner

**Use a self-hosted runner with a persistent journal.** The evaluator's journal records whether execution started, so an interrupted run can resume without repeating paid work. That guarantee needs one host, a persistent owner-only POSIX volume, and the same journal and output directory on every run. NFS and other network file systems are not qualified, because the journal relies on `flock`. On this kind of runner, the wrapper reuses results across commits and resumes cancelled work.

**Ephemeral runners work in a degraded mode.** GitHub-hosted and autoscaled runners start without the previous journal, and `actions/cache` can't carry it because the journal is locked while in use and must stay on one host. In this mode, every attempt creates a fresh request and runs every case. An attempt that was cancelled or lost stays `running` until the service expires it and records it as interrupted. Nothing is reused. Budget for a full run on every push.

Never run the check for untrusted code on a self-hosted runner. See [forks and untrusted pull requests](#forks-and-untrusted-pull-requests).

## Add the GitHub Action

Copy `workflows/pr-check.yml` from the CI starter to `.github/workflows/agent-quality.yml`, then adjust the paths and variables.

```yaml title=".github/workflows/agent-quality.yml"
on:
  pull_request:
    paths: [agent/**]
permissions:
  contents: read
  pull-requests: write # only for the optional comment
concurrency:
  group: agent-quality-${{ github.event.pull_request.number }}
  cancel-in-progress: true
jobs:
  gate:
    if: github.event.pull_request.head.repo.full_name == github.repository
    runs-on: [self-hosted, acclimate-evaluator]
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false
          fetch-depth: 2
      - id: gate
        uses: anveld-dev/acclimate/examples/ci@v0.1.0
        with:
          app: /opt/acclimate/evaluator
          policy: /opt/acclimate/evaluator/quality-policy.json
          bundle: ${{ vars.ACCLIMATE_BUNDLE_ID }}
          bundle-dir: agent
          memory: none
          config-json: ${{ vars.ACCLIMATE_EVALUATOR_CONFIG }}
          token: ${{ secrets.ACCLIMATE_EVALUATE_TOKEN }}
          base-commit: ${{ github.event.pull_request.base.sha }}
          live: true
          max-cost-usd: '5'
          comment: true
```

To pin the action to code you reviewed, vendor it instead: extract the CI starter into your repository, for example as `.github/actions/acclimate`, and use `uses: ./.github/actions/acclimate`.

The step fails when the check doesn't pass. It writes a Markdown summary to the job page and annotations that name failed criteria, regressed cases and missing evidence. With `comment: true`, it keeps one PR comment up to date. If you make the check required, remove `paths:`. A skipped workflow leaves a required check pending. Reuse makes unchanged bundles cheap to check.

| Input | Use |
| --- | --- |
| `app`, `policy`, `bundle` | Required. The evaluator directory, the quality policy and the bundle ID. |
| `bundle-dir` or `payload` | The committed bundle source. `bundle-dir` defaults to `agent`. |
| `memory` | Approved `memory/` files, one per line, or `none`. |
| `config`, `config-json`, `service-url` | Where the evaluator config comes from. `config-json` holds the non-secret fields `serviceUrl`, `projectId`, `evaluatorPrincipalId` and optionally `journalRoot`. |
| `token`, `token-file` | The evaluator token. Pass a secret; it is never written to the job log. |
| `live` | Allows model-backed execution. It defaults to `false`. |
| `deadline`, `max-cost-usd`, `concurrency`, `shard`, `cases` | Passed to the evaluator's `run` command. |
| `commit`, `base-commit` | The commit to evaluate (default `github.sha`) and an optional base for the changed-file list. |
| `output-dir` | Request state and review exports. The default is `~/.acclimate-ci/OWNER-REPO`. |
| `abandon-uncertain`, `cancel-grace` | Recovery controls. See [cancellation](#cancellation-and-cancel-in-progress). |
| `comment`, `github-token` | The optional PR comment. |

Outputs: `result`, `verdict`, `comparison-id`, `request-id`, `candidate-version-id`, `candidate-digest`, `parent-version-id`, `exit-code` and `summary-json` (the path of the full JSON summary).

## Grant the least privilege

Give the PR check an evaluate-only grant for one workspace. That grant lets the evaluator create and run evaluation requests, but it can't release, so a compromised PR job can't change a channel. Keep the releasing credential in a protected GitHub environment that only the post-merge release job can use. See [provision evaluator access](/docs/operate/evaluator-access#grant-access).

Store the token as a secret and pass it as the `token` input. The action never writes the token into a file in the workspace. The wrapper copies it into a temporary owner-only config inside the output directory and deletes it when the run ends. Outside GitHub, pass `--token-env NAME` or `--token-file FILE` to the wrapper, or set `evaluatorTokenFile` in the evaluator config if your SDK release supports it.

## Which commit and which parent

**The parent is the channel's current release**, not the PR's merge base. A passing check means the candidate is at least as good as what is released now, which is the comparison that matters for a release decision. If the channel's release changes while a PR is open, the next run compares against the new release. A request against a channel with no release fails with `request.channel_empty`. Publish a baseline release first.

To see what the PR changed, pass `base-commit` (or `--base-commit`). The summary then lists the bundle files that differ from that commit. This list is informational. A comparison against the merge-base bundle isn't offered, because that version was never released and the service binds every comparison to a release on the channel.

**The candidate is the checked-out commit.** On `pull_request` events, `actions/checkout` checks out the test merge commit, and `github.sha` is that commit. The action evaluates `github.sha` by default, which is what the PR would release once merged. To evaluate the PR's head commit instead, check out `${{ github.event.pull_request.head.sha }}` and pass the same value as `commit`. The wrapper rejects a `--commit` that differs from the checked-out `HEAD` and names both commits.

## Reuse, cost and time

The wrapper reuses a request when the bundle content, the channel's release, the evaluator descriptor and the selected cases are all unchanged. A PR commit that only touches files outside the bundle therefore costs a status read, not a run. Reuse needs the persistent output directory and journal of a self-hosted runner, and the wrapper must be able to read the channel with the evaluator token. When it can't, it falls back to one request per commit and records `reuse.status` as `unavailable`. Pass `--no-reuse` to always create a request per commit.

Set a job `timeout-minutes` as a hard limit. Use `max-cost-usd`, `deadline`, `concurrency`, `shard` and `cases` to bound the evaluator's own work. The wrapper passes them to the evaluator's `run` command. The [evaluator CLI reference](/docs/reference/evaluator-cli) describes their behavior.

## Cancellation and cancel-in-progress

With `cancel-in-progress: true`, a new push cancels the running check. GitHub sends `SIGINT`, then `SIGTERM` about 7.5 seconds later, then kills the step 2.5 seconds after that. The wrapper forwards each signal to the evaluator's process group. The evaluator stops starting cases, records the cases it finished, and closes the request. If the evaluator is still running after `cancel-grace` seconds (20 by default), or shortly after a second signal, the wrapper kills the process group so nothing keeps running or holds the journal. The wrapper then prints its summary with `result: cancelled` and exits with 130 or 143.

A cancelled run isn't a verdict. Rerunning the same commit starts a fresh request automatically. If the evaluator had to be killed during execution, the next run reports `execution_unresolved`, because the application's own work may still be running. Either wait until the service expires the abandoned attempt, after which the next run starts a fresh request, or set `abandon-uncertain: true` to interrupt it immediately. Interrupting doesn't stop work outside the evaluator, such as a hosted agent session.

## Forks and untrusted pull requests

- **Secrets aren't available to workflows triggered by forks.** The example skips forked PRs with `if: github.event.pull_request.head.repo.full_name == github.repository`. Run forked changes after a maintainer moves them to a branch in the repository.
- **Don't run forks on self-hosted runners.** On a public repository, a forked PR could run arbitrary code on the runner that holds your evaluator, private cases, journal and provider credentials. GitHub recommends against self-hosted runners for public repositories.
- **Avoid `pull_request_target`.** It runs with secrets in the context of the base branch, so checking out and evaluating the PR's code would hand your credentials to that code.
- **Keep `live` off for code you don't trust.** `live: true` lets the evaluator call models and tools at your expense. A model-free evaluator can still check structure and deterministic cases.

## Release after merge

Copy `workflows/release.yml` to release the candidate after a merge to `main`. The `gate` job runs the same check on `main`. When the bundle, release and evaluator are unchanged since the PR, it reuses the PR's request, so the released candidate is the one that was reviewed. The `release` job runs only when the gate passes. It uses a protected `acclimate-release` environment that holds the releasing token, installs the SDK release, and promotes with the operator CLI:

```sh
acclimate-operator promote --project "$PROJECT" --bundle "$BUNDLE" --channel stable \
  --version "$CANDIDATE" --comparison "$COMPARISON" --expected-revision "$REVISION" --key "release-$GITHUB_SHA"
```

The service checks the releasing principal's permission, the evidence and the expected channel revision. See the [operator CLI](/docs/reference/operator-cli) and [review and release](/docs/guides/review-and-release).

## Use the wrapper in another CI system

Run the wrapper from the checkout. It needs Git and Python 3.8 or later. Python evaluators need Python 3.11 or later.

```sh
sh "$ACCLIMATE_CI/ci.sh" \
  --commit "$CI_EXPECTED_SHA" --bundle-dir agent --no-memory \
  --app "$EVALUATOR_APP" --policy "$EVALUATOR_APP/quality-policy.json" \
  --bundle "$BUNDLE_ID" --channel stable --config "$WORKER_CONFIG" --token-env ACCLIMATE_TOKEN \
  --output-dir "$PRIVATE_PR_STATE" --live --format markdown
```

`--format json` (the default) prints one JSON object. `--format github` prints log lines and workflow annotations, and `--format markdown` prints a summary for a PR comment. `--summary-json FILE`, `--summary-md FILE` and `--github-output FILE` write the same information to files. The [CI starter README](https://github.com/anveld-dev/acclimate/blob/main/examples/ci/README.md) lists every option.

## Read the result

The JSON summary always includes `result` and `exitCode`, including after a configuration error or cancellation. When a phase fails, it also includes `failedPhase`, `diagnosticCode`, `failedChecks`, `hint` and `nextAction`.

| Result | Exit | Meaning |
| --- | --- | --- |
| `pass` | 0 | The policy passed. Associate the commit with `candidateVersionId` and `candidateDigest`. |
| `quality_failed`, `quality_indeterminate` | 2 | The policy failed or couldn't be measured. Review `quality.failedCriteria`, `quality.regressedCases` and `quality.evidenceGaps`. |
| `execution_failed` | 2 | Cases failed to run or grade. Repair the evaluator, then use `--rerun-after`. |
| `execution_unresolved`, `prior_execution_unresolved` | 3 | Earlier work may still be running. Wait for expiry or use `--abandon-uncertain`. |
| `cancelled` | 130 or 143 | The job was cancelled. Rerun it. |
| `preflight_failed`, `request_failed`, `check_failed`, `export_failed`, `configuration_error` | 1 to 3 | Fix the reported diagnostic and rerun. |

Share only the verified `reviewDirectory` under the output directory. Use `--selection` and an installed review mapper to share selected app artifacts.

## Rerun after repairing the evaluator

A changed evaluator descriptor already gets a new request. To deliberately evaluate the same commit again with an unchanged descriptor, for example after an infrastructure failure, pass `--rerun-after` with the previous summary's `handoff` value:

```sh
--rerun-after "$(jq -r '.priorHandoff // .handoff' previous-result.json)"
```

The wrapper accepts one successor per finished request and compares it against the channel's current release. A predecessor can be completed, failed or interrupted. A predecessor that is still `requested` or `running` is interrupted for you when its journal shows that execution never started. Otherwise pass `--abandon-uncertain`. `--retry-after` is the deprecated spelling of `--rerun-after`. Unlike `compare --retry-after`, which keeps the original parent, the wrapper always uses the channel's current release.

## Clean up

The output directory keeps one `requests/` directory per candidate, release and evaluator, and one `reviews/REQUEST_ID` export per request. Upload the review export, then delete it. Delete request directories you no longer need to reuse or recover, for example with `find "$OUTPUT/requests" -mindepth 1 -maxdepth 1 -mtime +30 -exec rm -rf {} +`. Clean the journal only for requests that are finished. See [recover an evaluation](/docs/operate/upgrades-and-recovery#recover-an-evaluation).
