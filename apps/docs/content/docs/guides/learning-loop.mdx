title: Run a learning loop

This guide is for a workspace administrator who wants the learning loop to improve a released bundle. Each round can release a better version to the channel, with no approval step.

See [Learning loop](/docs#learning-loop) for the terms and [What a round does](/docs#what-a-round-does) for the steps. To run the loop from a script, see [Ticket triage](/docs/tutorials/first-learning-round).

## Before you start

- The operator has set the optimizer and started an executor. See [Enable learning](/docs/operate/enable-learning), or [Run your first learning round](/docs/tutorials/first-learning-round) on the local stack.
- The bundle has a release on the channel you want to improve.
- You have an OpenAI-compatible model provider with at least two models, one for the task model and another for the judge model.
- You have examples of the agent's work to import as tasks.

## Connect a model provider

1. In the sidebar, under **Settings**, open **Model provider**.
2. Enter the provider's base URL, an API key and the allowed model IDs, then choose **Save provider**.
3. Wait while the executor verifies each model. A model passes when it answers a chat request and reports token usage.

<Screenshot name="model-provider" alt="The Model provider page with a base URL, a stored API key with a Replace key button, two allowed models, a Provider verified badge and both models verified." />

Any OpenAI-compatible endpoint works, such as `https://api.openai.com/v1` with a provider API key. The measured runs in these docs used CLIProxyAPI with a Codex sign-in. See [Set up a local model proxy](/docs/tutorials/first-learning-round#set-up-a-local-model-proxy).

## Turn on learning

1. Open the bundle's **Learning** tab, then **Settings**.
2. Choose the **Learning channel**, a **Task model** and a different **Judge model**. Use your application's model as the task model, so the loop measures the agent you run. See [How a rollout runs your bundle](/docs#how-a-rollout-runs-your-bundle).
3. Set **Maximum rounds per day**, the daily round limit. It counts rounds over a rolling 24 hours and defaults to 4.
4. Choose **Save learning settings**.

<Screenshot name="learning-setup" alt="The Learning setup panel with the learning channel, task model, judge model, task domain, benchmark name and maximum rounds per day, with Save learning settings at the bottom right." />

## Add tasks

Add tasks on the **Learning** tab's **Tasks** page in any of three ways:

- Under **Import material**, choose a spreadsheet, CSV, JSONL or text file, then choose **Import tasks**.
- Paste text under **Paste conversations**.
- Choose **Write a task**. Give an exact answer for a value that must match. For free text, write one criterion per line and optionally a reference answer.

<Screenshot name="import-material" alt="The Import material panel with a file chooser, a box for pasted conversations and the Import tasks button." />

Import about 50 rows for a first round. Start needs 20 admitted tasks in each split, and some rows are usually set aside. [Improve the bundle with the sample tasks](/docs/tutorials/support-agent#improve-the-bundle-with-the-sample-tasks) has a ready file of 60 rows.

The service assigns each source group to the evolve or held-out split by its hash, so about half the rows land in each. Tasks from the same source row, such as one conversation, share a source group, and so do tasks with the same input, even across imports. A production outcome is its own group. Pasted text and `.txt` files are split on lines that hold only three or more dashes (`---`), and each piece is its own row and source group.

The **Imports** section lists past imports, newest first, with their counts and set-aside rows.

### How a row is graded

| The row has | Graded by | Model call |
| --- | --- | --- |
| `input` and `expected`, where the answer is not a string, or is one line of at most 80 characters | Exact match | None |
| `input` and `expected`, where the answer is longer or has a line break | Criteria the judge model drafts, with the answer kept as the reference | Judge model |
| `input`, `expected` and `grading` set to `exact` or `criteria` | Your choice. Any other value rejects the import. | Judge model for `criteria` |
| Other fields, such as a request, a reply and a rubric | The judge model converts the row, keeping its criteria or drafting them from its answer | Judge model |

A held-out task with drafted criteria waits for a person to confirm it.

## Review and confirm tasks

Each task appears as a card with its source row and a short task ID you can copy. The executor checks every task before it counts. The check admits a task when its reference answer passes, an empty answer fails and the judge model grades it consistently.

<Screenshot name="task-card" alt="The Tasks panel with the split, Needs confirmation, Flagged only, admission and source filters, above an admitted held-out task card showing its source row, input, four criteria, reference answer and the Try task button." />

1. Read the cards and their source rows. Edit any card that is wrong.
2. Check **Needs confirmation** to list the held-out tasks that wait for you, and read their criteria. Choose **Confirm all shown** to confirm every unconfirmed held-out card in the list.
3. Choose **Try task** on a card to run the current version on that task. The card shows the output, the verdict, the reasoning and the gateway log of requests sent to the model provider. A failed trial says why. Trials do not count toward round scores.

A card is pending until it is confirmed and checked, then admitted or set aside. A row can also be set aside at import.

| Reason | Set aside at | What to do |
| --- | --- | --- |
| No usable reference | Import | Add an example answer or criteria to the row and import it again. |
| Not converted | Import | The judge model could not map the row to a task. Edit it and import it again. |
| Row too large | Import | Shorten the row and import it again. |
| Duplicate | Import | The input matches a live task or an earlier row. Nothing, unless you meant a different task. |
| Reference failed | Check | Make the reference answer meet every criterion. |
| Empty answer passed | Check | Tighten the expected answer or criteria so an empty answer fails. |
| Judge unstable | Check | Replace ambiguous criteria with requirements the judge can observe. |
| Check failed | Check | Check that the executor and model provider are up, then choose **Run check again**. |

Editing a set-aside card runs its check again. **Run check again** reruns it without changing the task. **Run all failed checks again** does that for every card whose check failed.

## Start the loop

On the **Overview**, choose **Start**. It needs a verified model provider, 20 admitted tasks in each split and an optimizer on the service. Without an optimizer, **Start** is disabled and the API answers 409 `optimizer-required`. Ask the operator to [set the optimizer model](/docs/operate/enable-learning#set-the-optimizer-model).

From then on, the service releases each adopted version to the channel automatically.

## Follow the rounds

A round either adopts a candidate, one of the five proposed versions, or keeps the current version. A first round often keeps it. After an adoption the loop runs another round. After two rounds in a row that adopt nothing, it waits for new evidence.

On the **Learning** tab's **Overview**:

- The score chart adds a point for each round. Evolve scores explain which candidate was chosen. Held-out scores show regressions.
- Open a round to see its candidates, the bundle changes each proposed and the evolve rollouts behind its score. It links to the task cards it mentions.
- Check **Flagged only** to list tasks with repeated failures, executor errors or inconsistent verdicts. Edit a card and try it again.

People signed in to the console can read, try and edit held-out cards. Edit a held-out card only when the task itself is wrong. Rewriting held-out tasks after reading the agent's failures fits them to the bundle, and the held-out score stops measuring unseen work. Add a new evolve task instead.

### When the loop waits

A running loop with no round to run shows why it waits.

| Waiting reason | Code | What happens next |
| --- | --- | --- |
| No new evidence | `no-new-evidence` | Add, edit or retire evolve tasks. The loop wakes once at least 5, and at least 10 percent of admitted evolve tasks, have changed since the last round. The console shows how many more it needs. |
| Daily round limit reached | `daily-cap` | The next round starts when the rolling 24-hour window has room. The console shows when. |
| Model provider unavailable | `provider-unavailable` | The loop tries again after ten minutes, longer after each further outage. The console shows when. `POST /start` or `POST /resume` runs a round at once. |
| No executor | `no-executor` | Ask the operator to start a connected executor. |
| Models no longer allowed | `models-not-allowed` | Choose two currently allowed models in the learning settings. |

### When a round fails

A failed round shows its cause, the error of the first rollout that failed. After three failed rounds in a row, by default, the loop pauses and the banner shows the cause. Inspect the recent rounds before you start again.

| Cause | What the loop does | What to do |
| --- | --- | --- |
| The model provider was unavailable for every failed rollout of the current version's evaluation | Waits and tries again, without counting the round toward the pause or the daily round limit | Nothing |
| The model provider refused the request, for example for a revoked API key | Counts the round toward the pause | Check the **Model provider** page |
| A sandbox could not start | Counts the round toward the pause | Ask the operator to check the executor |
| No executor matches the round's models and runtime | Fails the round without counting it toward the pause | Check the executor connection and model provider settings |
| The optimizer ran out of context | Pauses | Ask the operator to check the optimizer's context limit |
| A split fell below 20 admitted tasks | Pauses | Bring both splits back to 20, then choose **Start** |

## Pause, stop and roll back

**Pause** lets the active round finish. **Stop learning** cancels the work in progress.

**Automatic revert.** After each adoption, any drop in held-out results raises an alert linked to the round, with a **Roll back this release** button. The revert compares the held-out pass rate, the share of rollouts that pass, not the score with partial credit. It compares the adopted version with the version it replaced and nothing earlier, so a series of smaller drops never trips it. If the pass rate falls by at least 10 percentage points, or by half the previous version's pass rate when that is smaller, and at least two tasks go from passing to failing, the service measures both versions again. A version passing 8% of rollouts reverts at 4% or lower. If the drop holds and the channel still points at the adopted version, the service restores the previous version and blocks the adopted one. The alert says whether it reverted, and the round shows the confirmed scores. Workspace administrators with a verified email address get an email.

**Manual rollback.** While the adopted version is still current, choose **Roll back** on its round and confirm. The channel moves back to the version that round replaced, and the removed version is blocked from future adoption. To allow it again, review its digest and removal note, then choose **Unblock version**.

A rollback does not pause the loop. The next round can start at once from the restored version. The block matches the removed version's exact bytes, so a candidate that differs by one character can be adopted. The optimizer's history does not mark the rollback, and improvement memory keeps the attempt. If a person should look before another round runs, choose **Pause** first, then roll back.

**Restore** on the **Releases** tab also moves a channel back, but does not block the version it replaces. See [Roll back](/docs/guides/release-and-roll-back#roll-back).

## Report production outcomes

When a person corrects an answer in production, report it with `job.expect()` and the request becomes a task. The application needs a machine token with write.

1. The SDK sends the input, the expected answer, the version and digest the job ran with and, if you pass it, the agent's output.
2. The service assigns the outcome to a split and checks it like an imported row. Its `grading` option follows [How a row is graded](#how-a-row-is-graded).
3. An outcome graded by criteria becomes a task once the judge model drafts them. A held-out one then waits for you to confirm it.
4. If drafting fails, the outcome becomes a set-aside exact-match task that you can edit to add criteria.

One outcome does not wake a waiting loop. See [When the loop waits](#when-the-loop-waits).

[Report a correction](/docs/tutorials/support-agent#report-a-correction) is a worked example. The signatures are under Jobs in the [TypeScript SDK](/docs/reference/typescript-sdk#jobs) and [Python SDK](/docs/reference/python-sdk#jobs) references.
