---
title: Upgrade and recover
description: Back up and restore PostgreSQL, verify a service upgrade, and recover an interrupted evaluation.
---

Preserve stored content and release history when changing service releases, and recover evaluator attempts using their original worker state.

## Pin a release

Acclimate uses a shared `major.minor.patch` release version for the service, console and SDK artifacts. Git tags use a leading `v`, such as `v0.1.0`. The matching GHCR image tag is `0.1.0`. Use the release's checkout and read its release notes before changing versions. Set `ACCLIMATE_VERSION` in the Compose environment to the exact published image tag. That pin selects both the service and console images. The default tag is `latest`, which can change between pulls. Keep the original tag and checkout available for recovery.

## Upgrade the deployment

This release uses a fresh schema baseline. An installation using the former migration chain has no in-place upgrade to this baseline. Keep the existing database with its matching service build. Use a separate empty PostgreSQL database to try this release alongside it.

<Steps>
<Step>

### Stop traffic and drain the applications

Pause external clients and worker submissions. Take the public routes out of service and stop both application containers. Leave PostgreSQL running for the dump. In the bundled stack you can stop all three public routes by stopping Caddy first.

```sh
docker compose stop proxy
docker compose stop console service
```

</Step>
<Step>

### Back up and rehearse a restore

[Back up the application database and Keycloak separately](/docs/operate/backup-and-restore). Keep the previous deployment's private configuration available. Restore the application archive to a separate empty database and verify it with the matching service build before upgrading.

</Step>
<Step>

### Apply the release

Use the new checkout and set `ACCLIMATE_VERSION` to its published tag. Validate the Compose configuration and pull the application images. If you build from source, build the new service and console from that checkout instead. Use the same Compose project name and existing volume mapping when switching checkouts. Bring up the upgraded service and console while public traffic is still paused.

From `0.1`, rename `projectId` to `workspaceId` in every `ACCLIMATE_AUTH` grant before starting the service, and plan the SDK and evaluator upgrade for the same window. See [upgrading from 0.1](/docs/reference/versioning#upgrading-from-01).

```sh
docker compose config --quiet
docker compose pull service console
docker compose up -d --no-build --wait service console
```

Keep one Rust process per database. A normal `docker compose down` preserves volumes. The `--volumes` option deletes them.

</Step>
<Step>

### Verify before resuming traffic

Check service and console readiness. Start the proxy with `docker compose up -d --no-build --wait proxy` for [your authenticated read and sign-in checks](/docs/operate/health-and-readiness#verify-access-and-activity) while access is limited to your verification clients. Resume user and worker traffic after those checks pass. If verification fails after a schema change, recover the previous release using its matching verified backup.

</Step>
</Steps>

## Recover an evaluation

Keep the evaluator journal and private artifacts in separate protected backups. When restoring worker state, confirm the original worker has stopped and use one authoritative physical volume. A copied journal has its own kernel locks even at the same path.

| What you observe | Recovery |
| --- | --- |
| Start response lost before callbacks | Retry with the original journal, request, and evaluator config. The runner recovers the retained start and checks current request state. |
| Exact report saved and submission or finish response lost | Retry with the original config and journal. The runner resends saved bytes with the original key. |
| Execution started with no complete sealed report | Inspect the original app and external tasks. Confirm their state before explicitly interrupting and deciding whether to start a new request. |
| A comparison finished with an `execution_uncertain` gap | One arm's `execute` could not confirm its work stopped; the rest of the comparison ran. Its job directory holds `uncertain.json`. Confirm the external task stopped, then clean its quarantined files (the native starter provides `node native.mjs jobs cleanup JOB_ID --confirm-stopped`). |
| Original journal absent, relocated, or from another runtime | Restore supported ownership and the original canonical root, or inspect the external effects and record interruption. |

Use [evaluator status and interrupt](/docs/reference/evaluator-cli) to inspect and record the lifecycle. A stale heartbeat, an interrupted request, or a credential revocation cannot establish that an external job terminated.
