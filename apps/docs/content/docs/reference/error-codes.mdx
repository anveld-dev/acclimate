Every error the SDKs raise on purpose has a stable `code`. The TypeScript and Python SDKs use the same codes, messages, next actions and exit codes. Both test suites check them against this page.

## Error classes

Catch the base class to handle any SDK error, then branch on `code`.

| TypeScript | Python | Codes |
| --- | --- | --- |
| `AcclimateError` | `acclimate.errors.AcclimateError` | Base class for every error below. |
| `AcclimateUsageError` | `acclimate.errors.UsageError` | `usage.invalid_argument`: an SDK function received an invalid argument. The Python class also subclasses `ValueError`. |
| `TransportError` | `acclimate.TransportError` | `transport.unreachable` or `transport.timeout`: the service could not be reached. Only this error means an outage. It carries `serviceUrl` (`service_url` in Python). |
| `ApiError` | `acclimate.ApiError` | The service's error code, such as `not_found` or `base_conflict`, with the HTTP `status`. |
| `DeliveryError` | `acclimate.DeliveryError` | Delivery and cache codes such as `invalid_payload`, `unsafe_cache` and `cache_miss`. |
| `EvaluationError` | `acclimate.evaluation.EvaluationError` | The diagnostic codes in the table below. `diagnostic` holds the safe fields. |
| `DefinitionError` | `acclimate.evaluation.DefinitionError` | `definition.invalid` from `defineEvaluation` or `define_evaluation`. `field` and `reason` name the problem. |
| `OutputValidationError` | `acclimate.evaluation.OutputValidationError` | `output.invalid`: a callback returned a value that is not plain JSON. |
| `AppSetupError` | `SetupError` (internal) | `application.invalid`, `application.import_failed` or `definition.invalid` while loading the application module. |
| `EvaluationUsageError` | `EvaluationUsageError` (internal) | The `usage.*` codes for an invalid command line. |
| `PolicyError`, `AnalysisError` | `PolicyError`, `AnalysisError` | Policy and analysis codes. Both subclass `EvaluationError`. |
| `TaskExecutionError`, `InfrastructureError` | `TaskExecutionError` | Raise these from an execute callback. |

TypeScript exports every class from `@acclimate/sdk/evaluation`. The base classes are also exported from `@acclimate/sdk`.

## Reading a diagnostic

The evaluator CLI prints errors to stderr. On a terminal you get readable text. Otherwise, or with `--json`, you get one JSON line:

```json
{"schemaVersion":1,"command":"compare","error":{"code":"usage.missing_flag","field":"--live","reason":"This evaluator is live. Add --live to authorize model calls.","phase":"configure","executionState":"not_started","nextAction":"fix_command","message":"A required flag is missing. --live: This evaluator is live. Add --live to authorize model calls."}}
```

| Field | Meaning |
| --- | --- |
| `code` | One of the codes below. |
| `message` | The readable explanation. |
| `field`, `reason` | The flag, file, definition field or case that caused the error, and why. |
| `hint` | What to try next. |
| `nextAction` | A machine-readable next step. |
| `phase`, `executionState` | Where the error happened and whether callbacks may have started. |
| `serviceUrl` | The service the evaluator tried to reach, for `service.unavailable`. |
| `cause` | The first line of the underlying exception, such as an `ImportError` in your module. |

Pass `--verbose`, or set `ACCLIMATE_DEBUG=1`, to include the full stack trace and chained cause.

Diagnostics never include config paths, tokens, case inputs or expected values. Callback failures during a run are recorded privately on the evaluator machine. See [callback failures](/docs/reference/evaluator-cli#callback-failures).

## Exit codes and diagnostic codes

CI can route on the exit code alone: `2` means the candidate is worse, while `4` and `5` mean the pipeline needs attention.

### Exit codes

| Exit | Name | Meaning |
| --- | --- | --- |
| 0 | `ok` | The command succeeded. For a policy check, the candidate passed. |
| 1 | `usage` | Fix the command line, config, application module or definition, then rerun. |
| 2 | `gateFailed` | The quality gate failed: the policy verdict is `fail`. |
| 3 | `indeterminate` | The evidence cannot support a verdict yet: the policy is indeterminate, the run has not finished, or exported evidence is missing. |
| 4 | `infrastructure` | The run or the service failed: the request finished as `failed`, the service was unreachable or returned a server error, or a policy receipt was not confirmed. |
| 5 | `recovery` | Recovery is required before retrying: execution may have started, a submission is unconfirmed, the journal needs attention, or the request was interrupted or conflicts with a newer parent. |

### Policy check codes

A verdict lists the checks it ran in `checks`. A `pass or fail` check decides the verdict; an `unknown` check marks missing evidence and makes the verdict indeterminate unless another check failed.

| Check | Result | Meaning |
| --- | --- | --- |
| `policy.minimum_mean_improvement` | pass or fail | The lower confidence bound (or the point estimate under `none`) clears `minimumMeanImprovement`. |
| `policy.non_inferiority` | pass or fail | Audit stage: the lower bound clears minus `nonInferiorityMargin`. |
| `policy.step_non_inferiority` | pass or fail | Connected development step: the lower bound clears minus `stepMargin`. |
| `policy.development_benefit` | pass or fail | Connected development step: a point gain, an attested replay or a cost saving. |
| `policy.maximum_case_regression` | pass or fail | No checked case regressed by more than `maximumCaseRegression`. Absent when the `perCaseChecks` set is empty. |
| `policy.maximum_regressed_cases` | pass or fail | Checked cases that regressed by more than `maximumCaseRegression`, minus those that improved by more, are at most `maximumRegressedCases`. |
| `policy.protected_case_threshold` | pass or fail | Every repetition of a case in `protectedCaseThresholds` meets its threshold. |
| `policy.candidate_threshold` | pass or fail | The candidate mean meets `candidateThreshold`. |
| `policy.maximum_candidate_task_failures` | pass or fail | Candidate task failures over the checked cases are at most `maximumCandidateTaskFailures`. |
| `policy.maximum_candidate_cost` | pass or fail | The candidate cost is at most `cost.maximumCandidateUsd`. |
| `policy.maximum_cost_increase` | pass or fail | The cost increase is at most `cost.maximumIncreaseUsd`. |
| `policy.minimum_cost_savings` | pass or fail | The cost saving is at least `minimumCostSavingsUsd`. |
| `inference.minimum_cases` | unknown | Fewer distinct cases than `inference.minCases`. |
| `inference.minimum_repetitions` | unknown | A case has fewer repetitions than `inference.minRepetitions` (default 2). |
| `inference.zero_variance` | unknown | Every case difference is identical and there is no SD floor. |
| `evidence.incomplete` | unknown | Pairs are missing, or more trials are missing than `maximumMissingPercent` allows. |
| `cost.unknown` | unknown | A cost limit is declared and some cost is unknown. |
| `analysis.nonfinite` | unknown | An intermediate result is not a finite number. |
