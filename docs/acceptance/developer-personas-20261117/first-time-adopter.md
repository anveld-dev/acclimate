# First-time adopter acceptance, 2026-11-17

This is an independent scripted use of an installed release, following the first-time adopter's original needs. It is not usability research. Criteria below were written before executing the journey.

## Acceptance fixed before execution

1. **Find first value:** the README routes an existing-workspace adopter to exact package acquisition, credential ownership and an executable first command without deployment history. The installed offline trial identifies itself as simulated, makes no service mutation and reports parent/candidate behavior.
2. **Consume the content:** an external application uses only installed public SDK APIs; its awaited application callback reads the verified immutable instruction files. A candidate instruction fixes a failing saved task. Inputs survive until execution stops; a private result is retained before cleanup. A deterministic custom loop proves this integration boundary, not native model quality.
3. **Own the evaluator:** adapt the shipped starter with application-owned saved inputs and a separate grader. Generate its public descriptor; doctor, request, run, check, export and independently verify real paired evidence against isolated Rust/PostgreSQL. No checkout-private SDK import or CLI allowlist edit is permitted.
4. **Know authority first:** before request creation the guide must identify the service operator as evaluator provisioner, distinguish content-read from project evaluator read/write, and identify private persistent journals. Exercise preflight with evaluator access; a read-only credential must not pass evaluator preflight.
5. **Choose a relevant evaluation:** generic instruction adoption must not silently select the payment simulator. Installed-app descriptor use is exercised here; actual console default and public download behavior require browser evidence. Do not claim a console visit from this script.
6. **Obtain a coherent release:** install the operator-provided exact SDK artifact and starter archive after checking release checksums; record release/source/runtime hashes. Acquisition remains operator managed.

## Scenario

The adopter owns a small support-routing application. Its baseline instructions send every issue to normal support. Two private saved tasks cover a compromised-account issue and an ordinary issue. Its candidate instructions route the former to security. The application reads staged instructions after an asynchronous boundary and produces a queue label; its independent grader compares that label with a private expected answer. No model/provider call or promotion is authorized.

## Execution and disposition

**Accepted for the model-free first-time adopter path, including the continuous custom-app console handoff.** I used the operator-supplied release archive in external application directories against disposable real PostgreSQL and the existing Rust binary. The first run was headless; a second owned run used actual Chromium and the existing production console output. Neither used a production workspace, called a model, or promoted a channel.

The [original headless machine-readable report](first-time-adopter.json) preserves 24 passing assertions and its original request/comparison/version IDs. The [continuous console report](first-time-adopter-console.json) records another 29 passing assertions, its distinct browser-created request, exact descriptor/download hashes, scalar results, CLI exit codes and installed-release provenance. The reports record runtime versions and release/binary hashes; they exclude credentials, private paths, expected-answer files, journal contents and raw application outputs. Original private captures remain under ignored `artifacts/dx-personas-20261117/first-adopter/`; the continuous app and its private captures live outside the checkout under owner-only `/private/tmp` storage. Both fixtures shut down and remove their databases while preserving private consumer records.

/Users/benjaminarmstrong/.pyenv/versions/3.11.7/bin/python3.11 scripts/acceptance/dx_personas/first_adopter.py

The script does not build the service or release. It records the existing service binary hash but does not attest a binary-to-source build. Each run uses a fresh private app, service and database; it does not read ambient database/model credentials.

Reproduce the separate continuous browser journey with the already installed Playwright environment and existing production console output:

```sh
.venv-bdd/bin/python scripts/acceptance/dx_personas/console_custom_app.py
```

This second command stages the consumer outside the worktree, creates a new browser-owned request, executes only that downloaded request through the installed public evaluator CLI, and writes its own report. Its browser trace remains private. The two commands represent two distinct requests; neither reruns the other's callbacks.
