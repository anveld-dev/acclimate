## Security requirements versus avoidable UI

Keep visible at decision time: verified subject + issuer before member change, explicit identity confirmation, current/new role, last-admin constraint, exact destructive target, secret shown once and privately stored, original issuance/revocation/replacement recovery, private-directory constraints, separate reporting credential and reporting does not prove model consumption. These are product contracts and recovery affordances, not visual clutter. Do not bury permission-loss/unknown-outcome feedback in hover tips.

Avoid duplication and nested ceremony: the SDK repeats all five variables nearly verbatim when its environment disclosure opens. Keep one canonical compact definition list with actual URL/copy and required-variable meanings; let the disclosure add only private-directory requirements and advanced explanation. Preserve a brief always-visible reminder that credentials/private paths are required. Connections' “About connections and workspace details” combines concept help with IDs; a quiet identity disclosure and one short description would scan better, but this is lower priority than the actual duplicated SDK content.

## Bounded shared-library recommendations

1. Use the existing shadcn Dialog, Disclosure, NativeSelect, Input/Label and CopyButton. Share row spacing, heading/action hierarchy, status treatment and field help—not a new generic wizard, permission system or universal menu. A popover for a short action group, native select for a real finite choice and dialog for a commit/review flow remain different behaviors.
2. Make destructive confirmation identify the selected app + bundle/channel and, for a credential, exact ID/kind before Revoke. The current shared dialog has consequence copy but loses the target on opening. This is a small missing piece with direct review value.
3. Put Workspace ID format in persistent associated help. The `title` contains the format while visible help only says links/automatic filling. Native hover and browser validation are neither reliable mobile help nor a cohesive error presentation. Keep native validation; supplement with visible concise format copy and inline field association.
4. Give disabled actions a nearby reason when the cause is not obvious. Credential creation has several independent blockers (rights, busy, revoked connection, recovery); current global “disabled for this console” message is too broad. Reuse one local status pattern without adding tooltip-only explanations.
5. Track action-specific pending labels for credential issue/result-check/replacement and history loading. The single `busy`/`pending` boolean safely blocks duplicates, but several disabled buttons offer no local progress cue, and member pending can display “Updating…” during unrelated refresh. Retain retry and operation-key semantics.
6. Preserve selectable source text when copy fails; no toast-only feedback. Share modal error placement so server/validation/unknown-result feedback stays inside the relevant modal, with alert vs status chosen by urgency. Admin dialogs already mostly do this; align editor modal gaps with the same pattern.
7. Audit close semantics before changing density: credential X/Escape/outside close currently discards the one-time visible secret, despite the prominent “I saved it” action. This may be intentional, but the visual concept must show the real choice and recovery limitation; any stronger acknowledgement policy needs product agreement rather than an invented confirmation chain.
8. Group label + control + helper inside each connection field. Currently New connection puts each as a separate `DialogContent` grid child, while Members groups label/control with `space-y-2`. Shared field grouping should keep about 8px inside a field and 16px between fields; outer modal spacing should separate header/body/footer. This is a concrete composition gap, not grounds for a schema-driven form system.

Peer debate before boards: navigation agrees sparse lists should remain sparse and proposes giving mobile PageTitle descriptions their own full-width row instead of squeezing them between Menu/action. Editor and systems agree shared spacing/status/field grammar should preserve distinct primitives: small menus for commands, popovers for short action groups, native selects for finite values, disclosures for secondary content, dialogs for review/commit. Release agrees active recovery warnings remain visible, while each recovery flow retains its own operation/permission rules. Systems identified the concrete connection field-grouping inconsistency above; adopted.

Accessibility agrees ID syntax should be visible before native validation and secret-close is a current product contract, not permission to invent another acknowledgement flow. It flags that controlled Connections/Members dialogs open through ordinary buttons rather than `DialogTrigger`, with no explicit return target; test focus return and add a stable trigger/main fallback if needed. Shell creation already supplies an explicit return path and is a useful local precedent.

Debated actual renders with navigation, editor, release, accessibility and systems. Consensus is one existing Dialog family: compact utility forms with close label/control grouping; a bounded approximately 512px decision variant with full identity wrapping, safe focus gutter, scroll and footer behavior; stacked actions when narrow; explicit target/evidence/recovery wording. Contextual sizing is preferable to forcing every revoke, member review and one-time secret into an identical width. Keep real menus, native selects, disclosures and routes. No permanent inspector, new wizard, tooltip-only critical fact or drawer migration.
