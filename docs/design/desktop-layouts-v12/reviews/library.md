# Overall information architecture review

## Baseline audit

Viewed actual v11 1440px Content, 1920px dirty draft and 1024px coarse desktop shell; read current bundle-scope header/channel navigation and shell/layout source.

The baseline spends about 100px on two horizontal scopes before the workbench: workspace/global destinations, then bundle/channel/task destinations. This is compact in area but makes scope a horizontal reading exercise. At wide desktop workspace identity is far from workspace destinations; bundle identity/channel and bundle task tabs are also spread apart. At 1024px workspace labeling/icons are reduced and long identity depends on truncation/tooltips. A materially different navigation could improve scope association and consistent destinations, provided it earns any persistent width it consumes.

The workbench has useful scope boundaries already: draft-wide state/actions above selected-file heading/actions, then persistent file selection beside source. Review has no file navigator because its primary task is evidence. Library/admin/forms use narrower reading widths. A holistic proposal should preserve these task-dependent widths instead of giving every page the same three columns.

Assess all six alternatives against real movement: workspace switching, bundle/channel switching, Content→Changes→saved generation→evidence→release, file selection and return from hidden utilities. No fake bundle switcher, dashboard/command search or filesystem context is available. Dirty navigation, exact path/ID context, account/menu dialogs and resize/native-zoom focus behavior are part of the architecture, not optional polish.

## Independent ranking before peer debate

Viewed actual A–F pixels before receiving peer rankings. Order by architectural promise, with fictional controls excluded: **D → C → B → A → actual baseline → E → F**. This is an exploration ranking, not approval to ship any literal sheet. Illustrated source dimensions are not measured evidence.

1. **D, one contextual rail:** strongest scope association and most promising use of space. A 256px rail replaces both global chrome and the separate 216px file rail, rather than adding a third column. Workspace→bundle/channel→task→files becomes one visible hierarchy, while draft-wide/file-wide commands remain in the main pane. Requires refinement: static real bundle identity, explicit return path, actual import/history/details, global footer accessible with long file inventories, and frequent file access outside the navigation sheet at narrow/native zoom. Literal bundle dropdown, fabricated entry commands and evidence inset are rejected.
2. **C, labelled workspace sidebar:** clearest realizable separation of workspace navigation from bundle/file work. Direct labels and workspace chooser improve orientation over distant topbar groups. Costs a second persistent rail and roughly 180px of workbench width; long-source/evidence layouts need honest proof. Stronger than B for understandable destinations.
3. **B, narrow global rail:** potentially gains vertical source room with less width cost than C, while workspace/bundle share the scopebar. It trades explicit workspace destination labels for recognition/tooltip work; the actual image is wider than the claimed 64px rail. Do not copy its fabricated Workspace destination or metric box.
4. **A, two bands:** modest improvement by moving rare workspace creation into a real workspace menu. Keeps direct workspace destinations and frequent file selection, but largely leaves the baseline's remote scope associations intact.
5. **Baseline:** actual known functional scopes and usable persistent explorer. Its compact bands are a valid fallback, but past acceptance is not evidence that alternative navigation cannot improve orientation.
6. **E, combined command bar:** keeps current scope readable only by hiding workspace destinations. In saved-review detail, reaching another bundle becomes menu work while the persistent back action leads only to Changes. Long identities fall back to two rows anyway. Reject invented workspace settings/permissions entries.
7. **F, file finder:** removes the most frequent navigator to preserve low-frequency global links. Every file switch incurs opening/selecting and the overlay covers source; extra width alone does not justify that task cost.

## Peer disagreement and next evidence

All five peers debated the ranking. Editor, review and interaction ranked baseline first; skeptic ranked baseline/A/B before D; visual ranked C first. I retain D-first **exploration** preference, while conceding its most important cost: files begin after workspace, bundle/channel and view groups. Long identities and many paths may consume the saved height. Peers conceded that D replaces an explorer instead of adding another rail, and that review at 1440px could retain nearly all the currently bounded 1200px evidence width. We disagree about likely task benefit, not whether literal mock controls are valid.

Recommend an isolated reversible actual D geometry experiment against baseline; C can serve as a cleaner hierarchy control. Do not adopt D from its image. Required falsifier: matched 1440/1024 short-height long workspace/bundle/channel plus 24 real paths, selecting files 3/20, search/type/Add, Members and Back to changes; actual review with no Files and paired facts; native 200% with current named inline Files access outside the global navigation sheet. Preserve one document flow rather than inventing nested rail scrolling or fixed footer competition. If file selection requires repeated sheet opens or scope consumes its working area, baseline wins.

## Final independent verdict after actual experiment

**Retain the actual baseline.** My D-first exploration preference changed after inspecting the matched baseline/C/D source and review captures at 1440×900, 1440×700 and 1024px coarse, then the corrected D workspace-name sensitivity and narrow/native-zoom proof. This is a result of testing the strongest competing hypothesis, not automatic approval of the prior design.

D's promise was real: the tested 1440×900 source area increases about 9.3%, and review/diff facts remain readable at nearly baseline width. But its frequent file task loses the trade. I challenged an unfair expanded-workspace-name cost; restoring the existing one-line identity plus existing tooltip improves Files from 108px to 160px. It still cannot fit its measured 132px controls plus 141px first three rows (273px total), with no fully visible initial file row. At 700px height the corrected file region remains zero and real search/type clicks fail. This disproves this fixed-scope/fixed-footer D variant's suitability; it does not prove every unified rail impossible.

C provides clearer labelled workspace orientation and keeps actual file/evidence tasks usable, but source width falls from 1182px to 1002px at 1440px. Its short/coarse case wraps source heavily. Measured source height depends on the prototype's utility-footer reservation, so the observed 7px gain is not an architectural ceiling; even allowing the 49px earlier first line, I do not find enough task gain to justify the extra permanent rail. C remains the strongest alternative to revisit if workspace navigation frequency warrants it, rather than an earned shipping change now. A is marginal cleanup; B, E and F retain their unproven recognition, hidden-destination or repeated-file-opening costs.

The corrected common Add/import/history/details checks pass; their earlier shared locator failures are harness artifacts, not baseline/C product regressions. The clean narrow-contract report passes six cases across 390px and actual Chrome 200% for baseline/C/D: Files stays outside the global sheet and selection returns focus. Personally viewed native D and narrow baseline captures plus the actual import Dialog.

These are explicitly CSS/style-variable geometry overlays, with no node moves or shipping qualification; DOM order, a future structural sidebar implementation and broader app behavior are not proven by them.
