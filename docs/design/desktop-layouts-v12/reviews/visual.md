# Visual systems review

Baseline audit: the current global → scope → task hierarchy is compact and understandable, while the editor gives several horizontal bands similar emphasis. Long workspace and bundle identities put pressure on navigation. A bolder composition should be judged by useful source height versus lost width, durable identity, cross-page reading surfaces and breakpoint/focus costs, not novelty or empty-space filling.

I inspected current Mira configuration, shared shell/scope/task styles and workspace chrome, plus actual desktop11 editor, populated library and proposal.

**Independent composition ranking, recorded before peer debate: C > baseline > A > E > B > D > F.** This ranks plausible source-faithful composition, not the invented actions or unmeasured metric insets.

1. **C:** The labelled global sidebar provides the clearest orthogonal global → bundle → task hierarchy and can recover a global-header row. It spends source width, but bounded 768/1024px forms and 1200px evidence can remain largely intact on wide desktop. Worth a measured challenge, with a normal navigation-sheet fallback when width becomes scarce.
2. **Baseline:** Proven compact horizontal scope and maximal editor width. It remains the fallback until a challenger earns the tradeoff across real routes and long identities.
3. **A:** Calm and familiar, but essentially the baseline with a quieter workspace group. Moving creation into a custom chooser does not establish meaningful work-area gain.
4. **E:** Potential height gain without width loss, but the bar is crowded even with ordinary identities and hides global navigation inside a workspace menu. Long bundle/channel values may erase its gain.
5. **B:** Less width than C only if labels disappear. The actual image is wider than its claimed icon rail; labelled Connections cannot fit a 64px column. Icon-only navigation adds discovery costs.
6. **D:** Attractive nominal space tradeoff, but workspace/bundle/channel/views precede frequent files and compete for one vertical rail. Long identities and real file volume can force scrolling or push file switching into the global sheet.
7. **F:** Extra source width solves little while removing persistent file context and charging an open/select cycle for repeated navigation.

After debate with all five peers, C remains my clearest hierarchy challenger. I corrected the claim that a sidebar necessarily narrows the 1440px evidence view: 1440 − 180 − 40 leaves 1220px, enough for the current 1200px bound. Editor width remains its real cost.

The library reviewer's D argument changed my experiment recommendation: replacing a 216px file rail with a 256px unified rail costs much less width than adding C's global rail, with a credible larger height gain. D deserves a reversible actual prototype despite my low initial rank; a cheap C geometry control would make the comparison stronger. Adoption requires full long identities/Back/Refresh/global actions/utilities, 24/128 files and short desktop heights without new scrolling or poor file lookup. At 1024px/native 200%, Files must remain directly available outside the global navigation sheet. Incomplete paired evidence, expanded diff and decision dialogs must retain their facts. No mock metric or invented entry/admin capability counts as proof.

**Final decision: retain the production baseline `0f5464d8…`; reject C and the tested D variant for shipping.** My initial C-first preference changed after inspecting actual source, incomplete evidence, expanded full diffs, short-height/coarse states and the final sensitivity captures. C makes global hierarchy clearer and preserves the bounded evidence view, but the editor loses 180px of width. At 1440×900 the measured source changes from 1182×648 to 1002×655. The 7px height gain reflects this prototype's footer-sizing policy, not an architectural ceiling; its source begins 49px earlier. Even allowing that potential room, the observed benefit does not justify the narrower core workspace.

D produces a real larger source surface, but its frequent-file task loses. The corrected fixed-position measurements show a 108px file region at 900px height, versus 132px for its controls alone. Preserving the existing full-name tooltip while shortening the workspace to one line raises that region to 160px, still with no fully visible file row. At 700px height it remains 0px and native Search/type clicks fail. This is a rejection of the tested allocation, not a universal ban on a contextual rail. [Actual sensitivity pixels](../../../../artifacts/desktop12-experiment/final-supplement/d-1440x900-workspace-name-sensitivity-initial.png) show the tradeoff more clearly than the concept sheet.

I inspected the corrected [narrow contract proof](../../../../artifacts/desktop12-experiment/narrow-contract/summary.json) and its 390px/native Chrome 200% captures: all six baseline/C/D checks preserve inline Files outside the global sheet and return selection focus. These prototypes use deliberate CSS/style-variable injection, no DOM moves, and therefore do not qualify shipping accessibility/source order. Corrected native-hit/menu/utility evidence supersedes common harness errors; I do not call those errors product regressions. The [main measurements](../../../../artifacts/desktop12-experiment/accepted/summary.json), fixed-visibility and sensitivity reports retain the same production fingerprint and unchanged persisted state. No further image round or application change is warranted. I made no application edits, builds or test runs.
