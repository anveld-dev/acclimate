# Independent acceptance review

2026-11-14. Review only of `docs/architecture/production-only/plan.md` and current fixtures, CI, identity and Rust tests. No tests, services, browsers, models, external providers, Docker or credentials were used. The direction is viable; resolve the following before implementation.

## Decisions the plan must make

1. **Choose grant-backed project registration now.** `World.fresh_scenario()` creates a new grant-only project for every variant; `Harness`, `service-e2e.ts`, full-roadmap and container qualification also rely on this setup. Both `main.rs` and `GET /v1/projects` currently call `backfill_projects()`. Removing request-time writes is sound, but removing startup registration too silently changes machine bootstrap and breaks fixtures/content foreign keys. Compatibility review recommends retaining explicit, idempotent startup registration of configured grant project rows, with zero human memberships. I agree this is the smallest preservation contract. State it, test that GET is read-only and that registration grants no human/operator authority. If choosing removal instead, explicitly migrate every fixture and document how a new machine application obtains an existing project; do not conceal this API change in fixture SQL.
2. **Choose one migration contract.** Prefer existing singleton-lock-protected startup migration for this single Rust process. A new `migrate`/`serve` CLI adds dirty/pending/version/preflight/rollout branches and fixture launch changes without establishing needed acceptance by itself. If retained, the plan must enumerate and test those branches. Either choice needs an upgrade test, not just fresh databases.
3. **Define actual console startup and proxy boundaries.** Current `configured()` validates during identity requests, while `npm start` directly launches Nitro output and dev loads dotenv. Unit validation cannot prove failure before listen. Specify the preflight entrypoint used by both built and dev commands; test those exact commands with missing, malformed and legacy configuration, no runtime secrets during build, and no successful listener. The TLS fixture must prove how the real adapter reconstructs `request.url.origin` through the trusted reverse proxy; test forged forwarded host/protocol and direct-listener access against that chosen boundary. Production must not gain a fake-auth switch to solve this.

## One shared fixture, distinct claims

The proposed test-owned HTTPS issuer is necessary. Current `World.sign_in()` directly asserts issuer/subject to Rust, `BrowserFixture` uses HTTP and injects cookies, and `identity_consumer.mjs` injects provider claims. None proves successful default `openid-client` discovery/token/signature verification. Keep focused handler/authority tests, accurately labeled; they need not each run a browser.

Build a reusable test fixture lifecycle/configuration interface once and let BDD, productization browser/recovery and built-console startup checks consume it. Separate lightweight Rust/service configuration from optional browser/issuer startup. Every machine/Rust test needs explicit production security configuration, but does not need discovery or a browser if it never logs in. Do not build separate issuers for each lane or a second application protocol implementation.

The shared fixture needs generated test-only CA/signing material, HTTPS discovery/authorization/token/JWKS, exact issuer/audience/redirect/client binding, one-use expiring codes and S256 verification. Trust the CA in fixture Node children; document browser-specific trust. Keep installed default client behavior, Secure cookies and the real `/auth/login` → callback → Rust session → protected-page flow. No app HTTP allowance, global TLS disabling, fake-claims environment, magic cookie setup or test route may count as this evidence. Actor-specific contexts preserve state for admin/editor/viewer/uninvited users. Existing-cookie downgrade/removal checks must not relogin and hide authorization caching.

Use focused malformed-response tests for signature, issuer, audience, nonce, state, PKCE/code reuse, expiry and provider failures; retain deterministic clocks for unit expiry tests. Full browser evidence must include actual redirect/callback, protected page, logout, same-person renewal and switching accounts invalidating the replaced session. Generic upstream logout 401/404 does not establish revocation: test wrong transport credential/wrong upstream path and retain the cookie unless the response explicitly proves the session invalid or revocation succeeded.

## Evidence gates and scope

Default CI can prove production code paths with disposable PG and the test-owned HTTPS issuer. Reports must say exactly that. Keep separate explicit external-provider OIDC/HTTPS, executed container, backup/restore and native/model gates. `external.py --gate oidc` must continue to require configured real external resources; a fixture run cannot mark it passed. Current `container_check.py` tests only Rust/PostgreSQL, so update its intended contract for both processes before calling it whole-deployment qualification. Docker-unavailable means blocked/not run; manifest validation is a separate result. Preserve Luna-only opt-in model policy and model-free default execution.

No additional identity service, fleet, second Rust verifier, second issuer harness, broad test-framework rewrite or provider credential is needed to meet these gates. The implementation can be locally complete while external deployment evidence remains explicitly outstanding.
