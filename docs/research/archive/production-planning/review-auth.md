# Independent authentication review

Review only, 2026-11-14, against `docs/architecture/production-only/plan.md`, the planning inputs and the current Rust/console/SDK source. No application edits, runtime/database actions, tests, browser work, provider calls or secret reads.

The proposed authority split is appropriate. The console already uses the installed OIDC client for authorization-code exchange with PKCE, state, nonce and an expected ID token (`apps/console/src/server/identity.ts:26–51`), then checks exact issuer/subject (`:141–143`). Rust deliberately trusts the login credential's verified identity assertion. A second Rust OIDC verifier would introduce another relying-party configuration and token-validation implementation without removing that console trust. Keep the proposed boundary and document that compromise of the login authority can impersonate users. Explicitly enforce asserted issuer equality to Rust's configured issuer in `workspaces::login`; current code checks only nonempty/bounded strings (`src/workspaces.rs:229`).

## Corrections to make before implementation

1. **Logout needs a precise revocation result, not generic HTTP status inference.** The plan correctly says not to clear a cookie before revocation is known, but the existing implementation clears it on *any* upstream 401 or 404 (`identity.ts:195–198`). Counterexample: the console has a mismatched transport credential; Rust receives a valid session, then `workspaces::machine` rejects the bearer with 401 (`src/workspaces.rs:112–133`). The console erases the cookie although that session remains live. A wrong upstream path can similarly return 404 without revoking anything. Require a committed successful revocation or a narrowly identified invalid/expired/revoked-session outcome from the intended authenticated service endpoint. Retain the cookie for credential errors, arbitrary 404s, transport failures and ambiguous outcomes. This requires a small response contract and tests, not provider logout or a refresh-token store.

2. **Define adoption retries independently of present membership.** “Same operator is a semantic no-op” and “already-owned project is refused” otherwise overlap. Counterexample: operator A adopts, adds admin B, then B removes or demotes A; A retries the original request after an uncertain response. An implementation using `INSERT ... ON CONFLICT UPDATE role='admin'` restores A's privilege. Record one immutable adoption per project, including original verified actor, reason and result. After checking the current valid session and current operator allowlist, take the existing membership-writer lock, verify the project and look up that record. The same recorded operator receives the original adoption result without changing any current membership or original audit/reason; a different operator conflicts. Only absence of a record permits testing zero memberships and atomically inserting the membership and adoption record. A response must not imply the actor still has admin access merely because the historical adoption succeeded. A fresh reason on a retry must never rewrite the original reason; either ignore it for this semantic no-op or explicitly reject mismatch.

   Reuse the exact `membership:{project}` advisory-lock namespace and lock ordering from `src/workspaces.rs:395–404`, then recheck the session inside the transaction as existing authorization helpers do (`src/auth.rs:341–385`). A separate adoption-only lock does not serialize with membership writers. Keep the route outside `/v1/projects/{project}` because middleware rejects nonmembers before handlers (`src/auth.rs:313–327`). Do not generalize the zero-membership precondition to “no admin”: a project with existing viewers/editors is intentionally ineligible and needs separately authorized recovery. A unique project adoption constraint is a useful final guard; no invitation or global-administrator system is needed.

3. **Make the HTTPS/proxy boundary an explicit supported contract.** A TLS recipe and HTTPS origin string alone do not describe it. The handler compares `new URL(request.url).origin` to `CONSOLE_ORIGIN` before login, callback and logout (`identity.ts:116–119`), and logout separately checks Origin (`:179`). Counterexample: TLS terminates at the proxy but Node reconstructs an internal HTTP URL, so every callback fails. Trusting client-supplied forwarding headers to fix this can instead let callers choose the apparent origin. Specify proxy-owned replacement of forwarding/host headers, exact supported URL reconstruction, and prevention of untrusted direct access to the console's HTTP listener. Protect console-to-Rust HTTP on an explicit loopback/private boundary or use TLS. Prove login/callback/logout and rejection of spoofed forwarding/origin claims through the built topology. The richer boundary is already in `auth-input.md`; promote it into the actionable plan rather than treating Secure cookies as sufficient evidence.

4. **Describe the security cutover barrier around one-time session revocation.** Migration 0013 can revoke rows present when it runs; it cannot itself prevent an old authority from minting more sessions afterward. Specify stopping old browser authority/service traffic, reconciling pending machine-owned writes under their original principal, applying the migration under the existing singleton lock, and starting only the new credential/issuer-validating runtime before reopening browser traffic. Do not present rollback to the old permissive runtime as a safe rollback after reopening. An isolated 0012-to-0013 upgrade fixture must show old sessions revoked while users, memberships and business records remain unchanged; fresh-schema startup alone cannot demonstrate this. No session-provenance subsystem or business-data rewrite is required.

5. **Carry the actor-class rule through global endpoints while preserving rotation.** Current `auth::actor` permits machine bearer plus session to become a human actor (`src/auth.rs:134–173`); `workspaces::machine` also accepts machine bearer on session endpoints. Tightening project actor checks alone leaves global `/v1/auth/session`, workspace create/adoption and discovery paths inconsistent. Define the classes centrally: console transport plus current session for browser data/management; machine grants without session for their existing rights; scoped integration credentials for their existing delivery contracts; login authority only for session creation. The session-creation call may carry a previous session secret as an untrusted rotation hint (`identity.ts:148–149`, `src/auth.rs:263–268`); rejecting every non-console bearer carrying a session would break successful account switching. The prior secret does not authorize login, need not still be valid, and its matching old session must be revoked atomically with issuance regardless of old user ID (`src/workspaces.rs:238` currently restricts revocation to the newly authenticated user). All other credential-class confusion must fail before data authorization.

## Scope and review decisions

- Keep optional SDK `sessionToken` source compatibility (`packages/sdk/src/client.ts:61–70`) and token-only machine SDK calls. Require the console's server-only helper to attach a session and dedicated transport unconditionally, including direct fetch and durable-operation calls. A public SDK field is not a reason to retain anonymous console fallback, and removing it is unnecessary scope.
- Use an actual Node runtime preflight before the built/dev server listens. Current console validation is lazy and only reached from auth routes (`identity.ts:55`, `:115`); `apps/console/src/start.ts` installs CSRF middleware, not startup validation. Do not implement this as unconditional module-import secret validation that also runs during secret-free `vite build`. Static configuration can fail closed before listen without requiring a live provider fetch on every readiness probe.
- Keep the eight-hour session policy, transactional session/membership checks, exact operator pairs, existing grant-backed machine rights and scoped integration credential semantics. Avoid user-equals-operator shortcuts and a global mandatory-human middleware across all `/v1` requests. Existing machine integration administration remains legitimate (`src/integrations.rs:54–65`).
- Prefer the existing singleton-lock-protected startup migration unless a separate migration command has a concrete operational need. Auth cutover requires coordinated ordering whichever command owns migration; splitting commands alone provides no additional identity guarantee.

These objections were shared with the acceptance, compatibility and scope reviewers. They agreed on the single OIDC verifier, preserved SDK transport field, immutable adoption retry semantics, runtime preflight and actual HTTPS/proxy evidence. The compatibility reviewer clarified that historical adoption success must never reinstall current membership; the acceptance reviewer requested an upgrade fixture and real built proxy flow. Root owns the final plan resolution.
