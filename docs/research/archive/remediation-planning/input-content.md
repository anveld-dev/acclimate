# Input/content remediation draft

**Planning input. The [reviewed plan](../../../architecture/productization/remediation/plan.md) and [review resolutions](../../../architecture/productization/remediation/review.md) take precedence where choices differ.**

Keep this small: two validation layers, one durable bundle setting, and a bounded proposal-edit format. The audit is right about the gaps; the existing draft snapshots, version digests, release transactions and provider-attempt fencing are useful foundations.

## Contract choices

- **Generic validity stays generic.** Keep schema v1, existing path/collision/byte limits, all three kinds, arbitrary skill contents and multiple instruction files. Do not put native packaging restrictions into `validatePayload` / `validate_payload` or `contracts/bundle.schema.json`.
- **Compatibility belongs to the bundle.** Add `bundles.compatibility_target` (`generic|codex|claude|pi|cursor`, default `generic`) and monotonically increasing `compatibility_revision` (default 1). Return these as `compatibilityTarget` / `compatibilityRevision` in Bundle DTOs. This is a small fixed enum, not a plugin/profile registry. A release request cannot supply a different target to bypass the stored setting.
- New setup accepts an optional target, with omission meaning generic for existing API clients. The console makes this choice visible before import/setup and keeps the stored target visible in drafts, proposals and final release review. Generic says that native preparation has not been established. Connections/recipe selection does not silently change bundle policy; integrations currently have no plugin identity.
- Add one idempotent `POST /bundles/{id}/compatibility` command with `{target, expectedCompatibilityRevision}`, requiring both existing `write` and `promote` capabilities. Lock the bundle, CAS the revision, and validate every currently published channel against the requested target before committing. Reject tightening with channel/path diagnostics if any release is incompatible; repair/publish that channel under generic first. Changing to generic is an explicit, reviewable policy change, never an implicit fallback. Return unchanged settings without advancing revision for an identical target.
- Common native rules are **zero or one instruction**, skill paths `skills/<name>/<support-path>`, names matching `[A-Za-z0-9_-]{1,64}`, no case-folded package-name collision, exact `skills/<name>/SKILL.md`, matching frontmatter `name`, and a nonempty inline `description`. Cursor additionally keeps its current `[a-z0-9-]{1,64}` name rule. Do not impose the draft server's narrower lowercase-kebab rule on other plugins. Pin the existing supported frontmatter grammar in fixtures; adding a general YAML parser is outside this fix.
- Compatibility reports use stable codes plus path/package and short human explanation, never file contents. Generic validity and selected-plugin compatibility are displayed separately. Passing compatibility is a preparation check, not behavioral evaluation or provider qualification. Memory approval remains an independent delivery choice.

## Reuse and enforcement

1. Add a filesystem-free TS compatibility validator under `packages/sdk/src/`, publicly exported from `index.ts`; it takes a generically valid payload and target and returns structured issues. `internal/native-files.ts` and each native plugin call it using their actual target; remove Cursor's duplicate loop. Validate original content before staging/approved-memory filtering. Keep native filesystem and platform checks local to staging.
2. Mirror only that pure contract in `src/compatibility.rs`, using shared good/bad JSON fixtures under `contracts/fixtures/compatibility/` for TS and Rust parity. No cross-language runtime, policy interpreter or universal validation framework. Keep generic validators separate.
3. Console `server/setup.ts`, `server/drafts.ts`, import preview, and proposal/release preflight use the same SDK checker against the selected/stored target; remove the draft server's handwritten metadata parser. Initial setup/import checks the chosen target; existing-bundle import checks the whole merged payload against its stored target before applying. Surface exact missing manifest/name/description/instruction-count problems.
4. Service enforcement is authoritative: native-target setup, version creation (`src/bundles.rs`), draft create/save/setup (`src/drafts.rs`), proposal acceptance/result (`src/improvement.rs`), and release/restore (`src/channels.rs::promote_in_tx`) validate the **actual immutable payload** against the stored target. Setup checks its requested initial policy within the same transaction. Release checks apply equally to comparison-backed and explicit unevaluated releases, draft publication and rollback; fixture scores cannot override them. Reads of older incompatible versions remain available.
5. All policy-sensitive mutations acquire the bundle row lock before draft/channel locks, then read current policy and validate. The policy command uses the same order. Proposal acceptance checks parent compatibility. A worker reads target/revision before its provider call and rechecks them under that lock before inserting a candidate: a changed revision fails the attempt with a safe `compatibility_changed` explanation and no candidate, even if the target changed away and back. The per-attempt snapshot can stay in worker memory; restarted attempts reread durable policy. No client target field is needed on proposal requests. Existing attempt fencing remains intact.
6. Console commands may send optional `expectedCompatibilityRevision` for stale-review feedback; it cannot override active policy. Require it in the new console's existing-bundle mutations and return a distinct conflict when review policy changed. Initial setup has no prior revision. Existing SDK requests without it still validate against current policy. Authorized idempotent replay/result lookup happens before these fresh-write checks, including after a subsequent policy change.

## Small editor/review fixes

- In `draft-workspace.tsx`, choose `new-skill`, then `new-skill-2`, etc. from case-folded occupied package roots **and all proposed manifest/support paths**, regardless of existing kind. Generate the manifest's path, name and title from that one name. Use a small pure helper, and reject a rename collision before applying it. Repeated adds and rename/remove must affect one package each.
- Replace `improvement-workspace.tsx`'s text-only final review with the existing `ContentDiff` from `diff-content.tsx`, using the exact parent and candidate payloads already fetched. It already shows kind changes, additions/deletions (including empty entries), rename-as-remove/add, and a 500-line preview bound. Do not introduce another diff algorithm. Keep target/revision, version ID and verified digest next to that review.

## Remove the full-echo proposal limit

Change only the OpenAI adapter's provider response contract initially; keep public `ProposalModel -> (BundlePayload, rationale)` so other implementations and the worker boundary remain compatible. The adapter reconstructs a candidate using a pure helper, then the worker still enforces generic limits, allowed paths, unchanged kinds/file set and current native policy.

Provider JSON becomes `{schemaVersion: 1, edits: [{path, oldText, newText}], rationale}`. Strictly reject unknown keys/wrong types, cap JSON content at 32 KiB, rationale at 4 KiB, and edits at 128. Every path must be an exact existing allowed path. Each nonempty `oldText` must occur exactly once in the **original parent file**, counting overlapping occurrences too; reject absent/ambiguous anchors and overlapping original ranges. Empty `oldText` is allowed only for an empty parent file, with one edit for that path. Multiple disjoint edits may share a path. Apply them from the end of each original file, preserving original file order, kind, path and all untouched UTF-8 text. No fuzzy matching, implicit append, sequential matching against earlier edits, file creation/deletion or kind changes. An empty edits list is a valid unchanged candidate.

This supports a small change inside a large file without making the model calculate byte offsets or echo untouched text. Repeated ambiguous text needs a longer unique anchor; very large replacement text remains bounded and can fail honestly. Keep the existing parent/request input bound and provider timeout/token cap. Raise the separately bounded HTTP response envelope from 64 KiB to 256 KiB to accommodate JSON-escaped 32 KiB content; cap streamed bytes before parsing. Provider truncation or excessive edits produce a safe terminal failure, never a partial candidate. Prompt explicitly preserves existing SKILL metadata; worker validation supplies the selected-target guarantee without expanding the provider trait. Do not advertise unlimited edits to 1 MiB bundles.

## Acceptance that closes the audit gaps

- Shared fixtures cover zero/one/two instructions, absent/miscased manifests, support-only packages, missing/mismatched metadata, name length and case collisions, uppercase/underscore names allowed by Codex/Claude/Pi but rejected by Cursor, and UTF-8/CRLF. Each fixture asserts generic validity independently of every target's compatibility.
- Console/server and PostgreSQL route tests: malformed skill import fails for a native bundle without any partial setup/snapshot; the same payload succeeds for generic. Native draft/proposal edits removing metadata cannot create a candidate or publish. Generic multi-instruction create/save/propose/publish remains supported. Exercise the real plugin preparation on accepted fixtures without models.
- Store an old generic incompatible version, adopt a native policy only after current channels are repaired, and verify rollback to the old version fails while history/read still works. Direct promote, draft publish and unevaluated promote enforce the same rule. Race policy changes with proposal completion/publication; get either a fully checked commit or a conflict, never incompatible native publication. Include replay after a policy change to preserve the earlier successful outcome.
- Add two skill packages, rename one and remove one; verify distinct paths/frontmatter and a saveable payload. Assert existing roots/path collisions advance the generated suffix. Render final review with an instruction-to-memory kind change, an empty-file deletion, an empty-file addition and a rename; each appears, with large diffs still bounded.
- Model-free provider adapter test: parent has an untouched 40,000-character memory file plus a changed small instruction; a small edit response succeeds and preserves the memory text exactly. Also edit a unique span inside a >32 KiB file, including non-ASCII text. Reject unknown/disallowed paths, duplicate edits, ambiguous/missing/overlapping anchors, unsupported operations, malformed JSON, excessive content/envelope/edits, and reconstructed file/payload overflow. Assert no candidate row on failure and retain existing late-attempt fencing tests.

## Delivery/ownership and compatibility effects

Service/content owner owns migration, bundle policy command, lock ordering, `src/{bundles,drafts,channels,improvement,compatibility}.rs`, provider reconstruction and transaction tests. SDK/contract owner owns Bundle/setup/change-policy DTOs, optional expected-policy revisions, typed client method, TS validator and parity fixtures; coordinate corresponding Python DTO/client additions. Console/content owner owns import/draft/review wiring and the two small editor fixes. Native plugin owners replace duplicated checks and run preparation fixtures.

Existing bundles migrate to generic without rewriting payloads, versions, digests, promotions or proposals. Previously stored generic drafts regain generic saving rather than inheriting a hidden lowercase restriction. Native adoption is deliberate and checks all active channels; historical snapshots can be opened but must be repaired before a new native-policy save/release. Existing queued proposals use current policy when their next attempt starts. No proposal storage migration or full-payload provider fallback is needed; persisted requests contain no old provider response schema. Additive HTTP fields are backward compatible; Rust struct literals/fixtures constructing expanded DTOs need source updates. Existing provider-trait implementations remain unchanged.

Coordinate before implementation: the improvement/evaluation owner also touches `src/improvement.rs`, `src/lib.rs` and `improvement-workspace.tsx`; recovery owner touches draft/release commands and idempotent replay; connections owner touches Bundle DTO consumers/recipe selection. One owner should land the migration/DTO shape and lock order first, then validators and enforcement, then UI/provider patches. Do not independently edit the same request structs or replace recovery checks in parallel.

Open decisions for the combined plan: exact public command path/name and stable error-code vocabulary; whether to require explicit target choice for every new console bundle or preselect generic with its limitation visible. The recommended storage, enforcement and patch contracts above do not depend on those presentation choices.
