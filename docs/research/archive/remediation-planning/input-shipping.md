# Shipping and local setup remediation input

**Planning input. The [reviewed plan](../../../architecture/productization/remediation/plan.md) and [review resolutions](../../../architecture/productization/remediation/review.md) take precedence where choices differ.**

Planning only, based on the [2026-11-14 audit](../../../architecture/productization/current-audit.md) and source inspection. No setup, model call, artifact upload or deployment was run for this plan. The immediate result should be a usable local path plus an explicit qualification ledger. A checkout build is not downloadable distribution; offline adapter tests are not live provider evidence.

## 1. Make launcher failures useful without exposing configuration

`scripts/dev-console.ts` already raises useful errors for occupied port 3000, unsafe private files and an existing console configuration, then discards every explanation in its final catch. Its port probe also misses a listener that accepts a connection without returning a health response. Native database settings are intentionally fixed at `127.0.0.1:5432`, OS username, and a checkout-specific database.

- Extract typed setup failures and an allowlisted formatter, e.g. `scripts/local-config.ts` / `scripts/local-diagnostics.ts`, used by `scripts/dev-console.ts`. Emit a stable category and concrete next action for missing `psql`/`createdb`/Cargo/Node, unavailable native PostgreSQL, port 3000 or 3100 occupied, private-path permissions/ownership/symlink failure, conflicting `.env.local`, build failure and child startup/ownership-retry exhaustion. Check both binds before starting children; handle the bind race as a startup failure too.
- Keep unexpected errors generic with the failed phase. Never interpolate arbitrary exception text, child stderr, environment values, database URLs, config contents or credentials into diagnostic output. Existing child inherited logs need review too: database/tool failures should pass through the same safe classification rather than printing a secret-bearing connection string. Do not remove/reset configuration, chmod an existing unsafe path, kill another listener or fall through to creating another database as recovery.
- Add focused tests under `scripts/`: inject process/filesystem failures and a sentinel secret; assert category, actionable text, nonzero exit, child cleanup and absence of the sentinel. Exercise both occupied ports with disposable listeners, including a non-HTTP listener. Preserve existing code-75 backend-only retry tests in `scripts/local-processes.test.ts`.

Done locally when the known errors remain distinguishable, unexpected errors remain private, and `npm run local` can start empty, stop and reopen its own workspace. No native database failure should be mislabeled as a general console error or vice versa.

## 2. Keep two database paths explicit; add the missing manual console bridge

Use the smallest bridge first. Keep `npm run local` / `npm run demo` as the native-PostgreSQL convenience path. Document a complete manual Compose service + console path in `docs/development.md`, `apps/console/README.md` and `deploy/README.md`; do not imply that exporting the Compose `DATABASE_URL` changes the launcher. Today it does not.

- Start only `docker compose up -d postgres`, then the Rust service with the documented loopback Compose database (`55432`, role/database `acclimate`) and a private project grant. Start only the frontend with `npm run dev`, using an owner-only `apps/console/.env.local` containing the matching service URL, project and server-side credential. A fresh project needs no bundle ID; select/create/import in Bundles. Generate real local tokens privately; do not ask users to paste them into UI or reusable shell history. Any small configuration writer should reuse the launcher's private-file checks and refuse an unrelated existing `.env.local`.
- Show which process owns each stop/start operation and which database holds the content. The manual path must never launch `npm run local` against an already-running Rust service or silently replace the native workspace state. Compose teardown must preserve its volume unless the operator deliberately requests deletion.
- Add model-free disposable acceptance coverage for the console bridge: empty workspace, explicit example/import, authenticated read, restart persistence, wrong grant, unavailable DB and config conflict. Keep native launcher coverage separately. If Docker is unavailable, an equivalent isolated PostgreSQL test can verify connection/config plumbing, but mark the actual Compose run blocked.

Done when a new operator can follow either recipe end to end without guessing how the console connects. An arbitrary remote/database URL override, automatic Docker startup and database migration between the two paths are scope cuts.

## 3. Give the local evaluator a private credential handoff

Dependency: the improvement/evaluator remediation owns installed evaluator configuration, request/attempt binding, behavior cases, grading and retry semantics. This task supplies launch context and a runnable command only; it must consume that owner's fixed entry point and configuration ID, never introduce another evaluator protocol.

- Add `scripts/local-evaluate.ts` and an npm command, with a safe invocation such as `npm run local:evaluate -- --bundle ID --requestID ID`. Replace the unusable raw `npx tsx examples/evaluate-request.ts ...` hint in `apps/console/src/components/improvement-workspace.tsx` only for launcher-backed local workspaces. Bundle/request IDs are public routing values, never credentials. Manual and hosted setups get explicit operator configuration instructions instead of a false claim that local state exists.
- Reuse a shared private configuration reader extracted from `scripts/dev-console.ts`. Validate ownership, mode, file type, symlink ancestry and schema before reading; fail closed for missing/conflicting state. Resolve the selected bundle and request against the fixed local project/service. Do not use the console's remembered bundle as the authority for a command copied from another bundle page.
- The current private author grant has `read` and `write`, which evaluator reads/transitions/comparison submission require; connection grants cannot do these writes. Use that existing local author principal for the first version, with one consistent principal across start/report/finish. Do not issue broader integration credentials or add new service rights as incidental work. A dedicated narrower evaluator authorization model is a later security/design choice.
- Pass configuration directly in process or through a minimal child environment to the allowlisted installed evaluator; never put tokens in command arguments, UI, logs or reports. Do not execute a command, module or URL supplied by a request. Keep subprocess output/errors sanitized and return only request/status/comparison identifiers. Do not inherit accidental model/provider settings; only pass runtime configuration explicitly approved by the evaluator owner.
- Acceptance: a launcher-created request completes a model-free installed fixture with no manual token export; a connection credential is denied; a different bundle/project and unsafe/missing private state fail safely; no sentinel token appears in captured UI/argv/stdout/stderr/artifacts. An uncertain child result links to the durable request rather than claiming failure or blindly starting a second attempt. Run `npm run test:evaluator` plus the owner's new binding/retry checks.

This is complete only once the owner's evaluator can actually consume the helper. A documented command that still needs an undisclosed environment is not completion. Paid behavioral evaluation remains separate and Luna-only.

## 4. Prepare versioned downloadable SDK artifacts

Existing `scripts/packaging/verify.mjs` builds five npm tarballs into a temporary directory, installs them offline, checks runtime/types/native helpers, then deletes them. `scripts/check-python-package.py` similarly verifies a wheel. Both contain hardcoded `0.1.0` checks. These are useful local evidence, not a download channel.

- Add a local-only artifact builder under `scripts/packaging/` and an npm entry point. Read versions from package metadata, require the intended SDK/plugin/Python compatibility set, and emit `artifacts/releases/<version>/` containing the five named/versioned tarballs, Python wheel, SHA-256 manifest and short install instructions. Record source commit, toolchain and optional peer versions; exclude `.local`, environment files, caches, evaluator evidence and credentials. A release version must identify one immutable artifact set; reject accidental overwrite with different bytes.
- Refactor both isolated-consumer checks to accept that exact artifact directory and derive expected versions from its manifest. Install outside the checkout, verify runtime imports and TypeScript declarations, preparation-only imports without native peers, native helper checks with pinned peers, and Python isolated imports. Validate archive contents and checksums before uploading. Existing peer-copy checks prove installed adapter compatibility, not fresh online peer resolution or provider access.
- Prepare a release workflow/runbook in `.github/workflows/` and `docs/development.md` that uploads the already-verified files to one versioned release-asset path, e.g. a repository release tagged `v<version>`. Document exact asset names and checksum verification so consumers can install SDK + selected plugin together without a checkout. No npm/PyPI publication is needed for this route.
- Local acceptance: build a retained artifact set and consume precisely those bytes in clean TS/Python apps; run `npm run pack:verify` and `python3 scripts/check-python-package.py` against the retained set after refactoring. Hosted CI execution is separate evidence; configured YAML is not a passing hosted run.

Local work finishes at a reviewable, tested artifact set and upload workflow. **Distribution stays blocked until a separately authorized release upload exists and a clean consumer downloads, verifies and installs those public/versioned bytes.** Do not publish, upload, tag a release or deploy as an incidental check.

Preserve the existing narrower Codex/Luna evidence; do not relabel this planning pass as a rerun.

Provider runs remain opt-in and **all model-backed development/qualification uses Luna only**. Missing compatible provider support is an honest external blocker; missing local examples, checks or safe diagnostics is unfinished implementable work. Real credentials, a working Docker host, an issuer/domain/certificate and explicit release/deployment authorization are dependencies, not permission to inspect private configuration or provision services now.

## Order and finish line

1. Ship safe launcher diagnostics and the manual Compose bridge; extract the private local configuration reader once.
2. Integrate the evaluator helper after the evaluator owner fixes its entry point, identity binding and recovery contract.
3. Produce retained versioned artifacts and a tested upload workflow; leave the external upload pending authorization.
4. Add provider/host qualification harnesses and the evidence ledger; execute only the locally available, authorized gates.

The local remediation can be marked complete with passing targeted model-free checks, documented working native/bridge flows, a usable evaluator handoff, retained installable artifacts and explicit outstanding gates. Shipping/hosted/native-provider claims stay incomplete wherever genuine external evidence is absent. No registry publishing, production rollout, new hosting platform, invitation system, multi-replica service, Windows ACL support, universal provider support or hot reload is included.
