# Contract review

Reviewed `plan.md` and the content, recovery, evaluation, and access/delivery inputs against current Rust/SDK sources. The fixed compatibility enum, separate generic validation, immutable JSON binding, and deterministic edit reconstruction fit this service. The following decisions need tightening before implementation.

## Must fix

1. **Binding enforcement is a client-breaking change.** `src/evaluations.rs:330–355` currently accepts matching unbound comparisons; `src/types.rs:116–126` and `packages/sdk/src/compare.ts:39–65` cannot express binding. Requiring it for every finish immediately breaks installed evaluators and in-flight requests, including legacy requests the input still permits creating. Optional fields and service-first deployment alone do not preserve behavior. Specify a coordinated runner upgrade/cutover and document the break, or an explicit bounded legacy transition. Keep old stored reports readable and existing terminal finish replay valid; never guess historical associations.

2. **Close must fence unmarked retries too.** Currently `src/commands.rs:60–80` consults durable records only when `durable` is true. Applying that condition to the proposed tombstones lets an unmarked delayed promotion/proposal bypass a confirmed close. Every allowlisted action must consult matching committed/closed identities under the shared lock regardless of opt-in; opt-in can control new receipt retention. Close must also inspect an unexpired legacy route receipt and return/promote its commit instead of writing a misleading closed result. Keep action/path collisions explicit. Existing setup/draft keys already use the shared namespace; their lock must remain compatible during rollout.

3. **Record and recheck all required rights.** The new compatibility command requires write plus promote, but `MutationTx.required_right` and `command_results.required_right` contain one string (`src/commands.rs:23,123,148–152`; migration `0008_command_results.sql:7`). Setup already separately checks promote before recording only write (`src/drafts.rs:438–442`). Define action-to-required-rights in the small allowlist and apply it to fresh execution, committed replay, lookup, and close; reauthorize inside the mutation transaction. This avoids a general permission framework while preventing a write-only machine grant from retrieving a dual-right outcome.

4. **Make the lock hierarchy complete, including nested helpers.** Bundle-before-draft/channel is correct, but inserting the new lock only in `promote_in_tx` is too late: draft publication already holds its draft, promotion advisory lock, and channel (`src/drafts.rs:237,268–284`). Direct promotion acquires advisory then channel (`src/channels.rs:173–179`); worker completion locks proposal before inserting its version (`src/improvement.rs:367–381`). Specify command locks → bundle → draft/proposal → promotion advisory/channel for these paths, acquiring bundle before entering nested promotion. Preserve replay before fresh bundle/policy locks. Race tests must include draft publication against direct promotion and policy changes, plus worker completion.

5. **State what direct promotion means after binding.** `src/channels.rs:196–239` requires complete matching evidence, parent/current channel, and digests; it does not require an evaluation request, evaluator principal, winning score, or completed request. Thus a complete bound report stored immediately before interruption can still authorize direct promotion although finish fails. Prefer preserving this small existing release contract, explicitly label the request status separately, and test it alongside historical unbound release. Do not claim binding makes request completion a release prerequisite. In every fresh release, current stored compatibility must still validate the actual target payload; committed replay after policy changes remains the earlier outcome.

6. **Freeze descriptor canonical bytes, not just “sorted keys.”** Runtime keys/case IDs currently accept Unicode (`src/evaluations.rs:125–132`), so JS UTF-16 sorting and Rust string sorting can disagree. Specify one ordering, string escaping, integer representation, and rejection of lone surrogates/duplicate JSON keys; golden vectors should include non-ASCII keys, control characters, and inventory reordering. A fixed-field serializer with explicitly sorted entries is enough. Keep this separate from immutable bundle encoding (`src/lib.rs:62–81`), whose bytes/digests must not change.

## Optional refinements

- Cursor design is sound. Preserve database microseconds throughout encoding/decoding; never round through JavaScript `Date`. Existing `ListQuery::bounds` only parses UUIDs (`src/evaluations.rs:56–63`), so scoped legacy resolution belongs inside the authorized collection transaction.
- Explicitly check provider `finish_reason` before accepting even syntactically valid truncated JSON (`src/lib.rs:234–245`); bound both decoded UTF-8 content and streamed envelope. Keep the public provider trait unchanged.
- Add policy fields to manually assembled bundle responses too (`src/workspaces.rs:172–174`, `src/drafts.rs:477`), not only the `Bundle` struct. Centralized additive migrations after `0009` are sufficient; no payload rewrite is needed.
