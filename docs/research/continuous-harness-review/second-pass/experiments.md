# Second pass: the continuous experiment model

Review date: 2026-11-17. Independently inspected TypeScript evaluator definition, execution, artifacts and journal, Rust request/comparison binding, and the twenty-round controller. No tests, models or applications were run. This review challenges the prior [evaluation](../evaluation.md) and [RRSI](../rrsi.md) findings rather than assuming their recommendations are necessary.

## 1. High for full harness evolution: distinguish experimental controls from each arm's treatment

**Confirmed gap, narrower than “shared runtime prevents harness changes.”** `CreateEvaluationRequest` has one `runtime` map ([evaluations.rs:19](../../../../src/evaluations.rs#L19)); the SDK freezes the same public descriptor for both arms ([definition.ts:137](../../../../packages/sdk/src/evaluation/definition.ts#L137)); request completion requires the comparison's entire runtime map to match ([evaluations.rs:404](../../../../src/evaluations.rs#L404)). That expresses one fixed evaluation configuration around two content snapshots.

This does **not** technically prevent comparing different tool implementations, model settings or executable harnesses. Execution receives `context.side` and the bundle ([types.ts:36](../../../../packages/sdk/src/evaluation/types.ts#L36), [runner.ts:566](../../../../packages/sdk/src/evaluation/runner.ts#L566)). An application can branch explicitly and encode `parentHarnessManifestSha256` and `candidateHarnessManifestSha256` as ordinary runtime keys. Therefore a claim that the schema makes arm-specific harness changes impossible should be retracted. The existing native-repository job record already retains source, harness, context-policy and selected-memory fingerprints ([repository-job.mjs:504](../../../../examples/native-repository/repository-job.mjs#L504)).

**Failure scenario.** A candidate changes context selection and tool code. The application either describes both arms with a misleading single `runtimeRevision`, or bumps the evaluator revision and treats a deliberately changed treatment as if it were a changed benchmark. Across repeated rounds, it is then unclear which differences are legitimate treatments and which make comparisons incomparable. Generic tooling cannot check that the new candidate actually became the next incumbent's same harness configuration.

**Smallest remedy.** Define an app-owned canonical experiment manifest with explicit `controls` (dataset, grader, fixture/environment protocol) and `arms.parent`/`arms.candidate` (content, runner/source artifact, tool contracts, context policy, model settings). A single manifest digest can fit the existing runtime map initially; no wire-schema migration or hosted runtime is prerequisite. Have the installed executor validate its actual selected arm against that manifest before launch and retain its identity in the private job record. A future typed wire shape can follow demonstrated usage. Digests detect accidental drift; they are not execution attestation, and a mutable provider model cannot be made immutable by hashing its alias.

**Confidence:** high. This is a domain-model clarity and reproducibility gap, not a current content-only evaluator defect.

## 2. Medium for continuous operation: the recovery unit is the whole experiment, not a trial

The journal has a single `executionStarted` marker and optional final report ([journal.ts:58](../../../../packages/sdk/src/evaluation/journal.ts#L58)). The runner persists that marker before any callback ([runner.ts:519](../../../../packages/sdk/src/evaluation/runner.ts#L519)), saves output and grader-explanation artifacts along the way ([runner.ts:637](../../../../packages/sdk/src/evaluation/runner.ts#L637), [runner.ts:710](../../../../packages/sdk/src/evaluation/runner.ts#L710)), but only saves the report after the entire inventory ([runner.ts:739](../../../../packages/sdk/src/evaluation/runner.ts#L739)). Any resume with started execution and no report refuses further callbacks ([runner.ts:473](../../../../packages/sdk/src/evaluation/runner.ts#L473)). Inspected tests explicitly expect this refusal even after one callback ([core.test.ts:574](../../../../packages/sdk/tests/evaluation/core.test.ts#L574)); those tests were not run here.

**Failure scenario.** A large comparison finishes almost every expensive trial, then the process dies. Retained outputs and explanations help inspection, but there is no authoritative per-trial completion ledger from which the generic runner can resume only untouched work. An always-running learner repeatedly reaches manual interruption/replacement rather than continuing its exact experiment. If a controller simply retries whole experiments until one finishes, it also needs a declared rule for retaining interrupted trials and accounting for their spend; otherwise reliability failures can silently select which measurements survive.

**Counterargument and correction.** Current refusal is the correct safety behavior for callbacks that might have caused effects. It is not evidence of broken idempotency: a saved final report is replayed with retained bytes/keys without rerunning callbacks. Do not “fix” this by clearing the marker or inferring completion from an output file.

**Smallest remedy.** Keep uncertainty refusal. Add an optional app-owned trial ledger keyed by campaign/request/attempt/case/repetition/side, with durable intent, confirmed result/grade and an explicit reconciliation contract. Resume only confirmed completed work and provably unstarted work; uncertain external work must settle under its original operation identity. The default nonreplayable callback model may remain conservative. A campaign should retain interrupted/abandoned measurements and usage as distinct records even when the quality report cannot be completed.

**Confidence:** high for current mechanics; medium for operational priority, which depends on experiment size and interruption frequency.

## 3. High before unattended optimization: freeze the collection and evidence-use protocol, not only the comparison rows

The runner uses declaration order, then parent before candidate ([runner.ts:537](../../../../packages/sdk/src/evaluation/runner.ts#L537)). Each arm has a distinct job ID/directory and cloned input, which prevents accidental shared input mutation; it does not reset external fixture state or process/global caches ([runner.ts:551](../../../../packages/sdk/src/evaluation/runner.ts#L551)). The analysis interface correctly requires an application assertion of independent stochastic pairs and explicitly estimates a **fixed-case** interval ([analysis.ts:24](../../../../packages/sdk/src/evaluation/analysis.ts#L24)); its bootstrap seed controls resampling, not execution randomization ([analysis.ts:342](../../../../packages/sdk/src/evaluation/analysis.ts#L342)).

**Failure scenario.** Parent work warms a shared cache and candidate work systematically benefits; or model/provider conditions drift during collection. A controller then repeatedly searches the same case set until a candidate clears the descriptive threshold. Neither a complete comparison nor a bootstrap interval computed from that selected experiment repairs the confounded collection or repeated peeking. Merely adding random order would also leave shared-state contamination unresolved.

**Counterevidence to retain.** The current deterministic simulators may be side-effect-free and require no randomized order. The twenty-round qualification already uses a once-only independent audit and refuses release if that audit fails ([twenty/run.ts:364](../../../../examples/self-improvement/twenty/run.ts#L364)); it must not be described as having no held-out evaluation. Its threshold policy is explicitly descriptive, and current service publication remains a deliberate authorized decision.

**Smallest remedy.** Freeze an application collection protocol alongside the experiment: trial inventory, seeded balanced arm order when stochastic, fixture reset/isolation contract, relevant environment/model regime, and recorded actual order. Separately version evidence-use rules: which trials may train/propose, which may select, which reserve a release audit, allowed audit cadence, exposure accounting and retirement. Retain every candidate decision, including failures and abstentions. A continuous controller must stop or rotate evidence under that protocol instead of treating the same audit as indefinitely fresh. Repeated unchanged-harness controls help calibrate observed noise; they do not establish arbitrary distributional generalization.

**Confidence:** high for the fixed order and analysis scope; risk depends on callback statefulness and how the future controller uses evidence.

## Resulting design direction

Keep application execution, exact content/request/attempt bindings, private artifacts, explicit missing outcomes and refusal to replay uncertain work. Add a deep application-side experiment module that owns arm manifests, the collection protocol and trial reconciliation; a campaign module owns the longer-lived selection/audit policy. Avoid expanding the content service into an execution runtime merely to express these concepts.
