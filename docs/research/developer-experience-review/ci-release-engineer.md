# CI and release engineer review

Date: 2026-11-16. This is a simulated, source-based persona review, not user research or a live deployment assessment. No application or service code was changed.

## Persona and job

I maintain an agent application's pull request checks. A developer changes a skill, I evaluate the candidate against the deployed baseline, publish reviewable evidence, and block regressions. An authorized reviewer subsequently releases the selected immutable version; rollback must be explicit and auditable. I expect to keep execution and quality policy in my application.

My adoption question: can an ordinary engineer add this to a disposable CI worker without learning Acclimate's internal qualification harness or inventing a second evaluation lifecycle?

## Journey through the current product

1. Install `@acclimate/sdk` and the required native plugin. The SDK exposes `compare`, `submitComparison`, and low-level evaluation lifecycle methods (`packages/sdk/src/index.ts:11`, `packages/sdk/src/client.ts:517`). This is a useful base for a headless integration.
2. Pin parent and child candidate versions, define cases, snapshots, settings, runtime, dataset revision, and grader revision. Supply my own execution and grading callbacks (`packages/sdk/src/compare.ts:39`). This fits an existing application.
3. To participate in the console request lifecycle with durable recovery, discover `examples/evaluation/runner.ts`, its installed adapter interface, and a separate private evaluator configuration. The checkout CLI only selects the three included adapters (`scripts/evaluate-app.ts:25`). I must build my own wrapper for my application.
4. Run the evaluation and submit evidence. The runner's terminal status describes evidence completeness, including failed partial evidence, rather than the application's quality verdict (`examples/evaluation/runner.ts:143`, `src/evaluations.rs:313`). The CLI reports that status but does not turn a returned `failed` status into a failed CI step (`scripts/evaluate-app.ts:58`).
5. Inspect the comparison through the console or operator review. Scores and missingness are visible, but detailed output references generated by the runner point to files on the evaluator machine (`examples/evaluation/runner.ts:127`). I must arrange retention and access for other reviewers.
6. Explicitly promote using the reviewed channel revision and comparison, then roll back using a reason if needed (`tools/operator/README.md:11`). This separation is sound. The service validates evidence identity and completeness, not my application's quality policy (`src/channels.rs:198`).

## Prioritized findings

### 1. High: a successful evaluator process is not a usable PR check result

**Observed evidence.** `scripts/evaluate-app.ts:58-64` prints `{requestId,status,comparisonId}` on every resolved result and sets `process.exitCode = 1` only for a rejected promise. `examples/evaluation/runner.ts:88` returns an already `failed` request normally; lines 143-151 also return newly finished failed requests normally. The service sets `failed` for incomplete comparisons (`src/evaluations.rs:309-317`). Complete losses deliberately remain `completed` (`examples/evaluation/README.md:48` and the source test at `examples/evaluation/runner.test.ts:37-45`). The operator `review` command returns evidence without a quality verdict (`tools/operator/cli.ts:226-236`).

**Impact.** A CI author who runs the provided evaluator as a required step can get a green shell command for failed infrastructure/grading evidence, as well as for a candidate regression. The JSON status allows a custom check, but the current command is an orchestration tool, not a ready-to-use regression gate.

**Recommendation.** Keep evaluation completion distinct from quality and release authorization. Provide an explicit check mode or separate gate command with documented statuses for incomplete evidence, quality failure, and execution/configuration failure. Accept an application-owned policy rather than implying that any positive mean is sufficient. Include a minimal PR workflow using that policy and showing how to preserve evidence on failure.

**Acceptance criterion.** An example PR check fails for incomplete evidence and a policy-defined regression, passes a complete policy-approved result, emits a machine-readable verdict, and never promotes a channel. A completed losing evaluation remains a valid saved evaluation.

**Classification.** Missing CI ergonomics with a concrete exit-status trap; the distinction between completion and improvement is intentional and correct.

### 2. High: the supported headless pieces do not form an installable custom CI evaluator

**Observed evidence.** The public SDK exports the comparison helper and low-level lifecycle client, but not `InstalledAdapter` or `runEvaluation` (`packages/sdk/src/index.ts:1-21`). Those live under `examples/evaluation/adapter.ts:6` and `examples/evaluation/runner.ts:51`. SDK package exports and shipped files are limited to `dist` surfaces (`packages/sdk/package.json:5-20`). The provided CLI's explicit allowlist contains `payment-retry`, `presence-contract`, and `codex-luna-review` (`scripts/evaluate-app.ts:25-36`). The operator command inventory includes proposal/review/history/promotion/rollback but no evaluation request, status, or interrupt commands (`tools/operator/cli.ts:13-20`). Documentation explicitly tells users to install the checkout separately or consume the public SDK for custom evaluators (`examples/evaluation/README.md:5`, `:26`, `:46`).

**Impact.** My app can absolutely evaluate headlessly, but installing the SDK does not give it the durable runner demonstrated in the console handoff. I either vendor source and its dependencies, maintain request/start/submit/finish/recovery glue, or write a simpler direct comparison integration that omits that lifecycle. This is substantial adoption work for an otherwise small integration.

**Recommendation.** Offer a supported installable evaluator helper with the current installed-callback boundary, or a standalone external-consumer template that owns all lifecycle glue explicitly. Include headless request/status/interrupt examples, adapter identity validation, persistent idempotency keys, and a complete workflow. Preserve the rule that service requests cannot load arbitrary code or endpoints.

**Acceptance criterion.** A clean external app installs documented release artifacts, defines its own installed execution/grading callbacks, creates and completes a request using documented imports, and needs no relative import into the Acclimate checkout. The example includes failure and retry paths.

**Classification.** Product packaging and documentation gap, not absence of headless APIs or a request to execute arbitrary uploaded adapters.

### 3. Medium: safe recovery assumes a stable machine filesystem, while CI assumes disposable workers

**Observed evidence.** Journals bind recovery to an absolute original root (`examples/evaluation/journal.ts:100-109`) and use a Python `fcntl` process lock (`:31-44`, `:58-67`). An existing running request with no local journal is refused; an execution marker without a complete report is also refused (`examples/evaluation/runner.ts:90-99`). The documented remedy after process death without a saved report is to interrupt and create a new request (`examples/evaluation/README.md:48-50`).

**Impact.** A normal fresh CI retry does not automatically have the original journal, path, or evaluator identity. A canceled run may leave a running request that a new worker cannot resume. Restoring arbitrary copied state into a different location is explicitly unsupported. These protections are valuable, but the integration recipe does not give a disposable-worker operating model.

**Recommendation.** Document two supported patterns: an application-owned durable evaluator worker with a stable private volume, and a disposable job that treats uncertain execution as requiring explicit interruption and a new request. Explain cancellation, the exact recovery boundary, stable identity, and required tools. Provide a headless cleanup example using the existing interrupt API; do not recommend deleting the journal or automatically replaying execution.

**Acceptance criterion.** A CI recipe explains and demonstrates cancellation before execution, after the execution marker, and after report persistence. Each case produces an explicit recoverable state or an actionable interrupt/new-request result, without duplicate agent execution.

**Classification.** Deployment/workflow friction caused by a deliberate at-most-once execution safeguard. Making journals freely relocatable is not the requested fix.

### 4. Medium: detailed eval evidence does not travel naturally from the worker to the reviewer

**Observed evidence.** The runner writes private per-case outputs into its journal directory and submits `file:` output references (`examples/evaluation/runner.ts:125-127`, `examples/evaluation/journal.ts:113-118`). The console renders the reference as text rather than loading output (`apps/console/src/components/evaluation-pair-row.tsx:40-43`). Operator review likewise displays untrusted references without fetching them (`tools/operator/README.md:15`). The evaluator CLI prints only request ID, status, and comparison ID (`scripts/evaluate-app.ts:60`).

**Impact.** The release reviewer can inspect outcomes and errors but cannot inspect the worker's detailed trace from a different machine. After an ephemeral job disappears, even a retained comparison can reference lost evidence. Teams must discover the journal layout and build their own safe artifact mapping and retention policy.

**Recommendation.** Provide an explicit evidence export manifest containing request/comparison identity, immutable version digests, per-case artifact names and content hashes, and a documented CI artifact upload/retrieval pattern. Support an application-controlled artifact store or locator without automatically fetching arbitrary untrusted URLs. Keep private journals and credentials out of broadly shared artifacts.

**Acceptance criterion.** From a saved comparison, an authorized reviewer on another machine can locate the retained output for a specific case and repetition and verify its association with the run. The recipe remains usable after the CI worker is deleted, and never uploads evaluator credentials.

**Classification.** Evidence handoff and retention gap; text-only treatment of untrusted references is a strength to preserve.

### 5. Medium: CLI errors discard the structured metadata CI needs for triage

**Observed evidence.** `ApiError` contains `status`, `code`, `requestId`, and optional details (`packages/sdk/src/client.ts:46-58`). The operator CLI emits only `{error: message}` (`tools/operator/cli.ts:264-271`). The evaluator CLI deliberately maps API and unexpected failures to a generic inspection message (`scripts/evaluate-app.ts:41-55`); all rejected cases have the same exit code (`:61-63`).

**Impact.** Automation must parse wording or direct operators to private state to distinguish access denial, a stale channel revision, descriptor mismatch, and an uncertain transport outcome. Correlating a CLI failure with service logs also loses the request identifier that already exists in the SDK. Safe defaults are sensible, but this increases time to diagnose failed checks and release attempts.

**Recommendation.** Add a safe structured error envelope with a stable category/code, request ID when present, operation, and a documented next action or retry classification. Preserve redaction of secrets and arbitrary server details. Differentiate a policy failure from an incomplete run and an operational error in the CI-facing command.

**Acceptance criterion.** Offline CLI tests can classify denial, revision conflict, invalid input, adapter mismatch, and uncertain submission without parsing prose, and no credential or private file content appears in output.

**Classification.** Diagnostic usability gap; do not remove error sanitization.

## Strengths to preserve

- Explicit release and rollback, compare-and-swap channel revisions, and evidence/version digest binding make automated evaluation compatible with accountable human release decisions (`src/channels.rs:187-240`).
- Fixed paired inventories, isolated snapshots, execution/grading separation, and retained infrastructure failures are appropriate foundations for PR checks (`packages/sdk/src/compare.ts:130-158`, `:205-214`, `:251-259`).
- A retry of a saved report can reuse exact operation keys without rerunning callbacks; source tests cover response-loss scenarios (`examples/evaluation/runner.test.ts:76-100`).
- Operator review verifies payload bytes, is read-only, distinguishes unknown usage, and never follows output references (`tools/operator/README.md:15`).
- The scorecard explicitly says complete evidence is not a win or release approval (`apps/console/src/components/evaluation-scorecard.tsx:90-97`).

## Verification and unknowns

Therefore the behavioral conclusions above are source-level findings, not newly executed test results. No live service, provider, deployment, or CI run was exercised; no claim is made about hosted CI status or the reliability of an external deployment.

The repository's `.github/workflows/ci.yaml:34-55` validates Acclimate itself extensively. It is not a ready-to-copy integration workflow for an adopter's custom agent quality policy. An organization may already have private wrappers, artifact storage, or release policy integrations; none were available for this review.

## Top three fixes

1. Ship a complete CI check recipe with explicit quality policy, incomplete-evidence handling, and machine-readable verdicts.
2. Make the custom durable evaluator usable from an installed external application through a supported helper or complete template.
3. Add a reviewer-ready artifact manifest and documented retention/retrieval workflow, alongside the stable-worker versus disposable-worker recovery recipes.
