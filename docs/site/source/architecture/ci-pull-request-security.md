# GitHub Actions pull request security

[Architecture guide](README.md) · [Release procedure](../releasing.md)

Treat pull request code as untrusted, including workflow changes, local actions, build scripts, dependencies, and configuration. Run PR builds and tests with minimal read permissions and without publishing credentials. Give credentials only to jobs that run reviewed code at an approved commit. [GitHub secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)

## Configure Acclimate on GitHub

- Protect `main` with a ruleset that requires pull requests, review, and the applicable CI checks. Keep the check names unique and select GitHub Actions as their expected source. Give repository write access only to trusted maintainers and use forks for contributions from others. [Required status checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging)
- Create a tag ruleset for `v*.*.*` and restrict creation, updates, and deletion to release maintainers. The release workflow checks that the tag points to a commit on `main`. The tag ruleset controls who can select the commit that supplies the workflow itself. Keep the `npm` and `pypi` environments limited to release tags with approval required. [Ruleset controls](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- Create a `docs` environment and allow only the `main` branch. Set `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as secrets in that environment. After verifying a deployment from `main`, remove the repository-level copies so workflows on other refs cannot request them. If the original token is unavailable, provision a replacement and revoke the old token after the deploy succeeds. [Environment secrets](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#environment-secrets)
- Enable the full-length SHA requirement after the pinned workflows have merged. Keep the default workflow token read-only and the option for GitHub Actions to create or approve pull requests disabled. [Repository Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)

## Workflow and credential boundaries

- **Fork pull requests.** A normal `pull_request` check uses the PR merge commit, including its version of the workflow. GitHub normally limits the fork's `GITHUB_TOKEN` to read access and withholds Actions secrets. Repository and organization policy can affect whether runs need approval and, for private repository forks, whether write tokens or secrets are sent. Keep those grants disabled for untrusted CI and treat approval to run as permission to use runner time. [Pull request events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) · [Repository Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#enabling-workflows-for-forks-of-private-repositories)
- **Same-repository refs.** Same-repository PRs and branch pushes lack the fork restrictions. Their workflow definitions can request token permissions and reference eligible repository or organization secrets. Set explicit workflow and job `permissions`, typically `contents: read` for checkout or `{}` when no scopes are needed. Use `persist-credentials: false` for checkouts that need no authenticated Git commands afterward. Reserve write and OIDC scopes for the jobs that need them. [Permission calculation](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#how-permissions-are-calculated-for-a-workflow-job) · [Secrets](https://docs.github.com/en/actions/concepts/security/secrets) · [Checkout](https://github.com/actions/checkout)
- **Privileged PR events.** Acclimate runs PR code on GitHub-hosted runners under `pull_request`. Keep privileged events such as `pull_request_target` and `workflow_run` out of that path. Reserve them for operations on trusted code and treat PR files and upstream outputs as data. [Secure use of pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target) · [Workflow run events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)

## Protected refs and manual releases

A workflow must exist on the default branch to receive `workflow_dispatch`. The dispatch selects a branch or tag, and the run uses that ref's workflow and commit. Repository write access allows a user to dispatch. Require an approved release ref and commit before publishing. Keep dry runs free of publishing credentials and use typed inputs to choose release behavior. [Manual workflows](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) · [Workflow selection](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows#workflow-triggers) · [Dispatch inputs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)

Enforce review and required checks on release branches. Use tag rulesets to restrict who can create, move, or delete release tags, and verify that each release tag points to a reviewed commit. Review who can bypass these rules. PR branch filters match the target branch. `github.ref_protected` only indicates that protections or rulesets are configured for the triggering ref. [Ruleset controls](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) · [PR branch filters](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#running-your-pull_request-workflow-based-on-the-head-or-base-branch-of-a-pull-request) · [GitHub context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context)

Scope deployment environments to explicit release branches or tags and use required reviewers where available. Put deployment secrets in those environments so the protection rules gate access. For OIDC publishing, restrict the provider's trust policy to the intended repository and release environment or ref. Verify these controls in GitHub and at the publisher, since the selected ref supplies the workflow YAML. [Deployment protection rules](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#deployment-protection-rules) · [OIDC trust conditions](https://docs.github.com/en/actions/reference/security/oidc#oidc-claims-used-to-define-trust-conditions-on-cloud-roles)

## Data crossing the boundary

- **Caches.** PR checks can restore eligible base-branch caches, and caches saved by a `pull_request` check are scoped to its merge ref. Keep credentials and sensitive files out of cached paths. Reserve writes to shared caches for trusted runs. Disable caching in privileged jobs or restore only dependency caches populated by trusted runs. Check cache settings in setup actions and reusable workflows as well as direct cache steps. [Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache)
- **Artifacts.** Keep PR-produced executables within PR CI. If a privileged job needs a PR report, bind the download to the expected repository, producer workflow, run ID, and source commit using GitHub metadata. Read only expected files and validate their contents before use. For releases, rebuild at the approved commit or verify provenance from an approved build. A digest checks the bytes against a recorded value. Verify the producer's identity and authority to build the release as well. [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#mitigating-the-risks-of-untrusted-code-checkout) · [Artifact downloads](https://docs.github.com/en/actions/tutorials/store-and-share-data#downloading-artifacts-during-a-workflow-run) · [Artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations)
- **Expressions.** Treat PR titles, bodies, branch names, commit messages, and manual string inputs as data. Keep them out of inline shell or JavaScript source. Pass them through step environment variables or structured action inputs, quote shell expansions, and validate values against the expected format or allowlist before using them. [Script injection guidance](https://docs.github.com/en/actions/reference/security/secure-use#good-practices-for-mitigating-script-injection-attacks) · [GitHub Script inputs](https://github.com/actions/github-script#passing-inputs-to-the-script)
