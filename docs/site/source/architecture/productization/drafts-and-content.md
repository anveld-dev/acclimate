# Durable drafts and content management

**Implemented.** Durable content routes and console authoring are connected. The exact reopened-snapshot evaluation/publication path is locally checked; see [acceptance](acceptance.md).

The console should let an operator return to a saved draft after closing the browser or restarting the service, make further changes, and publish exactly the snapshot they reviewed. A draft is a small mutable record pointing to immutable versions; it is not another copy of bundle content. This is single-operator workflow with conflict detection, not collaborative editing or filesystem synchronization.

The earlier single-file editor kept its version only in React. The current [draft workspace](https://github.com/anveld-dev/acclimate/blob/0dae127600f21ae1d456c5fce340982f34c90b40/apps/console/src/components/draft-workspace.tsx) loads durable draft records, retained generations and exact snapshots. [Versions](../../../migrations/0001_init.sql) store immutable payload bytes, parent, digest and ID; promotions and comparisons retain those identities. The navigation update opens one named draft or published view at a time.

## Storage and API

Add a `drafts` table with `id`, `project_id`, `bundle_id`, `channel`, `base_version_id`, `base_revision`, `snapshot_version_id`, `generation`, `status` (`open`, `discarded`, `published`), `created_by`, `created_at`, `updated_at`, and nullable `promotion_id`. Scope foreign keys to the bundle and channel; index open drafts by scope and update time. Both version references are scoped to the bundle; status changes never delete evidence. Draft IDs identify the working record; version IDs and digests identify exact immutable evidence. Saved snapshots are siblings under the same base, not a version ancestry chain. Draft generation orders those snapshots. Add `draft_snapshots(draft_id, generation, version_id)` with scoped foreign keys and unique draft/generation. Create/save append the exact snapshot association atomically. Publish/discard state stays on the draft and existing promotion record; no event-sourcing layer is needed. `GET /{draft}/history` exposes bounded history, so earlier sibling snapshots remain discoverable after restart. No migration should classify old orphan versions as drafts.

Under `/v1/workspaces/{workspace}/bundles/{bundle}/channels/{channel}/drafts`, expose paginated `GET` list and `GET /{draft}`. DTO: `{id, channel, baseVersionId, baseRevision, snapshotVersion: VersionMetadata, generation, status, createdAt, updatedAt, promotionId}`. Create via `POST` with `{baseVersionId, baseRevision, payload}`; save via `POST /{draft}/save` with `{expectedGeneration, payload}`; discard via `POST /{draft}/discard` with `{expectedGeneration}`; publish via `POST /{draft}/publish` with `{expectedGeneration, expectedRevision}` plus exactly one of `comparisonId` or `unevaluatedReason`. Commands use the existing [idempotency](../../../src/commands.rs) convention: same key and body replay the result; different input conflicts. Keep keys across an uncertain response and check the draft or release history before issuing a new command; the old R0 response cache remains 24 hours, while new product commands use the durable outcome contract below.

Create verifies the current channel's version and revision and atomically inserts a new immutable version parented to that base plus its draft record. Save locks the open draft, checks generation, validates and inserts a new immutable version parented to the *same base*, then advances the pointer and generation in one transaction.  Discard changes status with generation CAS, retaining snapshots. Publish locks draft and channel, checks generation, base version and base revision against the current channel, runs the shared promotion checks for either matching comparison evidence or an explicit unevaluated reason, then marks the draft published in the same transaction. The promotion references the exact snapshot; existing comparison IDs and their version/digest bindings are never rewritten. Reject stale generations and changed channels with distinct 409 codes and enough current metadata for recovery. Never silently rebase: the operator can inspect the old draft, create a new draft from the current release, and deliberately reapply changes. 

## Create the first bundle

Use one idempotent `POST /v1/workspaces/{workspace}/bundle-setups` command with `{name, origin: created|example|imported, sourceLabel?, channel, payload, reason}`. Require both `write` and `promote`. Validate the full payload, then atomically create bundle metadata, its first immutable version, channel revision 1 and an explicit unevaluated seed decision. Return `{bundle, version, resolution, promotion}`. A failure creates none of them. The user supplies the first entry or import batch; example templates are a separate explicit action. Keep the old empty-bundle creation route for SDK compatibility, with a truthful uninitialized state.

Optional `sourceLabel` is a trimmed human label of at most 120 characters/480 UTF-8 bytes, with no controls, absolute paths or URL. It never defaults to a private filesystem path. The content owner implements this transaction; the workspace and onboarding flows call it. Origin is the server-stored creation classification described in [onboarding](onboarding-and-status.md), never inferred from a filename or environment label.

## Editing and validation

The console lists open drafts in the selected workspace/channel, opens the verified snapshot by version ID and digest, and distinguishes unsaved browser edits from the last saved snapshot. It supports adding, removing, renaming and editing entries across a bundle. Renames are explicit UI operations represented as removal plus addition in the payload. Show a real line diff against the bound base, including added/deleted files and paths, with bounded rendering for large files. A saved draft remains editable; saving creates a new snapshot. Confirm navigation with unsaved text; preserve it on errors and conflicts.

From an empty workspace, the import preview builds an initial payload and calls `bundle-setups` once with `origin=imported`; no existing draft is required. For an existing bundle, import applies to an open draft. Both paths reuse the same bounded preview and validator. Import is an explicit selection of UTF-8 text files, with a preview of paths, kinds, collisions and changes. Bound file count, individual and total bytes before reading; reject traversal, binary or invalid UTF-8, duplicate/case-colliding paths and file/directory collisions. Validate the entire resulting payload before one atomic save; any error leaves both draft and snapshot unchanged. Native/CLI importers reject symlink inputs. Browser File objects cannot attest filesystem ancestry; validate their declared relative paths and bytes and never accept server filesystem paths. Do not watch or synchronize a local directory. Apply the existing payload limits and path rules in [SDK validation](../../../packages/sdk/src/cache.ts) and matching Rust validation; surface actionable errors. 

Skills are packages: `skills/<name>/SKILL.md` and supporting files move or delete together, with matching frontmatter name and description. Validate the native mapping rules in [native-files.ts](../../../packages/sdk/src/native-files.ts), including instruction count and skill name collisions, plus the selected target's stricter rules (for example Cursor's lowercase names). Provide a valid template, preview errors and test native preparation. Private mutable memory stays app-owned. Shared memory must be authorized reusable context; never include its text in logs or telemetry, and preserve explicit `approvedMemoryPaths` selection at native delivery. Editing or publishing memory does not itself approve its use.

Example: an operator opens release revision 7, edits a skill and adds a reference, then saves draft D at generation 1 with snapshot V1 parented to release R. After a restart they reopen D, edit again and save V2 at generation 2, still parented to R. V1 remains inspectable as immutable evidence. Publishing generation 2 succeeds only while revision 7 still points to R. If another release advances the channel, D remains available but publish reports the conflict; the operator creates a fresh draft and reapplies the intended changes.

A proposal evaluated for release must branch from the channel's published base. A draft snapshot can itself be an evaluated candidate when its parent is that published base. Evidence-backed release uses the draft publish command with its generation, so channel history and draft status commit together. A low-level external promotion does not silently discard or close another open draft; list it as base-changed when its base no longer matches. A new proposal based on an unpublished draft would instead have a sibling snapshot as its parent, which cannot satisfy the existing release invariant. In the first slice, block that action: finish the draft first or request a proposal from the published version. Never rewrite parents or pretend sibling versions form ancestry. See [improvement](improvement-and-evaluation.md).

## Recover uncertain writes

Today PostgreSQL retains idempotent responses for 24 hours, including across service restarts. The editor keeps its key only in React memory. Reload can lose it, and expired keys can create a second version or proposal. Generation and channel-revision checks already prevent repeating committed draft saves or publications; a conflict alone does not identify the earlier outcome.

For the first content slice, persist pending `{operationId, actorScope, resourceScope, commandKind}` in origin-private browser storage before sending. Keep exact request bytes in the active tab; do not persist content, memory or credentials for recovery. Reuse the existing idempotency key. Add compact successful command results for bundle setup and draft create/save/publish/discard, recording scoped actor, route, key, fingerprint and resulting IDs in the same transaction as the effect. Keep these associations with the retained domain records; deletion/GC is deferred.

After current authorization, look for a matching result under the existing operation lock **before** generation/revision checks. Matching bytes return the previous result; changed bytes conflict. The console must reach this replay or reconcile the stored result before rejecting on its own stale revision. `GET /v1/workspaces/{workspace}/operations/{operationId}` returns only that authorized actor's result IDs or “not observed.” This lets the browser recover a confirmed outcome after restart and response-cache expiry without storing payload copies.

A missing result is not proof of failure. Retry only the original key and bytes when available; do not automatically create a replacement command. If the body is gone and the outcome remains unknown, keep it unresolved and reconcile domain history. The first slice does not promise safe replacement of an indefinitely delayed unknown create. Defer generic abandonment, permanent tombstones and a universal all-mutation recovery protocol. Add coverage to later proposal/evaluation features only for the recovery behavior they actually promise.

Test a dropped response, browser/service restart, cache expiry and changed generation/revision. Confirm exact result discovery, no duplicate effect on replay, and no new-key retry based only on “not observed.” Recovery metadata does not prove an evaluator ran.

## Delivery order and ownership

1. Service owner: migration, scoped draft routes, transaction/CAS and idempotency tests; share DTO and error codes with console/SDK owners first. Reuse version creation and promotion logic rather than duplicating payload storage.
2. SDK owner: typed client methods, verified snapshot reads and common validation, with native plugin owners checking target compatibility. Service and SDK validation must agree on bounds and packaging.
3. Console owner: draft list/reopen, multi-entry editing, diff, import preview, conflict recovery and publish/discard flows against those contracts. Coordinate workspace/channel selection with the workspace plan; do not introduce a second selection model.
4. Integration owner: restart and browser coverage, documentation and explicit demo-data boundaries. Keep historical origin labels when reading existing workspaces.

Acceptance: close the browser with unsaved changes and they are lost after a warning; save, close or restart, and reopen the exact verified snapshot. Save twice and inspect both immutable IDs; a stale tab cannot overwrite the newer generation. Retry after a lost response without duplicate snapshots or promotions. A changed channel blocks publish even if its version later returns to the same ID, because revision also changed. Discard survives restart and cannot publish; a successful publish records the reviewed snapshot and reason once. Import rejects an oversized, invalid or colliding batch without partial changes. Add/remove/rename and skill support files appear correctly in the diff and native staging; memory is delivered only with explicit approval. 

Dependencies are existing version, channel, promotion and idempotency semantics, shared workspace selection, and consistent Rust/SDK/native validation. Automatic merge/rebase, collaborative editing, draft garbage collection, filesystem sync, hosted agent execution and migration of historical orphan versions are deferred.
