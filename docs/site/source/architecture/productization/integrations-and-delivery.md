# Integrations and delivery

**Implemented as an opt-in feature.** Give an application an opt-in identity and let it report a small set of delivery facts. A release still changes a channel; it does not prove that any application fetched or used the release. Native execution, sessions, credentials, and cleanup stay with the application.

Today `apps/console/src/server/channel.ts` reads channel resolution and promotion history, while `releases.tsx` presents release decisions. `packages/sdk/src/cache.ts` resolves and verifies bytes, and `packages/codex-plugin/src/index.ts` stages them for Codex. `examples/codex-agent.ts` connects those pieces to a real thread. None reports delivery to the service. Python has corresponding `resolve_and_cache` and `prepare_files` in `python/acclimate/delivery.py`.

## Identity and contract

Add an integration record under a project: opaque ID, user-chosen display name, bundle and allowed channel, and enabled/disabled status. It represents an application deployment, not an individual user or session. Creating it is optional; existing SDK clients continue unchanged. Issue separate revocable credentials for bundle/channel read and receipt write, bound server-side to this integration, project, bundle and channel. A pinned version must belong to the same bundle and have appeared in the allowed channel’s promotion history. An integration credential cannot fetch unpublished draft/candidate content; evaluators use separate scoped credentials. Neither credential grants publishing or integration administration. Console administrators create, rotate, and revoke credentials; show the secret only at issuance. Store only a secret verifier. Revocation blocks future service access and reporting; it cannot erase cached files or stop an already prepared session. Do not rely on the SDK's caller-supplied `scope` for authorization.

Freeze a shared receipt DTO before implementing clients: `eventId` (random idempotency ID), `connectionId`, `workspaceId`, `bundleId`, optional `channel` and `revision`, `versionId`, `digest`, `stage`, `occurredAt`, and `source` (`network`, `cache`, or `offline` where applicable). Channel and revision must appear together or both be absent; explicit-version delivery omits them. Include `resolvedAt` and `stale` with a mapping. Validate that revision against the allowed channel’s recorded version, and always match the digest to the stored version. No session ID, paths, content, prompt, memory, raw trace, output, or model token usage by default. Validate stage, sizes, timestamps and version/bundle membership; use server `receivedAt` for ordering and display client time as app-reported. Deduplicate `(connectionId, eventId)` and reject reuse with different bytes.

Use `POST /v1/workspaces/{workspace}/connections/{id}/receipts` for one receipt, and a project-authorized `GET` for recent receipts filtered by integration and bundle. Receipt credentials may only write their own integration. Integration read credentials only read their allowed content; neither integration credential authorizes console receipt/history reads. Receipt GET requires a verified browser principal with project read permission or a separately authorized operator machine grant. A single request uses one credential class; never union an integration token with console rights. Test two integrations in the same project as well as cross-project denial. Create/list/revoke integrations and issue credentials through project-admin routes. Persist integrations, credential verifiers, and append-only receipts in separate tables with tenant/project foreign keys and indexes for recent integration/version reads. Limit the cooperative SDK queue/retry age to 24 hours; expired events are dropped, never assigned new IDs. Keep the original app-reported occurrence time on retry and reject reports outside the documented age/skew bounds. Retain accepted receipts and their deduplication keys for 30 days. Use server receipt time for ordering, and mark delayed reports. These are untrusted app observations: timestamp validation handles ordinary delayed retries, not a malicious sender inventing fresh events. Deduplication ends with retention; there is no exactly-once telemetry guarantee or report-window service. Keep integration metadata until deleted and show that history is bounded.

`source` describes the origin of the selected payload throughout this report: `network`, `cache`, or explicitly permitted `offline`. `downloaded` requires network; `resolved` requires channel/revision; verified/prepared/started may refer to an explicit pinned version without a channel pair. Prepared and started inherit the verified delivery's source. Reject impossible combinations or a channel outside the credential. Receipts are separate app-reported facts; do not infer a completed delivery chain or execution ordering across unrelated events.

Stages have narrow meanings:

- **resolved**: a channel mapping was obtained or revalidated, or a cached mapping was selected under the stated policy. An explicit version has no channel resolution.
- **downloaded**: payload bytes arrived from the service in this attempt; a cache hit does not emit it.
- **verified**: exact bytes passed digest and payload validation, including when read from cache.
- **prepared**: the native plugin successfully staged the verified version for a new workspace.
- **started**: the application says it initiated a native session or turn with that preparation. This is not proof the model consumed any resource.

Add an opt-in TS delivery reporter to `resolveAndCache` for the first three stages and an explicit `reportPrepared` / `reportStarted` on a reporter bound to the selected version and integration. The app calls these after successful native preparation and its own start action; the plugin must not infer execution. Offer equivalent Python hooks around `resolve_and_cache` and `prepare_files`, with the same DTO and stage rules. Send asynchronously with a bounded queue and timeout; failures never block delivery or native execution. Reuse an event ID for retries and permit drops when offline. Disabled reporting is the default.

## Connect and evidence

Start with `examples/codex-agent.ts`: install the SDK and Codex plugin, configure service URL, project, bundle, channel, cache, integration ID and scoped credentials, then run a connect command that uses `resolveAndCache`, `prepare`, and a fresh Codex thread with `prepared.cwd`. Use `gpt-6-luna` for every live model test. A console setup test proves only that its own credential/read worked. An app connection check reports its own verified/prepared facts without a model call; label the optional native test separately.

For example, a published stable revision 12 points to v2. The app resolves it, downloads and verifies its bytes, prepares a workspace, and starts a fresh Codex thread. The console can show “App reported prepared v2, digest …, at …” and “App reported a session or turn started with v2 at …”. If it reports only verified, show that latest fact; never infer prepared or started. If nothing arrives, show “No delivery report received; status unknown.” A lost receipt, disabled reporting, offline operation, or an idle app can all explain absence. Show source, stale flag, revision, app-reported and received times, and current channel version. A cached or pinned v1 after v2 is published is a valid observed state, not automatically a failure. 

`packages/codex-plugin/QUALIFICATION.md` records a Luna marker experiment with fresh and resumed sessions. A resumed session may remember previous answers; a refreshed channel does not change an existing pinned session. Claude, Pi and Cursor mappings do not establish live model qualification. Do not claim provider compatibility beyond evidence actually collected.

## Separate qualification slices

The first local product gate uses the existing SDK credential to resolve, verify and prepare an installed bundle; it needs no new integration record or reporting infrastructure. The receipt slice is a later opt-in feature with its own identity, storage and acceptance below. Python reporting parity is required before claiming Python reporting support, not before qualifying the first TypeScript/Codex consumer.

## Delivery order and acceptance

1. Contract owner freezes identity, authorization, DTO and retention with SDK and console owners; service owner implements routes and storage with isolation, revocation and idempotency tests.
2. In parallel after the contract, TS and Python owners add opt-in stage hooks and failure-isolated reporting; native/example owner wires Codex preparation and explicit start reporting. Console owner builds integration setup and receipt views against fixtures, then connects real routes. 
3. Run offline tests for network, cache, offline and pinned selections, failed validation/preparation, duplicate receipt, denied cross-project access, revocation, queue expiry, unchanged old timestamps, duplicate reports within retention and delayed status ordering. Exercise a real service-to-SDK-to-Codex preparation flow, then the separately opted-in Luna native check. Verify that a v1 pinned session remains v1 after v2 promotion and that missing receipts remain unknown.

Acceptance: an authorized app can connect and report the exact version and stages it observed; another integration cannot read or write its receipts; reporting outages do not change delivery; the console uses the evidence wording above. Defer dashboards, aggregation, alerts, raw traces, mandatory call mediation, cross-provider qualification, and claims of model consumption.

## Credential retry behavior

Integration creation uses the normal idempotent mutation transaction. Credential issuance stores only the verifier and issuing operation identity. An identical retry returns `credential_already_issued` with the credential ID, never another secret or a second credential. The authorized integration list exposes IDs/kinds/revocation times for recovery; revoke an unknown/lost secret before replacing it. Secrets are not cached in replay responses.
