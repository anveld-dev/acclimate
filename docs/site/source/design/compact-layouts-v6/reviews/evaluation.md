## Initial findings before desktop clarification

The existing review has sound evidence distinctions, but reading them together is costly. `ComparisonEvidence` in `apps/console/src/components/improvement-workspace.tsx` renders a semantic three-column Table with a 32rem minimum width. Its contained overflow prevents a page-wide layout failure; it does not make the Candidate column visible alongside Parent on a phone. The v5 release review explicitly observed Candidate beginning offscreen. v6 should make both sides of each `(caseId, repetition)` readable in one narrow reading sequence, while retaining every expected row and every unexpected returned row. A stacked pair inside the same evidence section is a plausible small-screen composition of existing Table/Disclosure primitives; a missing-row filter, winner-only view, or summary-only phone view is not equivalent.

`apps/console/src/lib/comparison-summary.ts` is the client consumer. It uses `JSON.stringify([caseId, repetition])` to match expected tuples, renders absent expected pairs, then appends unexpected reported tuples. A pair is scored only when both outcomes have `gradingStatus === 'scored'` and non-null rewards. Zero reward is valid. Each absent/unscored/null-reward outcome contributes a missing grade. Execution status is a separate count. Total cost is unknown if any displayed outcome lacks reported cost; reported zero cost is known. These rules must survive any density change. The similarly named server helper is not imported by the review component; do not substitute its result-count-based logic for this tuple inventory.

The selected evidence summary shows short candidate/request references, binding/attempt, dataset and grader, but full snapshot identity and the diff live in separate disclosures after request results when requests exist. Runtime, full comparison provenance and raw comparison live further down in comparison lookup. This is an optional context-cost improvement, not demonstrated user misassociation or a release-safety defect: the saved generation/title and full snapshot disclosure already provide continuity. A compact identity bridge near the selected evidence could lower the cost, with full IDs still inspectable/copyable in place. Do not add identity tooltips as the sole source of a decision fact. The final publication dialog already displays full parent, candidate/generation and selected comparison IDs; its binding should remain explicit.

Request status is a report from an external app. Requested means ready to run there; running means last reported running. A completed request with a comparison offers Inspect evidence; it is not an approval. Complete inventory is not a win, statistical proof, or release approval. There is no source-backed aggregate quality delta, confidence interval, automatic promotion threshold, or console-hosted execution to introduce into the concepts.

The local shadcn-backed Disclosure is intentionally force-mounted and hidden when closed. It preserves local reason/configuration edits across open/close. Use this component and the existing Button, Table, Dialog, Input, Textarea and copy controls rather than replacing forms with ephemeral popovers. First-request setup intentionally remounts/collapses after the first request; that transition must not be confused with accidental data loss.
