# Interaction and accessibility review

**Final verdict:** retain the baseline. The tested C/D workbenches do not improve the whole interaction enough to earn replacing it. No application change or further concept round is warranted by this evidence; this is not a claim that every possible sidebar or unified rail must fail.

My independent first ranking, saved after all six images and before peer discussion, was **baseline > A > C > B > E > D > F**. I also inspected the current editor, focused workspace tooltip and account-dialog breakpoint evidence, read Shell’s focus ownership and the state inventory, and reviewed the actual experiments.

A preserves the existing task boundaries most closely, but a new workspace chooser adds behavior for an unmeasured gain. C’s labelled sidebar has clearer global recognition than B’s compressed icon/label rail; both spend source width for header height. E hides direct global destinations in a workspace popup and relies on short identities fitting one line. D makes scope and files compete vertically. F adds an opening action to frequent file selection and covers source. Mock dimensions, fictional entry/admin actions and hover-only critical identities are not implementation requirements.

Debate with all five peers was substantive. The visual reviewer initially preferred C; the library reviewer preferred D. D’s width rebuttal was valid: a 256px combined rail replaces a 216px file pane rather than adding a third column. I supported actual testing of that promising height/width trade, including long scope, 24 files, repeated selection, short/coarse viewports, incomplete evidence and full diff. Prior baseline acceptance was not treated as a sufficient answer.

The actual C experiment loses 180px of source width at 1440px. Its source begins 49px earlier, but recorded visible height improves only 7px under the experiment’s footer-reservation policy. The 1024px coarse stress case loses width and height. Those numbers are not architectural ceilings or a mandatory shipping breakpoint; they simply do not demonstrate a compensating workflow gain here.

D gains real source height, but file finding loses. Even the fairness supplement, restoring the baseline’s one-line workspace name and existing full-identity tooltip, leaves a 160px file region at 1440×900 against 273px for heading/search/type and three rows. No full row is initially visible. At 1440×700 the file region remains zero-height, scope overlaps global navigation, and real Search/type clicks time out. The 900px Search is genuinely painted and clickable; the earlier ancestor-clipping detector was wrong about that. The rejection rests on the visible file budget and short-viewport task failures, not that detector or a blanket objection to file-list scrolling.

I inspected the main 36-capture experiment, sensitivity pixels, corrected menu/import proof, incomplete paired evidence and expanded diff. The clean six-case narrow supplement verifies the named inline Files picker stays outside the global sheet at coarse 390px and actual Chrome 200%, selection returns focus, and sheet Escape retains the correct focus. Shared earlier selector/measurement errors are harness diagnostics, not baseline product regressions.

The production hash remains `0f5464d8…`; application controls, data and persisted state remain unchanged. These are labelled CSS geometry experiments, not qualification of a shipped alternative. Existing menu, tooltip, disclosure, dialog, validation, pending/recovery and focus boundaries retain their prior foundation. Rare unrendered branches remain source-reviewed; no new broad assistive-technology, OS-popup, provider or model-quality claim is made.
