# Skeptical product review

Initial audit covers all eight actual desktop11 pages and shared shell/source. Current hierarchy separates workspace administration, bundle/channel routes, draft/review operations and file actions. Ordinary editor source starts at y=197 with broad working width. That is evidence to beat, not a reason to freeze the layout. Permanent navigation rails must earn their width and keep parent navigation distinct from file navigation. Sparse records do not justify filler, while one uniform content cap would ignore the different reading/editor/evidence tasks.

## Independent ranking before peer debate

I viewed all six actual images. Ranking of complete product directions: **baseline, A, B, D, C, E, F**. This ranks scope clarity and ordinary repeated work, not illustrated editor heights or inset metrics.

- **Baseline:** Best proven balance of durable workspace/bundle/channel orientation, early frequent file navigation and broad source/evidence width. Its repeated horizontal scopes cost height; that cost is real.
- **A:** Closest challenger. Moving infrequent New workspace into a chooser could reduce header crowding without losing editor width. A searchable custom chooser adds interaction/state cost, and ordinary source geometry is essentially unchanged. It must demonstrate a meaningful narrow/long-identity gain to beat baseline.
- **B:** Most plausible vertical-space challenger. A genuinely narrow global rail could exchange modest width for source height while retaining early files and separate parent scope. Generated labels exceed its claimed 64px rail; icon-only navigation would require reliable focus/hover naming. Its metric inset is not proof.
- **D:** More interesting than a second full sidebar: one contextual rail could reclaim both headers for only modest width beyond the file rail. But parent navigation pushes files substantially down, and workspace actions compete with bundle/file groups. Real long names, many files and short-height reflow must establish whether that grouping works.
- **C:** Durable labelled workspace orientation earns something, but a second 180px rail spends too much source and paired-evidence width for the gained header height. Wide administration pages benefit less than the editor pays.
- **E:** One bar is attractive in the short-name sketch. It mixes global and bundle scope, hides all workspace destinations, and must revert to two rows under realistic width. Its generation-height win is not established for long identities. Invented admin links do not strengthen the product case.
- **F:** Reopening a finder for frequent file changes loses persistent context and overlays source. Extra source width has no demonstrated task value here.

All concepts invent some actions, paths, truncation policies or UI facts. Those details are excluded from this ranking.

## Debate and unresolved challenger

There is substantive disagreement. Library independently ranks D first; editor places E above the global rails; review initially ranks D last; interaction favors baseline and labelled C over B. My ranking remains recorded above. Library's D argument changed my view: its 256px rail replaces the 216px explorer, so ordinary source loses about 40px, not another full sidebar. A review page without Files can retain roughly 1184px beside that rail at 1440px, close to baseline's 1200px bound. Width alone cannot reject D.

I requested an isolated reversible actual D prototype rather than adoption from the mock. A useful falsifier is matched long-scope/24-file/short-height work at 1440px and 1024px/coarse pointer: find files 3 and 20, search/filter/Add, navigate Members and Back to changes without repetitive drawer reopening or source occlusion. Also inspect a fully loaded incomplete comparison, full diff and decision dialog. Files below parent navigation, shared rail/footer scrolling and narrow frequent file access remain real costs to measure.

## Actual result

I recommend retaining baseline production after inspecting the matched baseline/C/D source and incomplete-evidence screenshots, corrected visibility evidence, one-line-workspace sensitivity and native 200% inline-files state. D's promise was real: at 1440×900 its source is 1134×738 versus baseline 1182×648, roughly 9.3% more area. Its paired review facts remain readable. But the tested allocation leaves 108px for Files versus 273px needed for its heading/search/type/first three rows. At 700px height it leaves none and actual Search/type clicks fail. Giving workspace identity the same one-line treatment as baseline improves the 900px file budget to 160px, still insufficient; short-height access still fails. That is a frequent-work regression, outweighing extra source height in this implementation.

C gives clear labelled orientation, but measured source width falls to 1002px for only 655px visible height versus baseline's 1182×648. Its review retains facts; the ordinary editor trade does not earn a global migration. Corrected narrow checks pass for all three with inline Files outside the global sheet. Shared menu/utility harness errors and the original fixed-rail clip-detector error are not product failures or reasons to prefer baseline.

These are isolated CSS/style-variable experiments on unchanged build `0f5464d8…`, not shipping qualification. Their sizing and fixed-rail allocation are not architectural ceilings; a future contextual rail could solve the measured constraint. My decision rejects these tested alternatives, not all sidebar designs. Independent rankings and disagreements above remain visible. No production edit, further broad image round or redundant baseline test run is warranted by this evidence.
