# Access and delivery handoff review

I inspected all six A–F concepts, actual desktop8 App setup/Connections/Members pages, and `sdk-setup`, `workspace-connections` and `workspace-members` source. I debated the alternatives with library, editor, interaction, visual and skeptic reviewers.

**Support A’s bounded sequence, F’s identity/role adjacency and conditional C selected-connection layout.** A keeps install → private access → delivery check in order; its aligned five environment definitions are easier to scan. B repeats scope, variables and credential navigation in a permanent reference column without earning the width. Copy recipe must remain clearly associated with the complete recipe, rather than imply it copies the nearby invocation alone. Preserve both language branches, the admin-only bundle/channel-scoped credential link and the nonadmin ask-admin branch. No setup step is evidence of completion or connection.

C has a stronger case than the rejected v8 library master/detail: the existing URL-selected connection already has a substantial credential, recovery and receipt task. A wide directory beside that task can preserve context while avoiding scrolling past every connection. Keep a bounded directory alone before selection, normal links and current-page state; stack at narrower widths and native zoom. D is the fallback if C compresses real receipt/ID facts. No fixed side pane, nested scrolling or invented selection workflow is justified.

F suits the actual member action: identify a person, then manage their role. Keep the source subject and role adjacent, with full issuer below and Manage nearby. E separates role from identity for a distribution-comparison task the product does not need. Both generated dialogs are rejected: retain the real lookup, internal user ID distinct from issuer/subject, explicit identity-confirmation checkbox, unchanged-role disabled Save, removal disclosure and last-administrator guards. A generated “Verified” badge cannot replace that action boundary.

Reject C/D’s literal switches and masked-token rows. Revocation is a deliberate scoped action, not a reversible access toggle. Issued credential metadata does not make its one-time secret recoverable. Enabled/Revoked describes access; app-reported receipts remain independent observations, with unknown status when none exist and no inference of model consumption. Keep read credentials distinct from optional reporting credentials, exact target facts in revoke confirmation, and recovery restrictions beside the affected credential action.
