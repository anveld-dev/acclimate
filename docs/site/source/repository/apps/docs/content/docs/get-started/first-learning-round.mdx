This page takes the local stack to its first learning round, in which the service improves a bundle and releases the result. It is for someone evaluating the [learning loop](/docs/concepts/how-it-works#learning-loop) on a laptop.

You need the stack from the [Quickstart](/docs/get-started/quickstart) running, and a Codex sign-in for the model proxy.

Learning needs two model settings, and neither has a default:

- **The optimizer** proposes and selects changes to the bundle. You set it on the service, in the shell before `npm run local:up`.
- **The model provider** serves the task model, which answers tasks, and the judge model, which grades them. You set it in the console.

## Set up a local model proxy

These steps use [CLIProxyAPI](https://help.router-for.me/) with a Codex sign-in for both settings. Use a fixed build of the proxy. The steps were checked against the revision that the example configuration link points to. The [operator guide](https://github.com/anveld-dev/acclimate/blob/main/deploy/README.md#cliproxyapi-with-codex-sign-in) has the details.

1. In the proxy's configuration file, set `server.port` to `8317`, put a private key of your choice under `access.api-keys` and set `routing.cooldown.disable-cooling: true`. With one Codex sign-in, cooling would block a model for minutes after one rate-limited reply. The [example configuration](https://github.com/router-for-me/CLIProxyAPI/blob/f5c5681a8361c9da53e93c60b6507816eee7468b/config.example.yaml) shows where each setting goes.

2. Sign in, then start the proxy.

   ```sh
   cli-proxy-api -config /private/config.yaml -codex-login
   cli-proxy-api -config /private/config.yaml
   ```

3. Check which model IDs the proxy serves. On Linux, use the address the proxy listens on, as the warning below explains.

   ```sh
   curl -H "Authorization: Bearer <proxy-key>" http://127.0.0.1:8317/v1/models
   ```

4. Start the stack with the optimizer settings and the provider allowlist.

   ```sh
   export ACCLIMATE_MODEL_ENDPOINT=http://host.docker.internal:8317/v1/chat/completions
   export ACCLIMATE_MODEL_TOKEN='<proxy-key>'
   export ACCLIMATE_MODEL=gpt-6.2-astra
   export ACCLIMATE_MODEL_REASONING_EFFORT=high
   export ACCLIMATE_PROVIDER_HTTP_HOSTS=host.docker.internal
   npm run local:up
   ```

   The model IDs on this page are examples. Use IDs from step 3. The containers reach the proxy at `host.docker.internal` over plain HTTP. The service and the executor refuse that unless the host is listed in `ACCLIMATE_PROVIDER_HTTP_HOSTS`.

   The stack saves these settings in `.local/stack/service.env` and reuses them on later starts. Export an empty value to clear one.

5. In the console, open the workspace's **Members** page and, under **Model provider**, enter:

   | Field | Value |
   | --- | --- |
   | OpenAI-compatible base URL | `http://host.docker.internal:8317/v1` |
   | API key | The proxy key, the same value as `ACCLIMATE_MODEL_TOKEN` |
   | Allowed models | At least two IDs from `/v1/models`, one for tasks and one for the judge |

   The executor verifies each model. `local:up` has already set the provider encryption key that the service needs to store the API key.

The two URLs differ. `ACCLIMATE_MODEL_ENDPOINT` is the full `…/v1/chat/completions` URL, because the service posts to it as written. The provider's base URL is the `…/v1` base, and the executor adds the path.

<Callout type="warn" title="Linux">
On Docker Desktop, `host.docker.internal` reaches your laptop's loopback, so a proxy on `127.0.0.1` works. On Linux, `host.docker.internal` is the Docker bridge address, such as `172.17.0.1`, and a proxy bound to `127.0.0.1` is unreachable from the containers. Set the proxy's `server.host` to the bridge address. Binding it to all interfaces also works, but exposes the proxy to your network.
</Callout>

## Run the ticket triage example

`examples/ticket-triage/` teaches an agent to route support tickets to the right queue. One script publishes the bundle, turns on learning, imports 64 labelled tickets, starts the loop and reports each round.

1. Issue a machine token. On the workspace's **Members** page, under **Machine tokens**, choose **Issue token** and tick **Read content**, **Write content** and **Promote releases**. The script needs all three [rights](/docs/concepts/credentials#rights).

2. In a shell at the root of the checkout, load the stack's settings and export the token and two of the provider's allowed models. Then run the script.

   ```sh
   npm ci --ignore-scripts
   source .local/stack/env.sh
   export ACCLIMATE_TOKEN='<machine-token>'
   export TASK_MODEL=gpt-6-luna JUDGE_MODEL=gpt-6.2-sol
   npx tsx examples/ticket-triage/loop.ts
   ```

The script prints each step, then one line for each finished round. In the measured run, round 1 took 14 minutes and ended with this line:

```text
Round 1 adopted and released version ba6a0ffc-33c7-4d04-a93b-3bfa2690f90e. Evolve tasks: 0% before, 100% for the adopted version. Held-out tasks: 100%.
```

The starting instructions do not name the queues, so they passed none of the evolve tasks, which the loop learns from. The adopted version passed all of them, and every held-out task, which the optimizer never sees.

Learning runs on the service, so you can stop the script with Ctrl-C after the first adoption. The bundle's **Learning** tab in the console shows the same rounds. If the proxy answers with rate limits, lower the [executor concurrency](/docs/get-started/run-locally#executor-concurrency).
