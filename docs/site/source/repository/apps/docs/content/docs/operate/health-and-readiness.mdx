This page is for the operator of a self-hosted deployment. Use the probes for monitoring and during an incident. Run the two checks at the end after every deployment and upgrade, through the same HTTPS endpoints your users and applications use.

## Probe the stack

Run these from the checkout with your deployment settings loaded. Replace the variables with your hostnames if you run them elsewhere.

```sh
docker compose ps
curl -fsS "https://$API_HOST/health"
curl -fsS "https://$API_HOST/ready"
curl -fsS -o /dev/null -w '%{http_code}\n' "https://$CONSOLE_HOST/ready"
```

In a healthy deployment, `docker compose ps` shows every container as `healthy`. The three requests return `ok`, `{"ready":true}` and `200`.

| Probe | What it checks |
| --- | --- |
| API `GET /health` | The service process is running. |
| API `GET /ready` | The database answers, this process is the only service using the database, its background worker is running and it is not shutting down. |
| Console `GET /ready` | The console's configuration is valid and the service is ready. |
| Caddy container health | The proxy process is running with its configuration loaded. |
| Executor container health | The service has answered the executor in the last 120 seconds. See [Check the executor](/docs/operate/enable-learning#check-the-executor). |

An API that is not ready returns HTTP 503 with `{"ready":false}`. A ready service does not show that learning rounds are progressing or that a model provider is reachable. The console's `/ready` does not contact Keycloak on each probe. Caddy starts only after both the service and the console are healthy.

If `/ready` stays unavailable during normal operation, read the service log. Check that the database is reachable, that its migrations completed and that no second service process uses the same database.

```sh
docker compose logs --tail 100 service
```

When the service receives SIGTERM, it stops reporting ready first. It then finishes open requests and work and releases its hold on the database. Compose gives the service, the console, the databases and Caddy 90 seconds each to stop.

For a list of symptoms with their causes and fixes, see [Troubleshooting](/docs/operate/troubleshooting).

## Read exit codes

Compose restarts a container that exits. While it does, the status column of `docker compose ps` shows the exit code, and the container's log ends with the error.

| Container | Exit code | Meaning | What to do |
| --- | --- | --- | --- |
| `service` | 75 | The service lost its exclusive hold on the database. | Make sure only one service process runs against the database. |
| `service` | 1 | Any other error, such as invalid configuration or a failed migration. A failed migration stops the service before it listens. | Read `docker compose logs service`. |
| `acclimate-executor` | 78 | The executor's configuration cannot work: its credential, the runner image or the sandbox runtime is wrong. Restarting does not help. | Follow [Check the executor](/docs/operate/enable-learning#check-the-executor). |

## Verify API access and sign-in

The repository includes two checks for a live deployment. Its own tests run against test certificates and a test issuer only, so run both checks against your deployment before you send it traffic.

Both checks run from a checkout of the repository with Python 3. Each prints a JSON result and exits with a nonzero status unless the check passed. The optional `--output` flag also writes the result to a file, which must not exist yet. Choose a path in a private directory.

### Check API access

You need a [machine token](/docs/concepts/credentials#credential-types) with the read right for one workspace. Put it in an environment variable and pass the variable's name, so the token never appears in the command.

```sh
python3 scripts/productization/external.py --execute --gate https \
  --url https://api.example.com --workspace <workspace-id> --token-env ACCLIMATE_CHECK_TOKEN \
  --output /absolute/private/https-check.json
```

The check verifies the API's certificate and hostname, requests `/health` and `/ready`, then lists the workspace's bundles with the token.

### Check sign-in

You need:

- Playwright for Python with its Chromium browser installed
- a machine with a display, because the check opens a browser window
- a test account in your Keycloak realm

Pass the public console URL and the exact Keycloak issuer. For the co-hosted Keycloak, the issuer is `https://<keycloak-host>/realms/acclimate`.

```sh
python3 scripts/productization/external.py --execute --gate oidc --interactive \
  --url https://console.example.com --issuer https://auth.example.com/realms/acclimate \
  --output /absolute/private/oidc-check.json
```

When the browser opens, sign in with the test account within three minutes. The check confirms that the console sends you to your issuer and that sign-in returns to the console. It then checks that the session cookie is secure and that signing out clears it. The browser session is discarded afterwards.

Neither check shows that learning works. The repository's guide lists the other checks under [What has been tested](https://github.com/anveld-dev/acclimate/blob/main/deploy/README.md#what-has-been-tested).
