# Production acceptance and fixture migration input

Planning only; repository inspection on 2026-11-14. No application changes, services, tests, browser sessions or model calls were run. No applicable `AGENTS.md` was found in the workspace or its ancestor directories.

## Current evidence and gaps

- Static inspection of `scripts/bdd/inventory.json` confirms **141 behavior IDs / 183 variants**: service 64/88, browser 49/60, SDK 22/26, identity 5/8, runtime 1/1. `scripts/bdd/run.py` compares stories with the reviewed inventory; `coverage.py` requires every variant to pass for full coverage. Preserve that mechanism and stable IDs. A partial lane must continue to report uncovered behaviors.
- `scripts/bdd/world.py` starts the real Rust binary against `Harness`'s private PostgreSQL cluster. Most scenarios use explicit machine grants. `@hosted` scenarios configure separate login/console authority and an operator allowlist, but `sign_in()` submits issuer/subject directly to `/v1/auth/sessions`.
- `scripts/bdd/browser.py` selects local mode unless `world.sessions` exists. Hosted scenarios inject the session cookie with `context.add_cookies()`. Thus the 60 browser variants do not establish working production sign-in; most also bypass membership-based console authority.
- `scripts/bdd/identity_consumer.mjs` invokes the real identity handler and Rust authority, but imports `createIdentityHandler()` with an injected provider. It synthesizes callbacks and provider claims. It does not run a browser redirect, discovery, token exchange or JWT verification. `apps/console/tests/identity.test.ts` provides useful handler security tests and an invalid-token/state SDK check, but no successful signed-token integration.
- The current real handler in `apps/console/src/server/identity.ts` already uses `openid-client` discovery, authorization code + S256 PKCE, state, nonce, bounded single-use process-local transactions, separate authority tokens, and Secure/HttpOnly/SameSite=Lax cookies. It requires HTTPS origin and issuer. Keep these production properties when removing mode branches.
- `scripts/productization/hosted_authority.py` explicitly checks only the Rust trusted-adapter seam. `external.py --gate oidc` separately observes an HTTPS real-provider redirect/callback and cookie/logout. These establish different claims; a fixture issuer must never satisfy the external gate.
- `qualify.py`, `full_roadmap.py`, `rust_tests.py` and BDD share `Harness`. `local_recovery.py` / `local-recovery-fixture.mjs` launch a local console with a machine credential. Removing local launcher/operator code therefore requires migrating these consumers, not deleting their product assertions.
- `.github/workflows/ci.yaml` runs the complete BDD suite and one Vite draft scenario, alongside Rust/private-PG, package, console and qualification checks. It currently also runs `test:operator` and uploads `installable-local-release`; both require a deliberate production replacement or retirement with assertions mapped elsewhere.

## Target fixture boundary

The product has one production authentication path and PostgreSQL persistence. A disposable test deployment is that same product with test-owned configuration and external dependency fixtures; it is not an application mode or fallback.

Create a test-owned issuer under `scripts/bdd/fixtures/` with discovery, authorization, token and JWKS endpoints. Generate signing keys and client credentials per test run, implement one-use codes bound to redirect URI/client/PKCE, and issue signed tokens containing issuer, audience, subject, nonce and expiry. Test controls select disposable identities and malformed responses inside the fixture only. No app import of this issuer, automatic issuer startup, trusted-header shortcut, mock-claims flag, default user or preissued-cookie path.

Preferred browser arrangement: test-owned HTTPS reverse proxy for the issuer and built console, with a generated CA/certificate trusted only by fixture child processes and browser context. Keep production cookie flags and default `openid-client` configuration. The actual console `/auth/login` route must initiate navigation, actual discovery/token/JWKS requests must reach the issuer, and `/auth/callback` must mint a real Rust session before the browser opens protected UI. Trust the temporary CA in the test Node process; do not globally disable TLS validation. An HTTP upstream behind that proxy is internal transport, not an HTTP browser callback.

If focused protocol tests use loopback HTTP callbacks or `openid-client`'s insecure-request facility, that configuration must be constructed by test code through an explicit dependency seam. It cannot be read from production environment, compiled into a fallback, or cited as evidence for HTTPS/Secure-cookie behavior. The full browser acceptance lane must use HTTPS. This avoids a second production protocol policy solely to ease tests.

Keep the transaction map process-local and bounded. A restart may invalidate pending logins and require retry, while established Rust sessions and workspace state retain their documented PostgreSQL behavior. No distributed session store, auth cluster or new identity platform is needed.

## Acceptance gates

1. **Behavior preservation:** run all BDD lanes on production configuration against owned PG. Every original ID and all 183 original variants remain mapped and pass; added behavior variants receive deliberate inventory review. No blanket snapshots, skipped security stories or coverage-count-only substitutes. Keep the focused Vite scenario in addition to the built-console lane.
2. **Browser identity:** prove the actual built console completes issuer redirect, code exchange, signature/issuer/audience/nonce/state/PKCE validation, callback, session cookie and protected page load against real Rust/PG. Reject replay, missing/wrong browser binding, expired flow/code/token, invalid signature, wrong issuer/audience/nonce and provider failure without issuing a session. Keep unit-level deterministic-clock tests for expiry rather than long sleeps.
3. **Human authorization:** unauthenticated console transport denied; configured operator bootstrap only; first visitor gets no operator authority; viewer/editor/admin behavior, unknown-user handling, final administrator protection, membership downgrade/removal and workspace separation enforced by Rust with unchanged cookies. Browser logout revokes the server session; cross-origin logout is denied; stale-cookie login renews the same verified person. Invalid/expired/revoked sessions never fall back to machine console privilege.
4. **Production configuration:** missing or malformed identity settings fail closed; no local/default mode bypass; login and console authority remain distinct from SDK grants. HTTPS callback and Secure/HttpOnly/SameSite session cookies remain enforced. No default test issuer, demo account, magic headers or app-hosted fixture route. Browser responses, generated recipes and build artifacts expose no authority/client secrets.
5. **Persistence and workers:** preserve publication, draft generation/revision conflicts, exact snapshots, lost-response reconciliation, receipt retries, owned evaluator evidence and PostgreSQL restart recovery. Run complete Rust tests with explicit private database variables so database tests do not silently return without exercising assertions. Run existing SDK/Python/package install checks with explicit scoped credentials and no browser identity.
6. **Qualification honesty:** fixture acceptance reports say “production path with a test-owned issuer,” never “live provider qualified.” Preserve separate opt-in external HTTPS/OIDC, backup, container and native-provider gates where applicable. No provider credentials or paid-model execution enters default CI. Model-free provider fixtures and deterministic evaluation remain clearly labeled; a fixture cannot qualify model quality or external interoperability.
7. **Isolation and cleanup:** all databases, ports, CA material, client secrets, session cookies and grants belong to the run. Use a minimal inherited environment or explicitly strip ambient `DATABASE_URL`, all PG connection variables, `ACCLIMATE_*`, `CONSOLE_*`, provider credentials and user-state paths before constructing fixture values. Current `Harness` strips only `DATABASE_URL`/`ACCLIMATE_*`; strengthen that shared boundary without changing toolchain resolution. Never read dotenv, existing local state, user databases or credential stores. Test cleanup on failed startup and interruption; redact tokens from reports/traces and retain private artifact permissions.

Default CI can establish production code-path correctness with these fixtures. External provider interoperability, deployed TLS configuration and real model/native-agent behavior remain separate evidence, acquired only by their explicitly authorized qualification runs.
