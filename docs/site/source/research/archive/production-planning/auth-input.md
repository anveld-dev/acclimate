# Production-only authentication planning input

Planning only, based on the repository on 2026-11-14. No runtime changes, commands against a database, tests, browser work, provider calls, or user configuration/secret reads. No applicable repository or ancestor `AGENTS.md` was found. PostgreSQL is already the SQLx backend (`Cargo.toml:12`); this work does not require a database-engine migration.

## Recommended boundary

Keep the existing division: the console server is the OIDC relying party, Rust is authoritative for browser sessions, workspace membership, operator capability, and authorization. Require this path for every browser request that reads or changes application data. Delete local-operator mode and its default behavior, rather than renaming it or keeping a development bypass.

OIDC proves an exact `(issuer, subject)` identity. It does not grant workspace access. A signed-in person with no memberships gets an account and an empty-workspace screen. Only an explicitly configured operator pair may create a workspace, and that operation gives its creator the new workspace's initial admin membership. An operator does not become an administrator of every existing workspace. Viewer/editor/admin retain their current meanings; machine credentials retain explicit project/right scope and cannot manage memberships or create browser identities.

Retaining console-side OIDC verification is the smallest coherent change. It means Rust deliberately trusts a narrowly scoped login authority, rather than independently verifying OIDC tokens. The dedicated login secret authorizes an identity assertion, so compromise of it or the console server can impersonate users. That trust must be explicit in deployment documentation. Moving the relying party into Rust is a separate architecture choice, not needed for this change.

## Sessions and preserved data

Keep `users` keyed by `(issuer, subject)`, project IDs, memberships, bundles, audit records and integration credentials. `migrations/0006_workspaces.sql` already contains the necessary basic tables and role constraint. Preserve session-secret hashing and database expiry/revocation. Eight-hour absolute lifetime is an adequate initial explicit policy; do not add silent refresh or a provider refresh-token store as incidental scope.

Successful login must issue a new secret and revoke the valid session being replaced, including account switching. Current rotation in `src/workspaces.rs:235` revokes the supplied prior secret only when it belongs to the newly authenticated user; switching accounts therefore leaves the old server session live. Logout must retain its current behavior of waiting for confirmed revocation before clearing the cookie on service failure. Expiry/revocation must deny reads, mutations and durable-operation receipt/replay access, including a stale cookie presented with a valid transport credential. Define bounded expired/revoked-session cleanup without deleting users or application data. Document that provider logout/account disable does not currently revoke Rust sessions; application logout/expiry does. Immediate provider-driven logout/revocation is outside the minimum contract unless explicitly added.

There is no safe automatic membership conversion from local machine grants. Grant principal strings are not verified OIDC identities. Existing backfilled workspaces may have no human admin (`backfill_projects` creates only project rows), and workspace-creation capability cannot administer those rows. Before cutover, require an explicit, auditable bootstrap/adoption procedure assigning an exact existing workspace to an exact verified user after OIDC login. It must be idempotent and preserve existing admins, rather than globally promoting the operator or making the first login an admin. Choose the narrow offline administrative procedure versus a deliberately authorized bootstrap command during review; do not leave this as an undocumented database edit or silently seed membership on startup.

Existing session rows do not record verification provenance. Decide whether to revoke pre-cutover browser sessions and require fresh OIDC login; this can preserve all user/membership/business records. Do not claim existing sessions were cryptographically verified solely because they exist in PostgreSQL.

## Deployment prerequisites and real limits

The deployer must supply an OIDC application with registered exact HTTPS callback `/auth/callback`, issuer, client ID/secret, stable exact operator issuer/subject pairs, public console origin, explicit service address, separate high-entropy login/console/machine credentials, PostgreSQL connectivity, and a concrete initial workspace-adoption mapping where existing projects lack admins. These are external deployment inputs; planning must not fabricate identities, secrets or a provider. Local development runs the same browser authentication path with HTTPS and a real issuer, or explicitly test-only issuer fixtures isolated to tests. Production configuration must never select injected fake identity providers or fixtures.

The service currently serves plain HTTP through `axum::serve`; console Vite config binds loopback. Production needs TLS termination and a defined trusted-proxy boundary. The proxy must strip/replace forwarding headers, preserve/reconstruct the configured public origin correctly and block direct untrusted access to the backend listener. Do not accept arbitrary `Forwarded`/`X-Forwarded-*` claims. Internal console→Rust HTTP is acceptable only on an intentionally protected loopback/private boundary; otherwise use TLS there too. Validate supported deployment configuration at startup and verify TLS/header behavior in deployment acceptance checks. Setting Secure cookies does not itself create TLS or establish proxy trust.

One Rust process owns the proposal queue via PostgreSQL advisory lock (`src/main.rs:50`); a second service process exits. OIDC transactions are a bounded, five-minute, single-use process-local map (`identity.ts:112`): console restart loses pending logins, and callbacks must reach that same console process. Keep the initial deployment explicitly one Rust process and one console process. Database-backed sessions survive process restart, but that does not make this a multi-replica architecture. Do not invent leader election, distributed login storage, enterprise IAM, tenant federation or an OIDC provider implementation here.

## Review and acceptance evidence to request later

Existing tests provide useful starting contracts: `apps/console/tests/identity.test.ts` covers PKCE/state/nonce/token rejection, replay, cookie binding, expiry and logout failures; `tests/workspace_access.rs` covers session/membership revocation; access/setup/navigation/channel tests expose local-mode expectations that must be replaced, not merely dropped. Implementation should demonstrate: omitted/legacy mode and incomplete config fail startup; anonymous browser data calls never use machine grants; each credential class is rejected at the other authority boundaries; spoofed trusted headers and mixed credentials fail; viewer/editor/admin and operator creation stay distinct; final-admin/concurrent revocation checks remain transactional; account-switch rotation revokes the old session; existing workspace adoption is explicit; direct fetch and SDK-backed console calls share the same required-session behavior. Use isolated provider fixtures only in tests and a deployment-level HTTPS/proxy acceptance check. No tests were run for this planning input.
