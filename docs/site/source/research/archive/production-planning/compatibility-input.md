# Production-only compatibility input

Planning audit, 2026-11-14. Source inspection only: no application changes, runtime/database access, private configuration reads, tests, browser actions, or model calls. No applicable `AGENTS.md` was found in the checkout or its ancestor directories. Paths and line numbers below describe the current checkout.

## Recommended boundary

Remove the browser's implicit local operator identity and the launcher/configuration paths that supply it. Preserve the application's programmatic service identities, PostgreSQL records, immutable content and evaluation ownership. A machine bearer token is an intentional app API credential; it is not evidence that a browser user is signed in.

## Existing data and workspace ownership

The local launcher already uses PostgreSQL. `scripts/dev-console.ts:23` derives a database name from checkout path, fixes project ID to `local-demo`, and provisions separate seed, console and evaluator principals (`:174`). `--example` creates ordinary stored content with origin `example`; its private `seedKey` prevents duplicate setup (`:214`). Removing local operation is an access/configuration transition, not a SQLite-to-PostgreSQL migration.

`migrations/0006_workspaces.sql:1` backfills projects from bundles and creates users, sessions and memberships without assigning any owner. `src/workspaces.rs:30` also creates project rows from machine grants. Neither path creates browser admins. Existing project creation inserts a new project and the operator's admin membership atomically (`src/workspaces.rs:305`); it cannot claim an existing project. Membership management requires an existing browser admin (`:377`). Therefore simply requiring sign-in leaves seeded/local projects inaccessible in the console even though their content and machine APIs remain intact.

Recommended new contract: a narrow, explicit adoption action for an existing project with **no memberships**, authenticated by a valid browser session whose stable `(issuer, subject)` is in the existing deployment operator allowlist. Require the exact project ID, an explicit adoption reason and an idempotent operation identity. Lock the project and membership-administration namespace, verify the empty-membership precondition in the transaction, add the acting operator as admin, and write an attributable audit record. Repeat of the same committed action returns the same result; a different action after membership exists conflicts. Then existing member management can add a separately verified user. No arbitrary target-user assignment or global project listing is needed.

This is new behavior, not something the current project-create endpoint already supports. A scoped adoption route needs deliberate handling because `session_context` currently rejects session calls under `/v1/projects/{id}` before the handler when no membership exists (`src/auth.rs:313`). Prefer a narrow bootstrap action outside that membership-gated path, or an exact exception for adoption that independently verifies the operator session in its transaction. Do not weaken ordinary project authorization.

Small alternative: a documented operator-run one-time database transaction can perform the same checked/audited adoption without adding a permanent HTTP endpoint. It has a smaller API surface but poorer operator ergonomics and must be maintained as a real migration tool, not copied ad hoc SQL. Choose one mechanism; no enterprise provisioning control plane is warranted. Existing projects with memberships keep them unchanged and are ineligible for this adoption flow. Never assign all old projects to the first login, infer ownership from an email/local token, or reparent bundles into a fresh workspace.

The cutover plan must explicitly select the old PostgreSQL database/volume or perform a verified PostgreSQL backup/restore into a fresh target. Keep project/bundle/version IDs, payload bytes and digests, parentage, channel revisions/history, draft/proposal/evaluation state, integration hashes, receipt/history records, operation outcomes and audit attribution. Keep migration files append-only; do not edit already-applied migrations to reinterpret local records. Local private state is a credential/journal pointer, not the content database. Do not delete it or a PostgreSQL volume as launcher cleanup.

## Evaluator helper and honest handoff

Current coupling is precise: `scripts/evaluate-local.ts:14` accepts bundle/request IDs, adapter and optional state root, then reads `state.json` implicitly from `.local/console-demo` via `scripts/private-state.ts:129`. It constructs a dedicated read/write machine client with the hardcoded scope `local-app-evaluator`. `apps/console/src/lib/evaluation-config.ts:48` emits this command for three matching bundled descriptors without proving that an app runner is configured for the selected project. A production deployment cannot honestly claim that copied command is ready merely because the public descriptor matches.

Recommended successor is an app-owned example CLI, e.g. `npm run evaluate:app -- --config /absolute/private/config.json --bundleID UUID --requestID UUID --adapter NAME`. The config schema should be explicit and versioned: service URL, project ID, evaluator principal ID, evaluator token, and journal root. Use the configured principal for SDK cache scope rather than a hardcoded local label. Require a canonical owner-only private file/directory; never fall back to launcher state, auto-create credentials, start services or seed data. Keep secret values out of copied commands and output. Copy-safe placeholders must be visibly incomplete instructions, not a supposedly runnable command. A secret-manager adapter is optional later work, not a prerequisite or a new general configuration subsystem.

App config stays outside console/public evaluation descriptors. Preserve the installed adapter allowlist and structural match against dataset/grader/runtime/case inventory. Public requests cannot choose arbitrary scripts, import paths, endpoints or credentials (`examples/evaluation/README.md:29`). Keep explicit `--live` for the paid installed adapter; custom request descriptors must remain a request-ID/configuration handoff unless that application's runner exists.

Prefer UI copy that says “Create request” and “Run with your application's evaluator”; show the public request ID, bundle and project plus runner instructions. A command is available only when a server-controlled app runner profile is actually configured for that service/project/descriptor, or is clearly labeled as an example requiring setup. Never derive a private filesystem path or runnable shell fragment from request runtime metadata. The console creates/observes/interrupts requests; it does not launch execution. No queue-dispatch service or runner-registration product is required to express this honestly.

Preserve the runner's exclusive journal and recovery protocol (`examples/evaluation/runner.ts:65`): frozen request/version/digest identity; durable start/submit/finish keys; execution marker before callbacks; exact report before upload; no automatic reexecution after an ambiguous crash. Preserve evaluator principal ID and journal scope for in-flight work: start/finish bind evaluator and attempt (`src/evaluations.rs:298`, `:325`). `serviceUrl` participates in journal identity; changing endpoint, principal or private root is a recovery migration, not a harmless command rename. Prefer draining/finishing or explicitly interrupting old attempts before changing those fields. Interruption changes service state; it does not promise cancellation of app callbacks already running. Existing output references can name private local files and should not be presented as server-accessible artifacts.

Small alternative: retire the copied runnable helper entirely and retain `runEvaluation`/`evaluateRequest` as app integration examples with request-ID handoff. That removes the local-state dependency with less CLI/config surface but requires users to wire their own runner. Choose this or maintain the successor helper end to end; leaving the existing copied command broken is not a compatibility strategy.

## Sessions and pending operations at cutover

Current actor storage scope hashes service URL plus session secret, falling back to service token (`selection.ts:106`); selection encryption also derives from the console service token (`:33`). Signing in or rotating the console token changes these namespaces. Selection is convenience only and can safely require reselection. Do not treat a decrypted old selection as membership or convert a service token into a person.

Pending writes cannot be moved to a new actor by copying their keys. `src/commands.rs:63`, `:157`, `:342` binds locks, replay outcomes and lookup/close to principal/project/namespace/key. A local-web-console write is a different operation owner from `user:<uuid>`, even with the same text and key. Browser envelopes also contain actor/service/project/bundle/channel scope and exact action/body (`apps/console/src/lib/pending-operation.ts:2`); account changes erase submitted text while retaining scoped uncertainty (`:147`). Credential-issuance recovery similarly uses actor/project/integration metadata, while issuance keys are bound to `issued_by` (`src/integrations.rs:190`).

Recommended compatibility rule: before disabling the old console, stop new submissions and reconcile/close outstanding operations under their original legitimate machine principal using existing SDK `getOperation`/`closeOperation`, retaining exact paths/keys. Preserve any unresolved metadata and audit records. A missing observed outcome is not proof of failure. After sign-in, never auto-replay/rekey old writes or declare old issuance absent; review stored outcomes and revoke an uncertain issued credential before replacement. Existing same-person session changes also need an explicit recovery policy if a future UI promises continuity; do not smuggle that redesign into local-mode removal. No global principal rewrite or cross-principal recovery API is required for the initial production cutover.

## Packaging, retirement and acceptance scope

New contracts needed for this plan are limited to production-only browser configuration validation; one checked adoption/bootstrap mechanism if retaining existing unowned workspaces; and either the explicit app evaluator config/CLI contract or a documented request-ID-only handoff. Existing SDK routes, machine grants, integration credentials, immutable content, evaluator state machine and operation ownership remain compatible.

Retire `local`/`demo` root scripts and launcher-only `scripts/dev-console.ts`, `scripts/console-bridge.ts`, local state provisioning/process/recovery helpers and associated local qualification stories as their callers disappear. Do not remove `scripts/private-state.ts` wholesale while evaluator journals still need its general private I/O helpers; split reusable primitives from the launcher default and local diagnostic dependency. Likewise preserve ordinary app SDK examples, the operator CLI, PostgreSQL backup/restore tools and package-consumer verification.

The evaluator and operator CLIs are currently checkout tools, not installed SDK commands: root scripts invoke `tsx`, SDK package ships only `dist`, `scripts/build-packages.mjs` publishes only package source trees, and `scripts/packaging/verify.mjs` exercises SDK/plugins rather than these helpers. `tsconfig.build.json` includes examples but excludes scripts/tools; compiled examples alone do not make a complete distributed runner. State clearly that a successor runner remains a checkout/app example unless deliberately packaging its CLI, adapters, journal/private I/O dependencies and required lock helper. Keep evaluation orchestration out of the core SDK package unless separately chosen.

Update active instructions together: `README.md`, `docs/development.md`, `apps/console/README.md`, `.env.example` and deployment examples, `deploy/README.md`, `examples/evaluation/README.md`, active architecture/contracts and copied-command UI. Existing architecture text promising “existing deployments start in local mode” (`docs/architecture/productization/workspaces-and-access.md:45`) must be superseded by the explicit cutover rules. Historical remediation/research records can remain visibly historical. The checked-in documentation site contains copied source and rendered pages; regenerate it through the repository's established process so active navigation no longer recommends retired commands. Do not mass-edit archives to imply that earlier local acceptance was production acceptance.

Implementation acceptance should demonstrate machine token-only SDK reads/writes within configured rights, scoped integration content/receipts and revocation, session-required console access, adoption denial for nonoperators/already-owned projects, unchanged PG content/history/pins, principal-correct recovery and evaluator journal continuity. Include isolated package-consumer validation for anything newly shipped. These are proposed future checks; none were run in this planning audit.
