# Production console planning input

Planning only. Repository inspection; no application changes, runtime execution, browser checks, models, secrets, or tests. No applicable repository/ancestor `AGENTS.md` was found. PostgreSQL is already the implementation, including identities, sessions, memberships, audit and durable operations; this needs no SQLite replacement.

## Product boundary

Ship one browser product: verified OIDC sign-in → Rust browser session → current workspace membership → explicitly scoped console action. The console transport credential identifies the trusted server, never the person. A deployment bootstrap identity can create workspaces; it gets ordinary `admin` membership in each workspace it creates. Bootstrap permission must not silently grant access to every existing workspace.

Machine credentials remain valid for app delivery, evaluator and other intentionally supported API clients. They must not open a token-only browser operator experience. The browser must never select an actor, submit issuer/subject as proof, receive login/transport credentials, or supply trusted-user/role headers. Existing Rust middleware strips the trusted headers and resolves them from a live session; preserve that design and transactional membership checks. Person attribution uses the stored user ID plus session, alongside the service principal, rather than the shared console token.

## Production journey and concise setup UX

1. **Deployment unavailable:** “Acclimate is not configured. Contact the deployment administrator.” No broken Sign in loop, raw env list or token entry box. Diagnostics name missing keys only in protected deployment logs. Service connection outages are distinct: “Couldn’t reach Acclimate. Retry.”
2. **Signed out/session expired:** “Sign in to your workspaces.” One Sign in action. Authentication failure is distinct from a signed-in account with no membership. After an expired-session write, retain an unresolved operation as unknown; do not mark it failed or automatically issue a new write.
3. **Verified, no workspaces:** ordinary person sees “Ask a workspace administrator to add you” plus Copy user ID. Bootstrap identity sees “Create your first workspace”; creation atomically inserts workspace + creator admin + audit. Do not make first visitor admin, manufacture a sample workspace, or ask everyone for deployment configuration.
4. **Members:** person signs in once and gives admin their opaque ID. Admin looks up the already verified user, confirms issuer/subject, selects viewer/editor/admin, and adds/removes membership. Preserve pagination, last-admin protection and live server checks. A workspace admin cannot create unrelated workspaces merely by being admin. Invitation/email recovery is a separate product decision, not prerequisite for this minimal flow.
5. **Empty workspace:** “Create a bundle” with current initial-content/import/explicit-example choices. Existing bundle content, Changes, Releases and App setup remain the main work. No new onboarding wizard or sidebar redesign.
6. **App setup:** show service API URL, workspace/bundle/channel, language recipe and SDK installation artifact. Admin creates a connection and distinct content-read / optional receipt-write credentials; non-admin asks admin. Secret is shown once and belongs in the app’s private environment. App owns cache, job files, tools, model credentials and execution. Missing receipts remain “unknown”; published content and prepared sessions stay pinned as designed.

## Public configuration and role contract

Introduce a small sanitized product configuration DTO, separate from `process.env`: availability/auth status, optional public service API URL, verified identity/capabilities and deployment edits availability. Keep per-workspace role with the workspace record. Distinguish `signedOut`, `unavailable` and `authenticated` explicitly; an API outage must not masquerade as signed out or no workspaces. Avoid making every access failure a Sign in link.

`CONSOLE_SERVICE_URL` is server transport routing and may legitimately be private or loopback. Do not blindly copy it into app recipes. Configure a separate public app-facing service URL (for example `CONSOLE_PUBLIC_SERVICE_URL`) when different; show “Ask your deployment administrator for the service URL” if absent. This value is public metadata, not a proxy target accepted from a browser. SDK recipes can then fill the known public URL while preserving private credential placeholders. Never expose transport/login tokens, provider secret, database URL or evaluator private config in this DTO.

`CONSOLE_ALLOW_EDITS` can remain a deployment-wide authoring switch, but cannot grant a role. Project/bundle/channel defaults may remain navigation preferences, never access grants or requirements for bootstrapping. Keep deployment bootstrap capability separate from workspace role. Use admin-only Connections consistently in both UI and Rust; rendering a hidden button is not authorization.

## Evaluation handoff

`lib/evaluation-config.ts::localEvaluatorCommand` currently turns matching public fixture descriptors into `npm run evaluate:local` commands. `improvement-workspace.tsx` renders them as runnable from “this checkout,” even when the console is a remote app with no relationship to the viewer’s private launcher config. A matching descriptor proves configuration compatibility, not installed evaluator availability or authority.

Default remote UX: create frozen evaluation intent, then **Copy request ID** / **Copy request details** for the app’s installed evaluator. Include explicit public service/workspace/bundle/request identity and frozen config revisions. State “Your app runs this evaluation and reports evidence.” Keep last-reported status, actual interruption limits and evidence inspection before release. Do not add a server execution service, SSH runner, browser model call, or model credentials form.

Remove universal local presets/checkout-command claims from production. If documented example adapters remain, label them examples; selection must never imply an installed runner. Any optional command recipe must reference a documented installed public CLI and explicit app-owned configuration, not auto-detect compatibility from descriptor equality or inherit console transport credentials. Private local fixture helpers can remain developer tooling outside the production product path. Model-free delivery checks in App setup remain useful and correctly app-owned.

## External prerequisites and scope

Before real deployment: supply a real HTTPS OIDC issuer/client and registered exact callback (`CONSOLE_ORIGIN/auth/callback`); arrange issuer account access and the exact issuer/subject bootstrap allowlist through the deployment owner; configure distinct login authority and console transport secrets on both services, separately from machine grants; provide correct console origin/proxy routing, private service reachability, public app API reachability, PostgreSQL migrations/backups/recovery, and built console/SDK artifacts. Existing names are documented in `apps/console/README.md` Hosted access; make that the single required deployment contract or replace it coherently. Do not choose a paid identity vendor or ship fake authentication to fill absent environment values. Real provider/callback/sign-out qualification remains an external gate; fixture-tested code is not evidence of deployed sign-in.

The process-local five-minute OIDC transaction map is legitimate for one console instance: restart loses pending sign-ins and the person retries. It is not by itself a safety bug requiring Redis or an execution platform. Document one instance (or explicitly justified callback affinity); add shared transaction storage only if deployment actually needs multiple instances. Likewise, one issuer, manually bootstrapped verified IDs and no invitations are supportable first-production scope. The safety/product bugs are silent unauthenticated operator fallback, mixed workspace authority, accidental credential exposure, and asserting remote evaluator availability without evidence.

Preserve scoped `/w/...` URLs, URL-bound mutation destinations, per-actor component keys, encrypted selection preference, unsaved navigation guards, no-store reads, verified bytes, exact pending write bytes/keys, receipt-first reconciliation and one-time credential recovery. Role/session expiry must fail closed without converting an uncertain prior write into success or safe-to-repeat. These production boundary changes should keep the current polished UI and app-owned execution model intact.
