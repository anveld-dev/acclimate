A competing service exits. Migration numbering is already `0001` through `0012`; `0006_workspaces.sql` preserves bundle projects while adding users, memberships and hashed browser sessions.
- `src/main.rs:104` probes the ownership connection continuously with a two-second timeout. Losing it stops the worker and exits 75; worker termination exits 1. `src/improvement.rs:283` processes one proposal at a time, retries interrupted work below three attempts and bounds the provider call to sixty seconds. Queue SQL failures are largely swallowed, so a live worker task does not prove useful queue progress. Recovery must not promise exactly-once provider execution or billing.

The supervisor's forced-stop deadline is the outer bound. The unit gives 45 seconds; Compose gives 50.

Identity configuration is checked when handling auth requests, rather than a complete startup preflight.
- `src/auth.rs:250,388`, console `selection.ts`, `access-core.ts` and `identity.ts` switch between `local` and `hosted`; missing mode means local. Local console use can operate with a static machine credential and no browser identity. The separate hosted console credential already requires a browser session, and membership/session authorization is rechecked transactionally. Preserve those checks while deleting the alternate mode.

## Smallest real application topology

One TanStack Node process, one Rust API/worker process, one explicitly provisioned PostgreSQL 16 database, one external OIDC client and a trusted HTTPS reverse proxy. Proxy the browser origin to TanStack and provide the separately configured SDK API origin/path to Rust; backend listeners stay on loopback or a private container network. Keep Rust's database-wide ownership lock and one worker. Deploying another replica is unsupported in this scope; pending OIDC flows remain process-local and a console restart requires restarting an unfinished login.

Local development uses the same verified OIDC/session/membership path with an explicitly registered development client, callback and trusted loopback HTTPS origin. The operator supplies the database URL and identity configuration. Development tooling may watch/build/start those configured processes; it must not infer the OS PostgreSQL user, create/adopt a database, mint a browser authority, seed content, start Docker, or arrange a public deployment. Example content remains an explicit authenticated app action. No HA, Kubernetes, fleet, agent sandbox hosting or public DNS/certificate automation is needed to launch this app.

## Configuration and identity contract

Load and validate typed configuration once, before either process listens; remove `ACCLIMATE_MODE`/`CONSOLE_MODE` and all local fallback behavior. A missing production identity configuration is a startup error. Keep server-only values out of Vite/browser variables and logs.

| Process | Explicit required configuration | Optional configuration |
| --- | --- | --- |
| Rust | `DATABASE_URL`; intentional bind address; separate console transport and login-authority credentials; verified issuer/subject allowlist for initial workspace creation | Complete provider endpoint/token/model tuple; scoped SDK machine principals if compatibility requires an initial configured list |
| TanStack | Rust service URL; matching console/login credentials; canonical HTTPS origin; external OIDC issuer/client ID/client secret; intentional host/port | No selected project, bundle or channel is needed to boot |
| Supervisor/proxy | Executable/image versions, protected environment source, restart delay/limits, graceful-stop deadline, upstream routes and HTTPS identity | Explicit database CA/certificate settings when required |

The console/login pair is a narrow server-to-server trust boundary, not a global machine administrator. Browser calls require a valid session and current project membership regardless of any machine token presented. Keep configured issuer/subject workspace creators as verified humans; rename misleading “operator” product terminology if appropriate, but do not replace the allowlist with first-visitor admin or an OS-user bootstrap. Preserve `(issuer, subject)` identity; do not match users by incidental email/name.

SDK and application integrations still need machine principals. Preserve the existing issued integration credentials: `content-read` delivers the bound project/bundle/channel, including versions previously promoted to that channel; `receipt-write` submits receipts and cannot read content. `src/integrations.rs:243` enforces hashed credentials, enabled integration, non-revocation and scope under a transaction; channel resolution and version/payload reads call this path. `tests/integrations.rs` covers distinct credential kinds, rejection of unpublished-version reads and revoked-integration receipt rejection. The file's leading comment about never granting project access means these are not general project administration credentials; it does not mean all integration credentials are receipt-only. No replacement principal-management system is needed for existing SDK delivery.

Existing `ACCLIMATE_AUTH` contains per-project/action grants rather than a true global token, but the launchers mint a full-rights console grant that acts as the browser bypass. Remove that use and keep machine credentials unable to create human sessions, manage memberships or become console administrators. Application/evaluator write scopes may still need narrowly configured machine grants; decide that compatibility boundary explicitly and preserve legitimate SDK/evaluator use without granting browser authority. Do not silently reinterpret or invalidate existing credentials/data during the production-mode cleanup.

## Startup, upgrades and shutdown

Prefer an explicit `migrate` operation and schema compatibility check on normal `serve`, both shipped in the same release binary/image. This separates deploy-time schema authority from ordinary process restarts and lets the runtime role operate tables without owning DDL. A first empty database uses that same explicit migration command. Migration and serving must coordinate on the existing singleton lock; never apply migrations alongside a live old process. A single-host rollout is stop old process, verified backup, migrate, start API, verify API readiness, start/verify console and route traffic. No rolling-update claim is needed.

Keep historical migrations/checksums and all existing PostgreSQL content, users, memberships, session records, idempotency/operation records and audit history. Add new numbered migrations only where necessary. Removing implicit grant-based project backfill from `main.rs` and the GET projects handler must not delete existing projects or infer human membership. An existing database with no human administrator needs an explicitly designed, identity-verified administrative assignment procedure; it is not an excuse to mutate the user's database during planning or incident troubleshooting. No database migration or adoption is authorized by this document.

Proposed API probes: retain `/health` as cheap process liveness, add `/ready` with a short bounded PostgreSQL query, verified schema state, retained queue ownership, initialized worker and a draining flag. Readiness returns 503 during startup/drain/dependency failure, and exposes no identities or secrets. Database outages affect readiness; liveness need not restart-loop a healthy process for ordinary dependency trouble. Ownership loss remains fatal because exclusive execution is no longer safe. A representative authenticated read is still a release smoke test, not a load balancer's stored administrator credential.

Add console liveness/readiness too: build/startup configuration valid and Rust readiness reachable; a database query is owned by Rust. Do not call the identity provider on every probe. Validate OIDC discovery/client/callback separately before routing a new release; an IdP outage blocks sign-in without proving that existing sessions or the Node event loop failed.

Use one shutdown coordinator: mark unready, stop accepting HTTP and claiming proposals, drain bounded in-flight HTTP, cancel/bound the active worker, close connections and release the guard last. Recovery of an interrupted proposal remains durable and attempt-limited. On ownership loss, cancel worker work immediately and stop HTTP before releasing/closing ownership; do not rely on dropping the select's server future as the drain policy. Set one documented drain budget compatible with the thirty-second HTTP bound and align systemd/container/proxy grace deadlines above it; retaining a 45-second application budget and 50-second supervisor allowance is enough if worker cancellation is explicit. State that cancellation does not prove a remote provider stopped charging.

Systemd should supervise both actual application processes with delayed, rate-limited failure restart and explicit dependencies/readiness. Compose should have actual API/console services, persistent PostgreSQL volume, probes, deliberate restart policy and matching grace deadlines. Keep development passwords/ports out of production examples. Add a console image/build context (or separate native Node recipe); expand `.dockerignore` narrowly and keep private state excluded. A deployable app requires all these artifacts, not just `cargo build`.
