## 4. Drain Python receipts without holding process exit

**Owner: Python delivery.** Replace `ThreadPoolExecutor` in `python/acclimate/receipts.py`; `shutdown(wait=False)` is insufficient because executor workers are joined at interpreter exit. Use a single lazy **daemon `threading.Thread`**, created only after an opted-in reporter has work, with no executor or atexit join. Never make its call into the supplied client while holding the state lock.

Keep `DeliveryReporter(client, project_id, integration_id, max_queue=100, clock=...)`, `bind`, stage methods and asynchronous `flush()` compatible. Add `wait(timeout: float = 0.25) -> bool`, using a condition and monotonic deadline; true means idle, not successfully delivered. Change `close(timeout: float = 0.25) -> None` to atomically mark closed, discard queued work, signal the worker and join at most that deadline outside the lock. Validate finite timeout 0..5 seconds. Close is idempotent; post-close report/flush silently drop and cannot start another worker. Do not implicitly flush on close. A currently blocked daemon may outlive close, but cannot prevent interpreter exit or start another request after it returns. Do not claim Python can forcibly cancel that request.

Separate fresh pending events from retryable failed events. A worker drains fresh arrivals until empty and clears its running flag atomically with its empty check; this closes the current enqueue-during-flush race. Each failed event is parked, never immediately reinserted into the active drain. Only explicit `flush()` requests another attempt of parked events; coalesce concurrent flushes, and do not let repeated flush calls during an active pass retry that pass's failures immediately. Snapshot each event once per pass. No timers or endless self-rescheduling retries.

Enforce `max_queue` across pending + parked + in-flight events, retaining the existing 1..1000 bounds and dropping newest when full. At most one worker/client request per reporter, even if a client never returns. Preserve event ID, occurrence timestamp and exact receipt body across retry; drop events at age >=24h before send/retry. The active event cannot be unsent at expiry. Keep all failures isolated from resolution/preparation/start.

The recipe uses a separate stock receipt client with `retries=0, timeout=2`; content client settings remain independent. urllib's socket timeout is not a hard total request deadline, especially with slow data. The hard guarantees here are bounded caller waits, bounded memory/concurrency, and no interpreter-exit dependency on receipt I/O. Document that a stuck injected client occupies the sole daemon until return/process exit; do not spawn replacements or imply durable delivery.

**Acceptance:** replace tests that synchronize through private `_worker.submit` in `python/tests/test_receipts.py` with public `wait`/barriers. Block the first send, enqueue prepared/started while it runs, release it and observe all fresh events without another enqueue/flush. Test failed events are attempted once per explicit pass; concurrent flush/enqueue/close, capacity including active work, 24h boundary, unchanged IDs/times, no requests after close, idempotent close, and a reporter-free resolution creates no worker. Most importantly, launch a disposable Python subprocess whose fake client's send never returns: exercise both close and no-close paths, and require actual process exit within an outer 2-second test deadline. Include a slow-drip local HTTP receipt response. Kill/reap failed fixtures; a fast return from close alone is not a passing shutdown test.
