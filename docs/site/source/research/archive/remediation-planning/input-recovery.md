# Recover console writes without guessing

**Planning input. The [reviewed plan](../../../architecture/productization/remediation/plan.md) and [review resolutions](../../../architecture/productization/remediation/review.md) take precedence where choices differ.**

Plan only, based on the [2026-11-14 audit](../../../architecture/productization/current-audit.md). No implementation or runtime changes are part of this document.

## What is there today

- `src/commands.rs` fingerprints **method + route + exact request bytes**, serializes matching mutations, reauthorizes inside the transaction, and records success atomically with the write. `command_results` is durable only for setup/draft routes; other writes use the 24-hour `idempotency` table. `GET /v1/projects/{project}/operations/{key}` reads only durable results, for the current principal and project, and checks the recorded operation's right before returning it. `not_observed` means no committed result was visible to that lookup; an original request may still commit.
- `draft-workspace.tsx` persists only a key in localStorage. The command body survives only in a ref, so a reload followed by `not_observed` leaves no exact retry. Its later editor changes also need protection when an earlier save is recovered.
- `improvement-workspace.tsx` keeps keys in a signature map in memory. The same evaluation inputs reuse a key even after completion; reload loses uncertain proposal/evaluation/release operations. `bundle-releases.tsx` has the same reload gap for restore.
- `improvement.ts` reconstructs request bodies from today's channel, fixture configuration and draft generation. It and `edit-channel.ts` reject stale revision/parent/current-target state before service replay can return a successful older result.
- `integration-core.ts` reduces errors to messages. Credential issuance deliberately never replays secrets: `src/integrations.rs` permanently associates principal/project/integration/key with the issued credential and returns `credential_already_issued`, even after revocation. The Connections signature map retains that old key on this definitive outcome.
- Forms already supply explicit resource scope through `bundleEnvironment`/`connectionCommand`; do not replace it with the selection cookie. `actorScope()` currently hashes service URL plus session token (or local service token). It isolates sessions, but is not a stable account identity across login.

## One frozen pending-command format

Add a shared console command helper and storage module. Prepare a command once from the reviewed inputs, then store it **before the first network write**. The versioned envelope contains: operation UUID; current actorScope and service origin identifier; explicit project/bundle/channel and optional draft/integration/request ID; allowlisted action; exact UTF-8 JSON body string; expected generation/revision and pinned version/digest/configuration identity; creation time; original disclosure authorization for a proposal. The body is serialized once, including normalization such as trimmed reasons, and never rebuilt from live UI state. Metadata duplicates are verified against the parsed body. A browser hash detects accidental corruption, not authorization.

Expose internal server functions `prepareConsoleCommand`, `submitConsoleCommand` and `recoverConsoleCommand`. Preparation performs the existing fresh-write validation and returns the frozen envelope; it does not mutate. Submission accepts only the fixed action union and derives the service route from validated scope/IDs. No browser-supplied URL, bearer token, trusted-user header or arbitrary HTTP proxy. Add a narrowly scoped SDK transport helper that sends the stored body verbatim; ordinary typed SDK methods keep their current behavior. Recheck session, console edit policy and service authorization on every submission.

Cover draft create/save/discard/publish, proposal create, evaluation create/interrupt, direct release/restore, and connection create. Credential issue/revoke use the same pending lifecycle but the secret-specific behavior below. Receipt ingestion and app-owned evaluator start/finish remain outside browser recovery.

## Replay and reconciliation contract

1. A prepared command starts `pending` before transmission. Reload restores the envelope and offers **Check outcome** and **Retry identical command**. Restore the pending snapshot separately from editable working text. Editing never changes its key/body; another write in that operation's lane waits for resolution. Other bundles and drafts remain usable.
2. Lookup `committed`: validate returned route and result identity against the envelope, record the result, refresh that exact resource by ID, and remove local retry text. A recovered draft save establishes the submitted snapshot as the saved baseline; preserve newer editor text and keep it dirty. A failed follow-up read does not turn the known commit back into uncertainty.
3. Lookup `not_observed`: show “No committed result observed yet.” Keep the same command and key. A read error/timeout is `unknown`, not `not_observed`. Neither authorizes a replacement command.
4. An explicit retry first checks the operation. A committed result is returned before channel/draft freshness preflight. If no result is observed, run fresh-state checks against the **frozen expectations**, then submit unchanged bytes. Do not substitute today's parent, generation, reason, fixture configuration or revision. If state is stale, keep the command unresolved and offer another check or explicit close; do not generate a fresh key automatically. A concurrent commit between lookup and preflight is recovered by the next lookup. The service still checks authorization before replay and enforces all generation/revision/evidence/parent constraints when it has no stored result.
5. Preserve structured `code`, `status` and `outcome` through server functions: `committed`, `rejected`, `unknown`, `not_observed`, `closed`, plus `issued_secret_unavailable` for issuance. Distinguish transport/5xx uncertainty from authoritative validation rejection. A rejection of a retry does not by itself settle a previously uncertain request; reconcile or close it before unlocking its lane. `idempotency_conflict` never causes key rotation.

Extend durable command handling using an explicit route/action allowlist, not a broad substring test: setup/drafts plus proposal creation, evaluation creation/console interruption, promotions and connection creation. Keep existing setup/draft durability unconditional; the new console transport opts the added routes in with `X-Acclimate-Durable-Operation: true`. Unmarked clients retain existing per-route key semantics. Marked operations use principal/project/key uniqueness with route/body collision checks; acquire the legacy per-route lock and shared durable lock in a consistent order so mixed-version retries serialize. An unexpired legacy idempotency hit is promoted to a durable result atomically when replayed with the opt-in marker. Lookup requires current read access plus the original action right, including admin where applicable. Record outcomes atomically with writes; replay returns the original status/body, even when a request later finishes or a channel advances. Fetch the current request separately. Do not delete durable deduplication identities after 24 hours.

Durable results never contain credential secrets or a second copy of submitted draft payloads. Evaluation creation/interrupt responses do include their saved configuration/reason: explicitly classify those retained response snapshots as project content under the same retention policy as evaluation records. If project content is deleted later, retain a non-content deduplication tombstone and return an explicit unavailable/deleted outcome, never execute the old key again.

For a safe way to stop tracking an uncertain write, add `POST /v1/projects/{project}/operations/{key}/close` with an allowlisted intended action/scope. Under that same lock and current action authorization, return the existing committed result or insert a durable `closed` tombstone. A later matching or delayed write with that key must fail `operation_closed`; lookup returns `closed`. This is a fence against a future commit, not cancellation of a committed action. Recheck scope/path for existing records; an absent legacy record may be closed only for a valid authorized action in the selected resource scope. Credential issuance uses its own lock and is excluded from this endpoint. Only a confirmed close lets the UI discard tracking and start a newly reviewed command safely. A close timeout remains uncertain.

## Private browser storage policy

Use sessionStorage by default: exact retry text survives reload in the same tab and is normally removed when the tab closes. Offer an explicit **Remember recovery on this browser for 24 hours** option using localStorage, with plain disclosure that it contains bundle text, hypothesis/evidence, evaluation configuration and release reasons. This is private application data, not encrypted storage or a defense against another person using the same browser profile. Do not promise recovery of unsent editor changes or browser-crash survival with the session-only option.

- Namespace and verify every entry by current actorScope, service origin, project, bundle, channel and operation key; add resource ID where relevant. Keep today's session-derived actorScope: session rotation/account switching does not automatically adopt old commands. A future stable-account scope is a separate identity decision. Recovery never crosses accounts or service instances just because resource IDs match.
- Persist only submitted inputs needed for exact retry, not full fetched parents, editor autosaves, tokens, cookies or issued secrets. Enforce existing service body limits and a bounded total storage budget; never evict unresolved entries silently. A storage/quota failure blocks sending and explains why. Persist completion/closed state before best-effort text cleanup so a cleanup failure cannot cause a new write.
- Purge retry text immediately after confirmed success/rejection of an initially unambiguous request, confirmed close, explicit “Forget recovery text”, logout, or 24 hours after creation. Never extend expiry on reads/retries. For unresolved entries, retain only key/scope/action/timestamps until checked or closed; expiry/forgetting is not failure. Sweep on app startup and periodically while open; expired text is never read/rendered. Closed browsers cannot run cleanup, so disclose that physical removal occurs on next app use. Browser storage is never backed up to application logs, analytics, URL/search parameters or caches.
- Logout/account-change handling clears in-memory and known browser recovery entries; ensure same-origin other tabs receive the event and clear their state too. Account scope checks apply even when cleanup fails. Service functions retain `private, no-store`, and logs contain only safe operation metadata. A session expiry hides stored text until an authorized matching session is available; it does not replay automatically.
- Existing localStorage key-only draft/setup records migrate to metadata-only legacy entries after validating the original actor/resource scope. Check for a committed result first. Never reconstruct old bodies from current content. When absent, offer the close/fence path and a fresh review afterward. Older already-expired 24-hour operations may have committed without a durable receipt: disclose this limit and inspect resource/history before a new decision; a close only fences future writes and cannot prove past nonexecution.

## Evaluation and credential decisions

**Evaluation:** use a pending operation per intentional click, not a permanent map indexed by input signature. A lost create response retries that operation and returns the same request ID. After confirmed creation, follow the request by ID; creation is complete even while execution is running. Offer an explicit **New evaluation** after a terminal request, showing the pinned cases/settings and issuing a new UUID even if inputs are identical. Do not turn a retry into a second request or re-use an old terminal request for a new run. Request/attempt attribution, configuration and active-ID polling belong to the evaluation owner; this helper preserves their identities rather than implementing execution.

**Credential:** persist only key, scope, integration ID and kind. Retry a lost issuance with that same key. Preserve the existing `409 credential_already_issued` code/message for clients, and add optional machine-readable `details: {credentialId, kind, revokedAt}` to that error and its SDK representation. Never parse the ID out of human text. Treat it as definitive issuance with an unavailable one-time secret; remove the pending issue state and show the exact issued credential. Do not retry hoping to reveal its secret.

Require explicit revocation of that credential, then confirm `revokedAt` using the scoped authorized read (repeating revoke is already idempotent). A lost revoke response keeps replacement disabled until confirmed. **Issue replacement** is a fresh user action with a new UUID, same selected kind and current admin checks. Never recycle the old issuance key, even after revocation; retrying that key continues to identify the original issuance. Keep successful one-time secrets only in React memory until dismissed/unmounted/logout, and keep the secret dialog visible if a following list read fails. A lost dialog follows the same revoke-and-replace path. Disabled integrations cannot receive replacement credentials.

## Acceptance cases

- Reload after lost draft create/save response: committed lookup reopens the original draft/generation; `not_observed` restores exact retry bytes and same key. Retrying creates at most one draft/generation. Later editor changes survive reconciliation.
- Lost proposal/evaluation/publish/restore responses survive reload and more than 24 hours through durable lookup. Advancing the channel or draft after commit does not block returning that commit; an uncommitted stale command still fails fresh checks. A current-channel read outage cannot hide an accessible committed operation.
- Two concurrent identical retries share one result. Changed body/route with the same key conflicts. Close versus in-flight write serializes to either committed or closed; a late write cannot pass a closed tombstone. Closing never rolls back a release.
- An identical **New evaluation** after terminal execution gets a new request ID; uncertain retries retain the old one. Refreshing the page never starts execution.
- Lost issuance yields the original credential ID without secret replay; revoke with a lost response is reconciled; confirmed replacement uses a new key and yields a new credential. Retrying the original key still identifies the revoked original. Other principals/projects/integrations cannot retrieve issuance metadata.
- Removed/demoted member, expired session, wrong project, changed browser selection cookie, another tab/account/service origin, and disabled console edits do not bypass current policy. Required action rights are checked before stored results are exposed. Forged envelopes cannot choose arbitrary routes or headers.
- Storage disabled/quota exceeded sends nothing. Text expiry, explicit forgetting, logout and account switch remove sensitive text and preserve uncertainty correctly. Legacy key-only `not_observed` offers close/review instead of an unrecoverable permanently disabled Save. No secret or request text appears in logs, URLs or analytics.
- Cover these with `apps/console/tests/{drafts,improvement,edit-channel,integrations,identity,setup-selection}.test.ts`, service command/integration/evaluation/access regression tests, contract tests and browser reload/storage/race scenarios in `scripts/test_console_browser.py`. Use disposable data/fake responses; no provider calls or real credential issuance needed for planning validation.
