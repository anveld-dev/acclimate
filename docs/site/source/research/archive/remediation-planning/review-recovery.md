# Independent recovery/security review

Reviewed the plan and recovery, evaluation, access/delivery and shipping inputs against source. No credentials, services or provider calls were used. The direction is sound; settle the following contracts before implementation.

## Required corrections

1. **Specify fencing across marked and unmarked requests.** `input-recovery.md` preserves legacy per-route keys while introducing principal/project/key durable identity. Today unmarked non-draft writes acquire only their route lock and never inspect `command_results` (`src/commands.rs:60`, `:71`, `:80`). Merely adding the marker branch and a shared-lock close endpoint lets a delayed unmarked write bypass a closed record. Require every affected route, including unmarked callers, to serialize with close and inspect the applicable fence. Define whether a fence matches route/action or the entire new namespace. Preserve an unrelated legacy route's legal reuse of the same key. Also specify marked adoption when two different legacy routes already used that key: return conflict, without deleting or reinterpreting either legacy result. Test close against delayed marked/unmarked writers, legacy promotion, expiry and cross-route reuse. This is necessary for the promised safe close, not a hypothetical attacker model.

2. **Record effective replay authorization, not the initial actor right.** Integration creation begins with `write`, additionally checks machine `promote`, then checks browser `admin` before returning a replay (`src/integrations.rs:91–100`). `finish_mutation` currently records only `a.required_right` (`src/commands.rs:91`, `:123`), and lookup trusts that field (`:150–152`). Extending durability unchanged would expose a created connection through lookup after admin demotion to editor. Use an explicit action authorization policy shared by mutation, lookup and close, preserving browser-admin and machine-grant requirements. Add a connection-specific demotion/revocation test; generic write-denial tests do not cover this case. Keep current authorization before returning any saved payload.

3. **Add exclusive journal ownership before evaluation starts.** `input-evaluation.md` requires durable keys and forbids rerunning uncertain execution, but does not serialize two simultaneous helper invocations. Current service start accepts the same principal/attempt repeatedly (`src/evaluations.rs:290–298`); that protects request state, not application execution. Two helpers sharing one journal can both execute after the same successful start. Require a per-request process lock held through reconciliation, execution, report persistence and finish. A second process must exit/inspect without execution. Release on process death; never treat lock loss as evidence execution did not occur. Persist an execution-started marker before callbacks, and crash after that point without a complete saved report must require interruption/new request. Test concurrent launches and crash boundaries. Existing example launches execution immediately after start (`examples/evaluate-request.ts:57–63`).

4. **Resolve the evaluator handoff contradiction.** Plan section 3 and `input-evaluation.md:72–76` specify a separate evaluator principal and `scripts/evaluate-local.ts`; `input-shipping.md:28–31` instead specifies `scripts/local-evaluate.ts` and borrowing the author principal. Choose one command, configuration schema and principal provisioning owner. The separate read/write principal in the main plan is sufficient within the stated local trust boundary; it needs no new service right. Journal scope must include service/project/bundle/request and principal identity, and reject mismatches before execution. Reuse private checks for journal reads/writes as well as config reads. Current launcher write helper is not atomic (`scripts/dev-console.ts:65–75`), so extraction alone does not satisfy the proposed atomic token/journal persistence.

## Retain these requirements

- Recovery already correctly separates `not_observed` from failure, freezes exact body bytes, requires close after uncertainty, preserves newer edits, and keeps expiry/forgetting from proving nonexecution. Preserve these as acceptance gates. Exact serialization matters because fingerprints include raw bytes (`src/commands.rs:52–57`).
- Session-derived actor scope intentionally prevents adoption after login rotation (`apps/console/src/server/selection.ts:106–112`). Logout currently redirects after cookie deletion (`identity.ts:178–199`); implement the promised client purge and cross-tab invalidation before navigation, plus scope guards on restored state and late responses. No stable-account identity is required.
- Credential issuance already never replays secrets and keys remain associated with the original issuance (`src/integrations.rs:185–215`). Keep issuance out of generic durable response storage; return typed original metadata, confirm revoke, then use a fresh replacement key. This is adequately specified.
- Last-admin guarding inside the existing membership writer lock is correct (`src/workspaces.rs:393–411`). Keep concurrent crossed-admin tests; no additional lock or recovery account is needed.
- Python daemon replacement and actual subprocess-exit tests address the executor shutdown defect (`python/acclimate/receipts.py:20`, `:61`). Clarify “no requests after close”: an already claimed in-flight event may enter/finish the client after close; prohibit claiming another event. Strict cancellation of that dispatch race conflicts with bounded close and arbitrary blocking clients. This wording change should not weaken bounded queue, fresh-arrival draining or no automatic failed-event retries.
