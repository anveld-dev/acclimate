# Second pass: recovery, admission, and stop semantics

Static review on 2026-11-17, current Acclimate checkout. No model calls, tests, application changes, or upstream experiments were run. The first-pass lifecycle report correctly identified missing campaign durability; this pass checks where existing operation-level recovery already works and where it cannot supply continuous-learning semantics.

## 1. High for bounded continuous spend: proposal retries recover state, not external paid work

**Observed implementation.** A claimed proposal increments `attempts` before calling the provider ([improvement.rs:319](../../../../src/improvement.rs#L319)). Startup requeues running proposals below three attempts ([main.rs:174](../../../../src/main.rs#L174)); the worker also repairs leftover running state before fetching queued work ([improvement.rs:298](../../../../src/improvement.rs#L298)). The model interface returns only candidate files and rationale. Its actual HTTP dispatch sends the prompt/model but no proposal-attempt identifier or provider idempotency/reconciliation key ([lib.rs:233](../../../../src/lib.rs#L233), [lib.rs:243](../../../../src/lib.rs#L243)). Provider usage and request identity are not returned by that interface. Only after the response is validated does the candidate/success transaction begin ([improvement.rs:386](../../../../src/improvement.rs#L386)).

**Concrete crash window.** The provider accepts and bills generation; the process dies before committing the candidate. Recovery dispatches a new generation for the same proposal. Even a response already received can be lost before durable candidate storage. The attempts cap bounds generation retries within that proposal, but does not prove one paid operation or preserve the unknown first outcome. A new campaign/proposal can reset that limit.

**Counterargument / downgrade of the broad claim.** This is not evidence of duplicate database candidates, an unsafe concurrent queue, or exactly-once behavior being promised and violated. Repeating read-only model generation is a deliberate and often acceptable at-least-once policy. The row lock and transaction protect candidate insertion plus proposal success ([improvement.rs:390](../../../../src/improvement.rs#L390), [improvement.rs:411](../../../../src/improvement.rs#L411)). The problem becomes material when a continuous learner claims a durable aggregate budget or treats a failed/interrupted proposal as costing zero.

**Minimal remedy.** Persist a dispatch/attempt record before paid work: stable campaign/operation/attempt IDs, reserved budget, provider request identity when available, dispatch certainty, observed usage or explicitly unknown usage, and eventual reconciliation. If the provider supports idempotency or result lookup, use it. Otherwise preserve `outcome_unknown` and make “retry with another possible charge” an explicit bounded policy. Do not invent exactly-once external execution from PostgreSQL idempotency.

**Important counterevidence.** The installed evaluator already behaves more conservatively: it saves `executionStarted` before callbacks and refuses to rerun an attempt with that marker but no saved report ([runner.ts:473](../../../../packages/sdk/src/evaluation/runner.ts#L473), [runner.ts:520](../../../../packages/sdk/src/evaluation/runner.ts#L520)). Saved report submission/finish recover using retained bodies/keys ([runner.ts:778](../../../../packages/sdk/src/evaluation/runner.ts#L778)). Preserve that distinction rather than applying the proposer's automatic retry policy to arbitrary harness execution.

## 2. Medium: `interrupted` is a lifecycle decision, not proof active work stopped

**Observed implementation.** The server's interrupt transition changes evaluation status/reason ([evaluations.rs:329](../../../../src/evaluations.rs#L329)). The SDK checks remote state before execution and before later callbacks ([runner.ts:492](../../../../packages/sdk/src/evaluation/runner.ts#L492), [runner.ts:550](../../../../packages/sdk/src/evaluation/runner.ts#L550)). The signal passed into the callback combines caller cancellation and journal ownership, not remote lifecycle interruption ([runner.ts:415](../../../../packages/sdk/src/evaluation/runner.ts#L415), [runner.ts:591](../../../../packages/sdk/src/evaluation/runner.ts#L591)). There is no remote-interrupt polling inside an awaited callback. A check also cannot eliminate the interval between admission and external dispatch.

**Failure scenario.** An operator interrupts a long-running evaluation while its harness callback is waiting on a model/tool. The service immediately records `interrupted`, but the existing callback can continue until it settles or its own deadline/signal fires. A replacement campaign that interprets this state as “all paid work is stopped” can overlap the original work or release its reservation too early.

**Counterargument.** The current application-owned model cannot forcibly retract an external request. Remote interruption correctly prevents later admissible lifecycle writes/callbacks when observed. It is not a bug that a database status cannot kill an application process; the first-pass review should not imply this requires moving execution into Acclimate.

**Minimal remedy.** A continuous controller should distinguish `stop_requested`, `admission_closed`, `active_work_settled`, and `outcome_unknown`. Propagate a cooperative cancellation token to the owning app; retain in-flight attempt IDs and budget reservations until the app acknowledges settlement or explicitly records uncertainty. Stop admitting subsequent work immediately, but never report confirmed cancellation merely from the lifecycle mutation. Per-callback hard deadlines and adapter-specific cancellation remain app responsibilities.

## 3. High capability gap: operation journals do not recover a campaign decision

**Observed implementation.** The twenty-round controller initializes incumbent, observations, and rejected findings in memory ([twenty/run.ts:115](../../../../examples/self-improvement/twenty/run.ts#L115)). For an accepted candidate it promotes a working channel and only afterward updates the in-memory incumbent ([twenty/run.ts:297](../../../../examples/self-improvement/twenty/run.ts#L297)). Its round/selected-version/progress artifacts are written later ([twenty/run.ts:336](../../../../examples/self-improvement/twenty/run.ts#L336)). The model call and proposal caps are process-local ([luna.ts:11](../../../../examples/self-improvement/luna.ts#L11), [service.ts:65](../../../../examples/self-improvement/service.ts#L65)). The SDK attempt journal records execution/report/submission state, not selection policy, campaign cursor, budget, stop state, or audit exposure ([journal.ts:58](../../../../packages/sdk/src/evaluation/journal.ts#L58)).

**Concrete crash window.** A working-channel promotion commits, but the controller dies before saving the round's decision. The remote content state is ahead of its local feedback/incumbent record. Alternatively a completed report survives while its accept/reject decision and remaining budget do not. Restarting evaluation journals can reconcile that one report; it cannot decide which campaign checkpoint or audit exposure policy should resume.

**Counterargument / downgrade.** The qualification is explicitly disposable and does not promise production resume. The working promotion contains durable history, so this is not proven irrecoverable data loss. An app could reconstruct some state manually. The missing concept is an authoritative campaign transition/journal with deterministic recovery, not merely a missing scheduler or a need for distributed leases.

**Minimal remedy.** One app-owned learner module with a durable campaign record and append-only decisions is sufficient initially. Persist: objective/config revision, incumbent and best checkpoint, feedback cursor, round and candidate IDs, frozen evaluation/manifest identities, decision and release-operation bodies/keys, budget reservations/observed usage, audit exposure state, desired stop state and next action. Save a transition intent before dispatch; settle the same intent on restart before admitting another round. Use revision/CAS ownership to prevent two controllers advancing one campaign. Keep search selection separate from delivery-channel promotion.

## Corrections to retain from the first pass

- The singleton queue is deliberate. Startup holds a PostgreSQL advisory lock ([main.rs:151](../../../../src/main.rs#L151)); shutdown closes claims and waits/aborts owned workers before releasing it ([main.rs:232](../../../../src/main.rs#L232), [runtime.rs:78](../../../../src/runtime.rs#L78)). Lack of a distributed lease protocol alone is not a finding.
- Immutable state commits and external work settlement are separate guarantees. Do not describe the former as proving the latter.
- Evaluator `execution.uncertain` is a valuable safety property, not a defect to “fix” by blindly resuming callbacks. Add campaign reconciliation around it.
- Do not copy all of AgentRun's runtime or treat RRSI's file/ref history as a transactional campaign store. The minimum design is explicit durable intents, outcomes, admission and decisions at the app-owned seam.
