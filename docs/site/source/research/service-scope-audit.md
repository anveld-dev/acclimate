# Service scope audit

This audit reviewed the earlier runtime-platform proposal. Its evidence links now point to that archived snapshot. The [current design](../design/README.md) applies the narrower scope; this page records why. The corrected scope is a small centralized Rust service that improves, versions, and delivers skills, memories, and instructions to existing harnesses. SDKs help developers build plugins and background agents using their native SDKs, with local file caching. The application owns its agent loop, runtime, provider integration, and native session and recovery behavior.

## Where the earlier design exceeded that boundary

- **Running the user's work.** [Design guide](archive/runtime-platform/design/README.md) says Acclimate runs the review; [overview: One normal job](archive/runtime-platform/design/overview.md#one-normal-job) and [execution: Run lifecycle](archive/runtime-platform/design/runtime/execution.md#run-lifecycle) organize the product around managed jobs. Cut this as the default. A consuming application starts and runs its own task; Acclimate supplies versioned files and accepts explicitly authorized feedback.
- **Owning runtime effects.** [Execution: Effects and recovery](archive/runtime-platform/design/runtime/execution.md#effects-and-recovery), [Budgets, policy, and approvals](archive/runtime-platform/design/runtime/execution.md#budgets-policy-and-approvals), and [production: Reliability and overload](archive/runtime-platform/design/runtime/production.md#reliability-and-overload) specify leases, effect admission, approvals, gateway accounting, and reconciliation. These recreate responsibilities of the application and its harness. Cut the managed runtime and provider gateway from the core product; preserve ordinary service request durability and authorization.
- **A sandbox fleet for evaluation.** [Evaluation: What runs where](archive/runtime-platform/design/evaluation/workflow.md#what-runs-where) and [The v1 sandbox](archive/runtime-platform/design/evaluation/workflow.md#the-v1-sandbox) make Linux workers, disposable containers, a gateway, and graders prerequisites. Defer hosted execution and isolation. Start with developer-supplied feedback or evaluation results, clearly labeled by source; never imply externally supplied results were independently verified.
- **A universal harness protocol.** [Protocol: Worker-to-adapter methods](archive/runtime-platform/design/integrations/protocol.md#worker-to-adapter-methods), [Waiting and recovery](archive/runtime-platform/design/integrations/protocol.md#waiting-and-recovery), and [qualification: Harness test suite](archive/runtime-platform/design/runtime/qualification.md#harness-test-suite) define supervision, mediation, and recovery across harnesses. Cut these requirements for file delivery. [SDK: Two SDKs](archive/runtime-platform/design/integrations/sdk.md#two-sdks) should instead describe a small service client and optional integration helpers; native SDK usage belongs in the developer's application. Compatibility examples for Claude, Cursor, Pi, and Codex need separate source-backed research, not assumed capabilities.
- **An evaluation platform before improvement.** [Contracts: The records](archive/runtime-platform/design/evaluation/contracts.md#the-records) defines many trial and grading records, while [selection: Search-side selection](archive/runtime-platform/design/evaluation/selection.md#search-side-selection) introduces a parameterized search policy. Defer scheduling, trial slots, judge orchestration, novelty scoring, and automatic selection. Keep a proposal, its parent version, a diff, and optional evidence so a person can review an improvement. A basic comparison can be supplied by the application without making statistical automation a release prerequisite.
- **A release platform.** [Production: Improvement lifecycle](archive/runtime-platform/design/runtime/production.md#improvement-lifecycle) and [Rollout and rollback](archive/runtime-platform/design/runtime/production.md#rollout-and-rollback) require builds, fresh audits, canaries, and deployment controllers. Replace this lifecycle initially with draft, published version, and an explicit current-version pointer. Keep immutable versions and a way to select an earlier one. Defer cohort rollout and mandatory audit evaluations until a concrete need exists.
- **The roadmap proves the wrong product first.** [Roadmap: Prove the adapter boundary](archive/runtime-platform/design/roadmap.md#0-prove-the-adapter-boundary) through [Qualify a real harness](archive/runtime-platform/design/roadmap.md#3-qualify-a-real-harness) puts durable execution and recovery ahead of delivering useful content. Reorder around publishing, fetching, caching, feedback, and reviewing one improvement. The source design and HTML site have since been revised around the smaller service; the archived pages remain evidence of the earlier scope.

## Smallest useful product

Keep a Rust HTTP service with authenticated project-scoped access to immutable versions of a named collection of files. Each version has a manifest with paths and content digests; a mutable pointer identifies the selected version. Store an improvement proposal as a suggested file diff against a specific parent, with its rationale and any authorized evidence. A reviewer explicitly publishes it. The service may help generate a proposal, but that work need not make it the application's task runner.

An SDK resolves a collection and version, downloads and verifies its manifest and files, and caches them locally by version or digest. The application chooses when to refresh, then passes or exposes the cached files to its own harness using that integration's supported mechanism. Pin a version for a task when consistency matters. If the service is unavailable, an application can use a previously verified cached version according to its own freshness policy; a cache miss must be reported rather than silently inventing content.

Keep transport encryption, scoped credentials, path validation, immutable content integrity, and backups. Feedback submission must be opt-in and scoped: the application selects the content and evidence it is authorized to share, and the service records provenance and applies retention and access controls. Do not automatically ingest full traces or secrets. Make failed uploads retryable with a client-supplied idempotency key; avoid introducing a distributed execution subsystem to achieve this.

## Proposed developer workflow

1. Create a project and publish a collection of instructions, skills, and approved memory files.
2. Configure the application with scoped credentials and a collection; use the SDK to resolve a version and populate its local cache.
3. The application starts its own agent and supplies the selected files through its chosen harness integration.
4. When authorized, the application submits selected feedback or evaluation results with the version used and an idempotency key.
5. A developer or background agent proposes a change against that version, optionally using the submitted evidence; a reviewer inspects the diff and publishes a new version.
6. Applications refresh deliberately; an operator can point consumers back to an earlier immutable version if needed.
